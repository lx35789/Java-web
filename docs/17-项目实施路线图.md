## 1. 五个必须现在定下的工程决策

> 这五个决定如果拖到第 8 周再改，返工量按周计算。

### 1.1 不引入 Redis —— 用 MySQL + 进程内缓存替代

**理由**：设计文档里 Redis 是承担①缓存 ②向量检索（Redis Stack）两个职责。
但实测场景下：
- 知识库 `knowledge_chunk` 规模 **200–500 条**，向量维度 512（BGE-small）。
- 一次余弦相似度暴力检索 = 500 × 512 次乘加 ≈ **0.26 MFLOP**，Java 里 **< 5 ms**。
- Redis Stack 的向量索引能力对这个量级**完全是杀鸡用牛刀**，却要多装一个服务、多一个运维面、多一个答辩被问"为什么用它"的风险点。

**替代方案**：
| Redis 职责 | 替代 |
|---|---|
| 知识向量检索 | MySQL 存 `FLOAT[]`（或 BLOB），启动时载入内存，应用层暴力余弦 |
| 会话 / Token 缓存 | MySQL `user_token` 表，或 JWT 无状态（推荐） |
| 热点数据缓存 | **Caffeine**（进程内，零依赖） |

> 论文里可以写："考虑到知识库规模（<1000 条）与单机部署场景，采用进程内暴力向量检索替代独立向量数据库，实测检索延迟 <5ms，显著降低了部署复杂度。" —— 这是**加分**的工程判断，不是偷懒。

### 1.2 后端工具链：JDK 17 + Maven（走 IDEA 内置 + 阿里云镜像）

**为什么 JDK 17 而不是 21**：Spring Boot 3.x 要求 17+，17 是兼容性最稳的 LTS，第三方库适配最全。毕设不要追新。

**为什么必须配阿里云镜像**：不配的话 Maven 从中央仓库拉 Spring Boot 全家桶，
在你之前已经体验过的那种网络环境下，**大概率卡死或反复超时**。这是必须做的一步，不是优化。

### 1.3 识别：百度主 + Pl@ntNet 备，Key 只放后端

- 百度植物识别：2 万+ 物种，3 元/千次
- Pl@ntNet：免费 500 次/天
- **Key 绝对不能进前端**（前端打包后明文可见）
- 前端只拿 `provider` 和 `degraded` 字段用于展示"本次由谁识别/是否降级"

### 1.4 色彩分析：ExG 分割 + Lab `a*`/`b*`，不用 HSV 硬阈值

这是 `16-真实数据验证结果.md` 的直接结论：

| 项 | 旧方案 | 新方案 |
|---|---|---|
| 叶片分割 | HSV 三窗口并集 | **ExG = 2G−R−B > 10** + 剔除镜面高光 + 形态学开运算 |
| 判别主力 | `health_index = g×100 − y×80 − b×120` | **`chlorophyll = −a*`（CIELAB）** 与 **`ExG` 均值** |
| `health_index` | 主指标 | **降级为展示用**（`green_ratio` 在真实叶片饱和于 0.89–0.93） |

### 1.5 验收标准：配对方向一致率，不是横截面 AUC

| 旧标准 | 新标准 |
|---|---|
| 横截面 AUC > 0.7 | ❌ 作废（类别与拍摄场次混杂，AUC 会随场次翻转） |
| — | ✅ **同一叶片跨次拍摄，指标方向一致率 ≥ 70%**（本次实测 77/82 = **93.9%**） |

## 2. 实施主线：先打通一条最窄的垂直切片

### 2.1 为什么不能"先做完后端再做前端"

这个项目有 **5 层**（前端 / 后端 / AI 服务 / 数据库 / 外部 API），
如果按"一层做完再做下一层"的顺序，你会在第 8 周才第一次发现
"前端上传的文件后端收不到"这种问题——而它本该在第 2 周暴露。

### 2.2 垂直切片 #1：「拍一张照片 → 识别出物种 → 存进我的植物 → 前端看到它」

```
[前端] 上传组件
   │  multipart/form-data
   ▼
[后端] POST /api/v1/files        存图（本地磁盘 /data/uploads）
   │
   ▼
[后端] POST /api/v1/recognitions  调 AI 服务
   │
   ▼
[AI]   POST /ai/v1/recognize
   │      ├─ 百度 Provider  ──失败──▶ Pl@ntNet Provider ──失败──▶ 返回 degraded=true
   │      └─ 返回 {species, confidence, provider, degraded, raw}
   ▼
[数据库] recognition_result + plant + species
   │
   ▼
[前端] 结果页显示物种名 + 置信度 + "由百度识别"角标
```

**这个切片必须在第 4 周结束前跑通。** 它一旦通了，后面每个 Sprint 都只是在
某个环节上加一个能力，风险被摊平。

**Definition of Done（第 4 周验收）**：
1. 手机/电脑上传一张真实植物照片，能存下来并在前端显示缩略图
2. 返回真实物种名，置信度合理
3. **手动把百度的 Key 改错，系统自动降级到 Pl@ntNet，不报错**，前端角标变成"由 Pl@ntNet 识别"
4. 两个 Provider 都失败时，返回 `degraded=true` 并给出"识别失败，请重试或手动选择物种"，**不是 500 错误**

## 4. 五条设计红线（不可违反）

| # | 红线 | 违反后果 |
|---|---|---|
| 1 | **单张照片不下健康结论**，只给"当前状态 + 与历史对比" | 本次实验已证明单图判断不可靠（叶片方差 34.6%–42.2%）。违反=产品逻辑不成立 |
| 2 | **AI 只提供证据，结论由规则引擎给出** | 否则无法回答答辩必问的"为什么是这个结论" |
| 3 | **LLM 只负责措辞，不参与判断** | LLM 幻觉会污染诊断结论；且结论不可复现 |
| 4 | **识别必须有降级链，任何情况都不给用户抛 500** | 第三方 API 挂掉是必然事件，不是意外 |
| 5 | **所有第三方 Key 只在后端** | 前端打包后明文可见，泄露即被盗刷 |

## 9. 本周（W1–W2）立即要做的 7 件事

### 9.1 装 JDK 17

1. 下载 **Eclipse Temurin 17 (LTS)** 的 Windows x64 `.msi`

3. 验证（新开一个 CMD）：

预计输出 `openjdk version "17.0.x"`。

### 9.2 装 Maven + **配阿里云镜像**（这步不做后面会卡死）

1. 下载 `apache-maven-3.9.9-bin.zip`，解压到 `C:\tools\apache-maven-3.9.9`
2. 把 `C:\tools\apache-maven-3.9.9\bin` 加进系统 PATH
3. 新建 `C:\Users\lenovo\.m2\settings.xml`，内容：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<settings xmlns="http://maven.apache.org/SETTINGS/1.0.0">
  <mirrors>
    <mirror>
      <id>aliyun</id>
      <mirrorOf>central</mirrorOf>
      <name>Aliyun Central</name>
      <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
  </mirrors>
</settings>
```

4. 验证：
```cmd
mvn -v
```

> 备选路径：**直接用 IDEA Community 内置的 Maven**（新建项目时勾选 Spring Initializr），
> 但**镜像配置仍然要配**，IDEA 用的是同一个 `~/.m2/settings.xml`。

