## 0. 一页速览

| 问题（实测发现） | 根因 | 本次修复 |
|---|---|---|
| 绿萝照片被判成「月季·霜霉病 58.9%」 | 通用模型 29 类是「物种×病害」联合分类，且后端没做物种校验 | 物种路由 + 物种一致性过滤 |
| 芦荟炭疽病被判成「健康 36.4%」 | CNN 置信度低，但被当成结论展示 | 置信度 < 50% 转兜底复核 |
| 兜底时给不出病名，只说"判断不了" | 大模型只被要求判断健康/异常 | 闭集判断：在**该物种的病害清单**里选，附知识库症状 |
| 月季锈病/霜霉病被硬选一个 | 两者 CNN 概率几乎并列（31.5% vs 30.3%） | 分差 < 8% 输出并列 + 鉴别方法 |
| 第 1 步出现两个「月季」，都打勾且取消不掉 | 百度重复返回同一种；选中状态用 speciesId 判断 | 按物种去重；选中改用候选下标 |
| 月季明明覆盖却被判"无病害数据" | 百度返回「月季花」，前端精确匹配 `includes('月季')` 失败 | 覆盖判断改包含匹配 + 补别名 |
| 没注册的账号无法登录 | 只有 register / login 两个接口 | 新增 `/auth/login-or-register` |
| 隧道下页面 7–8 秒才出来 | 每请求 ~0.8s + 重复请求多 | 图片压缩 + GET 缓存 + 404 负缓存 + 请求合并 |

## 1. 现在的诊断链路

```
手机拍照
  │
  ├─① 物种识别：百度（主）→ Pl@ntNet（备）→ 按物种去重 → 映射植物库
  │     └─ 识别出「绿萝」→ 记录为本次诊断的物种（用户可改选/跳过）
  │
  ├─② 病害识别：自训 ONNX 模型（29 类 / 芦荟专用 5 类）
  │     ├─ 传入 species → 只保留该物种的类别（物种一致性过滤）
  │     ├─ 该物种概率质量 < 20% → 不作为结论
  │     ├─ top1 置信度 ≥ 50% → 直接出结论 + 知识库处置
  │     └─ 否则 → ③
  │
  ├─③ 兜底复核（仅在 ② 给不出可信结论时）
  │     ├─ 已知物种 → 闭集判断：只在「该物种的病害清单」里选（附症状描述）
  │     ├─ 视觉大模型判断「看起来健康 / 有异常」
  │     └─ Pl@ntNet 病害 API（EPPO 编码）作为第二意见
  │
  └─④ 症状诊断：35 条规则（不依赖模型，始终可用）
```

**设计原则**：任何一层给不出可信结论时，宁可说"判断不了/看起来健康"，也不跨物种硬给病名。

## 2. 物种路由与一致性过滤

### 2.1 问题证据

一张**健康绿萝**照片，CNN 的完整分布：

```
月季·霜霉病      41.4%
芦荟·叶斑病      16.4%
...
绿萝（4 类合计）  8.5%
```

只看 top1 会输出「月季·霜霉病」——**物种都不对**。原因是模型把 6 个物种的 29 个类别放在同一个 softmax 里，谁分数高就输出谁。

### 2.2 修复

**① 物种 key 映射**（`common/SpeciesKeys.java`）

中文名 → 模型 species key，支持包含匹配（"月季花" → `Rose`）。

**② 请求带上物种**

- 有植株档案：用 `userPlantId` 查物种
- 第 2 步时用户往往还没选植株，则用第 1 步识别出的 `speciesName`

`/diagnoses/disease` 请求体因此新增可选字段：

```json
{ "photoId": 139, "userPlantId": 45, "speciesName": "芦荟" }
```

**③ AI 服务做过滤**（`ai-service/app/disease.py`）

指定 `species` 且走通用模型时：
- 只保留 `code` 以该物种开头的类别
- 若该物种所有类别概率合计 < `MIN_SPECIES_MASS`（0.20），返回空结果 + 原因

实测：

| 输入 species | 该物种概率合计 | 结果 |
|---|---|---|
| `Money_Plant`（绿萝） | 1.1% | 无结论：`图像与「绿萝」的病害特征不符（该物种概率合计仅 1.1%）` |
| `Rose`（月季） | 93.9% | 月季·霜霉病 90.5% |
| `Aloe`（芦荟） | — | 走专用模型，无需过滤 |

## 3. 低置信度与兜底

### 3.1 置信度门槛

`MIN_TRUST = 0.50`：top1 低于此值不当作结论。

依据：芦荟炭疽病照片，专用模型给出 `健康 36.4% / 锈病 33.0% / 晒伤 14.9%`，**真值炭疽病根本没进前二**。30% 级别的输出等同于瞎猜，展示成结论比说"判断不了"更糟。

### 3.2 闭集判断（本次准确率提升最明显的一项）

做法：把**该物种的病害清单 + 知识库症状描述**一起给视觉大模型，要求它逐条对照后选一个，且只能从清单里选。

效果对比（同一张芦荟炭疽病照片）：

| 版本 | 输出 |
|---|---|
| 只给病名 | 芦荟·叶斑病 ❌ |
| 给病名 + 知识库症状 | **芦荟·炭疽病 ✅**（依据：凹陷斑、黑点，排除黄晕与孢子堆） |

> 关键点：**症状描述来自本地知识库**，模型只是做"图文对照"，处置建议也直接用知识库原文，不依赖模型自由发挥。

### 3.3 近似并列时给两个

月季霜霉病照片，CNN 分布：

```
月季·锈病      31.5%
月季·霜霉病    30.3%   ← 真值
```

两者差 1.2 个百分点，图像上确实难以区分（专业鉴定要看叶背孢子堆）。此时不硬选，输出：

> 可能：月季·锈病 或 月季·霜霉病（中）。鉴别：叶面出现淡黄绿色不规则斑块，叶背对应位置长出灰紫色霉层，多在早晨可见。

### 3.4 Pl@ntNet 病害 API

- 接口：`POST /v2/diseases/identify`，返回 EPPO 编码 + 置信度
- 覆盖：`GET /v2/diseases` 返回 **2500** 条（含虫害）
- 实测耗时：**11.75 秒**；额度与物种识别共用（每次 1 credit）
- 定位：**第二意见**，不是主通道

限制（必须写进报告）：

| 限制 | 说明 |
|---|---|
| 覆盖物种有限 | 官方原话：only a limited list of species and pathologies |
| 无中文 | `lang=zh` 对病害描述不生效，返回拉丁名/EPPO 编码 |
| 无"健康"类别 | 对健康植株会给低分病害（实测健康绿萝 → 介壳虫 33%） |
| 无法映射知识库 | 我们的 `disease_info.eppo_code` **29 条全为 NULL** |

因此当前只取"候选 + 置信度"，交给大模型翻成中文并判断是否成立；置信度 < 0.35 时不采信。

### 3.5 健康判断

CNN 判不了时，视觉大模型先判断"看起来健康 / 有异常"。实测健康绿萝：

> AI 观察：图片中未见明显病斑，植株看起来健康。叶片翠绿饱满，无病斑、霉层、虫孔或腐烂迹象。

## 4. 接口变化

| 接口 | 变化 |
|---|---|
| `POST /api/v1/auth/login-or-register` | **新增**：用户不存在则自动注册并登录；已存在则校验密码（密码错返回 2002，不会静默注册新号） |
| `POST /api/v1/diagnoses/disease` | 请求体新增可选 `speciesName` |
| `POST /api/v1/recognitions` | 结果按物种去重（百度常把同一种返回两条） |
| `POST /ai-service /v1/disease/predict` | 支持 `species` 参数做物种一致性过滤；返回新增 `filtered` / `speciesMass` |
| `POST /ai-service /v1/species/predict` | **新增**：按物种聚合概率的物种识别 |
| `GET /ai-service /health` | 不变 |

登录一体化的规则（刻意如此）：

| 情况 | 结果 |
|---|---|
| 用户名不存在 | 自动注册并登录（用户名 3–32 位，密码 ≥ 6 位） |
| 已存在 + 密码正确 | 正常登录 |
| 已存在 + 密码错误 | 明确报错，**不自动注册** |

> 为什么密码错不自动注册：否则用户手滑输错密码会被悄悄创建新账号，之后找不到自己的植物数据。

## 5. 已知局限（报告里要如实写）

| 局限 | 证据 | 影响 |
|---|---|---|
| 模型只覆盖 6 个物种 | 29 类 = 绿萝/芦荟/月季/姜黄/扶桑/菊花 × 各自病害 | 龟背竹、虎皮兰等 8 种直接跳过病害步骤 |
| 单叶片特写物种识别易错 | 龟背竹单叶：百度 84.6% 判成绿萝；Pl@ntNet 22.4% 判成喜林芋属 | 物种错 → 病害结果必然错 |
| 同属病害难区分 | 炭疽病 vs 叶斑病、锈病 vs 霜霉病 | 需要症状追问或叶背特写 |
| CNN 在真实手机照片上偏弱 | 健康绿萝：绿萝类别概率合计仅 8.5% | 大量走兜底，响应变慢（2–4 秒） |
| 兜底依赖外部大模型 | 需 `GREENTHUMB_LLM_API_KEY`，按量计费 | 未配置时只能给"判断不了" |

**结论**：当前链路能保证"不胡说"（不跨物种、低置信度不硬判），但**不能保证"一定说得准"**。准确率的天花板在模型与数据，不在代码。

## 6. 移动端接入（Capacitor）

### 6.1 方案

Vue 3 打好的 `dist/` 由 Capacitor 包进 APK，App 通过 HTTP 访问后端：

```
GitHub frontend/  →  npm run build  →  dist/  →  Capacitor  →  APK
```

后端（Spring Boot + MySQL + Python）**不打包进 APK**——Android 无法运行 MySQL，Spring Boot 也不支持 ART。

### 6.2 构建

```bash
cd frontend
npm run build -- --mode android     # 使用 .env.android
npx cap sync android
cd android && ./gradlew assembleDebug
```

要求：**JDK 21**、compileSdk/targetSdk **36**、minSdk 24。

### 6.3 运行时服务器地址

App 不写死地址，登录页「服务器设置」可修改，存 `localStorage` 的 `gt_api_base`：

- 自动补 `http://`
- 自动补 `/api/v1`
- 支持随时切换（局域网 / 公网隧道 / 云服务器）

### 6.4 明文与混合内容

`capacitor.config.json` 用 `server.androidScheme: "http"`，App 源为 `http://localhost`；访问 https 后端不触发混合内容拦截。调试期允许明文（`usesCleartextTraffic="true"`），正式发布应换 HTTPS。

### 6.5 上传前压缩

手机原图 3–8 MB，走公网隧道上传极慢。`utils/image.js` 在选图后压缩：

| 参数 | 值 |
|---|---|
| 长边 | 1600 px |
| 质量 | JPEG 0.8 |
| 跳过条件 | ≤ 1.2 MB 且长边 ≤ 1600 |
| 失败兜底 | 原样上传，绝不阻断 |

实测：3.2 MB → 121 KB；经国内隧道上传从十几秒降到 **0.6 秒**。

### 6.6 应用内相机（点一下直接拍，左下角进相册）

**演进过程**（三次迭代，前两次都不对）：

| 版本 | 做法 | 问题 |
|---|---|---|
| v1 | 单个 `<input type="file" capture>` | 只能拍照，没有相册入口 |
| v2 | 两个 input（带/不带 capture）| 部分 ROM 上点「拍照」仍进相册（见下） |
| **v3** | **应用内相机 `getUserMedia`** | — |

#### 为什么 v2 会「点拍照进相册」

Android 11+ 的包可见性限制：没有 `<queries>` 声明 `IMAGE_CAPTURE` 时，
`ACTION_IMAGE_CAPTURE.resolveActivity()` 返回 `null`，Capacitor 的
`showImageCapturePicker()` 返回 false 后**静默**回退到文件选择器，
日志里只有一行 warn，用户侧无任何提示。

#### 为什么最终改用应用内相机

系统相机是独立 App，**画面和按钮都由它控制，无法在左下角加「进相册」按钮**。
要自定义 UI 只有一条路：在 WebView 里用 `getUserMedia` 自己出画面。

`components/CameraCapture.vue`：

```
全屏 video（object-fit: cover）
├── 顶部：关闭 ✕ ／ 提示文案 ／ 手电筒
├── 中间：四角取景框
└── 底部：[ 相册 ]   [ 快门 ]   [ 翻转 ]
       左下角      居中      右下角
```

| 交互 | 行为 |
|---|---|
| 点上传区 | 直接打开相机（不再有「拍照 / 相册」选择面板） |
| 快门 | 把当前帧画到 canvas → `toBlob` → File，尺寸取 `videoWidth/Height` |
| 左下「相册」 | 关闭相机 → 唤起相册（原生走 Camera 插件 Photos，浏览器走 input） |
| 右下「翻转」 | 切换 facingMode 并重开流；只有一个摄像头时置灰 |
| 前置拍照 | canvas 先 `translate(w,0) + scale(-1,1)` 还原真实方向，避免文字镜像 |

#### 权限（关键，且与上一版结论相反）

`getUserMedia` **必须在 Manifest 声明 CAMERA**：

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

调用链：`getUserMedia` → WebView → `BridgeWebChromeClient.onPermissionRequest`
→ 看到 `resource.VIDEO_CAPTURE` → 申请 `Manifest.permission.CAMERA`。

若未声明，`permissionLauncher` 无权限可申请，`PermissionRequest` 不会被 grant，
`getUserMedia` 直接 reject（`NotAllowedError`），而用户在系统设置里
**根本找不到这个 App 的相机开关**——是个很难排查的死局。

> 与 6.6 上一版的结论（「不要声明 CAMERA」）不冲突，因为场景变了：
> 那版走 `input[capture]`，声明后被拒会静默 `onReceiveValue(null)`；
> 现在相机完全由应用内组件接管，不再依赖 `input[capture]`。

#### 降级链

```
getUserMedia 成功        → 应用内相机（默认）
getUserMedia 失败        → 「改用系统相机」按钮 → Camera 插件的 source='Camera'
仍失败 / 浏览器无摄像头  → 文件选择器
```

| 检查项 | 结果 |
|---|---|
| 上传区 input 数量 / capture | 1 个 / 无 |
| 相机全屏层级 | `position: fixed`，`z-index: 4000` |
| 相册按钮位置（左下角） | `left=26, top=650`（视口 459×732） |
| 快门居中 | 中心 x=230，视口中心 229.5 |
| 取景框角标 | 4 个 |
| 就绪态 | video 900×600 播放中，快门可用，翻转可用 |
| 快门拍照 | 生成 photo-*.jpg，预览 900×600，开始识别按钮解禁 |
| 左下「相册」 | 关闭相机 + 文件选择器被唤起 1 次 |
| 无摄像头时 | 显示「相机权限被拒绝」，并提供「改用系统相机」 |
| 控制台错误 | 0 |

> 实测中修掉一个真 bug：关闭按钮原本绑的是 `close`（只停流、不关界面），
> 导致点 ✕ 后画面不消失。已重命名为 `stopStream()` / `dismiss()` 并修正调用。

#### 坑 1：Manifest 里 **不要** 声明 CAMERA 权限

读 Capacitor 源码 `BridgeWebChromeClient.onShowFileChooser`：

```java
boolean capturePhoto = captureEnabled && acceptTypes.contains("image/*");
if (capturePhoto) {
    if (isMediaCaptureSupported()) {
        showMediaCaptureOrFilePicker(...);   // → ACTION_IMAGE_CAPTURE 调系统相机
    } else {
        permissionListener = (granted) -> {
            if (granted) showMediaCaptureOrFilePicker(...);
            else {
                Logger.warn("Camera permission not granted");
                filePathCallback.onReceiveValue(null);   // ← 静默返回 null
            }
        };
        permissionLauncher.launch(new String[]{ Manifest.permission.CAMERA });
    }
}

private boolean isMediaCaptureSupported() {
    return PermissionHelper.hasPermissions(ctx, CAMERA)
        || !PermissionHelper.hasDefinedPermission(ctx, CAMERA);
}
```

关键：`MediaStore.ACTION_IMAGE_CAPTURE` 唤起的是**系统相机 App**，
按 Android 官方说明这种用法**不需要 CAMERA 权限**。

所以：

| Manifest | 结果 |
|---|---|
| 不声明 CAMERA | `!hasDefinedPermission` = true → 直接调系统相机，**零权限弹框** ✅ |
| 声明 CAMERA | 首次弹运行时权限框；**用户一旦拒绝 → 静默 receiveValue(null)**，前端表现为“点了没反应” ❌ |

这也是为什么 Manifest 里只留 `INTERNET`，另外只写一条
`<uses-feature android.hardware.camera required="false">`（让无摄像头设备也能装）。

#### 坑 2：FileProvider 必须映射 external-files-path

Capacitor 拍照的临时文件写在：

```
getExternalFilesDir(Environment.DIRECTORY_PICTURES)
= /storage/emulated/0/Android/data/<包名>/files/Pictures/JPEG_xxx.jpg
```

`res/xml/file_paths.xml` 只靠 `<external-path path=".">` 属于祖先匹配，
在部分 ROM 上会抛 `FileUriExposedException`，
表现为**相机能开、拍完回到 App 却没图**。显式补一条：

```xml
<external-files-path name="my_external_files" path="." />
```

#### 验证记录（dev server + 浏览器实测）

| 检查项 | 结果 |
|---|---|
| 两个 input 的 capture | 分别为 `environment` / `null` |
| 占位区布局 | 区域 422×200，两按钮各 82×71 居中，无横向溢出 |
| 底部面板 | fixed 贴底（gap=0）、全宽、上圆角 14px、遮罩 0.42、z-index 3000 |
| 面板项（无图） | 拍照 / 从相册选择 / 取消 |
| 面板项（有图） | 标题「更换照片」+ 拍照 / 从相册选择 / 移除照片 / 取消 |
| 选图后压缩 | 2400×1800 → 1600×1200，113 KB → 14 KB |
| 选图后状态 | 预览渲染成功、「开始识别」按钮解禁、占位按钮消失 |
| 控制台错误 | 0 |

## 7. 部署与运行

### 7.1 三件套

```bash
# 后端（注意 -Djava.io.tmpdir）
java -Djava.io.tmpdir=<可写目录> -jar greenthumb-backend-0.1.0.jar \
     --spring.profiles.active=dev \
     --spring.config.additional-location=file:./src/main/resources/

# AI 服务
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 隧道（显式 127.0.0.1，避免 localhost 解析到 ::1 而连不上 IPv4 监听）
cpolar http 127.0.0.1:8080
```

### 7.2 踩过的两个坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 后端启动报 `Unable to create tempDir` | Tomcat 无权限在 `%TEMP%` 建目录 | 用 `-Djava.io.tmpdir` 指到可写目录 |
| 隧道 502 | cpolar 连 `localhost:8080` 走了 IPv6 `::1` | 显式写 `127.0.0.1:8080` |

### 7.3 隧道说明

cpolar 免费版**每次重连都会分配新域名**，App 里需要同步更新。要固定地址只能用云服务器或付费隧道。
