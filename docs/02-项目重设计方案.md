## 1. 项目定位

### 1.1 一句话

用户拍照识别植物 → 系统生成个性化养护计划 → 到期提醒 → 出问题时给出**有依据的诊断**。

### 1.2 核心价值主张（★ 修正）

初版隐含的主张是「**识别得准**」。本方案修正为：

> ### 「会解释为什么的养护助手」

**为什么改**：识别准确率的天花板由公开数据质量决定（House Plant Species 是 Bing 爬取、非专业标注），自研模型在物种识别上打不过 Pl@ntNet 这类工业级服务——把项目价值押在"识别准确率"上，等于选了一个必输的赛道。

而下面这些能力，通用识别 API **给不了**：

- 「为什么这周要浇两次水？」→ 能拆解出 `基准7天 × 夏季0.8 × 空调房0.9 × 陶盆0.9 = 5天`
- 「为什么你觉得是浇多了？」→ 能回答「因为你近 14 天浇了 5 次，而绿萝建议 7 天一次，且黄叶从下部老叶开始」
- 「这个说法哪来的？」→ 能给出知识库来源

**这才是项目的护城河，也才是答辩时能讲清楚"我们做的不是又一个识花 App"的地方。**

三条价值主线：

| 主线 | 含义 | 落地功能 |
|---|---|---|
| **认得准** | Top-3 + 承认不确定性，让用户确认而非假装权威 | F4 拍照识别 |
| **说得清** | 每个建议都给出系数依据 / 知识来源 | F5 计划生成、F9 问答、F11 症状诊断 |
| **记得住** | 计划 → 提醒 → 日志闭环，沉淀养护历史 | F6/F7 |

### 1.3 角色

普通用户（USER）、管理员（ADMIN）

### 1.4 边界

**保留初版**：

- 只做室内常见绿植 50 种（绿萝、龟背竹、多肉、虎皮兰、发财树等）
- 不接土壤湿度传感器；光照/温湿度靠用户手动录入或天气 API
- 不做电商、不做社交（社区仅可选，且只做简单评论）
- 识别结果给 Top-3，不追求 100% 准确

**★ 新增边界（这是修正带来的）**：

| 新边界 | 理由 |
|---|---|
| 病害识别**只覆盖有标注数据的病理性病害**（5–8 类），不承诺全病害谱系 | 没有数据的类别做不了，见 3.2 |
| 生理性症状（黄叶/焦边/落叶）**不做图像分类**，走规则 + RAG 诊断 | 黄叶是"结果"不是"原因"，图像上无法区分病因 |
| **不提供农药处方**，只给园艺级处理建议 | 安全合规，且超出项目能力边界 |
| 识别模型的训练数据仅用于校内项目，**不对外发布** | House Plant Species 授权限个人使用 |

### 1.5 目标场景

设计一切功能前先锚定这三个场景：

| # | 场景 | 期望 |
|---|---|---|
| **S1** | 刚买一盆绿萝，不知道多久浇一次水 | 拍照识别 → 自动生成计划 → 告诉"5天一次，因为…" |
| **S2** | 养了三个月的龟背竹，叶子开始发黄 | 症状诊断 → "最可能是浇水过多" + 判断依据 + 怎么做 |
| **S3** | 出差一周回来，多肉叶片发皱 | 看提醒日历 → 补浇 → 记一条日志 |

> **判断功能要不要做的标准**：它是否让 S1/S2/S3 更顺畅。不相关的一律砍。

### 2.2 关键流程设计

#### 流程 A — 拍照识别（F4）

```
上传照片
  ├─ 预处理：EXIF 旋转矫正 → 等比压缩到长边 1024 → 尺寸归一 224×224
  ├─ 自研模型推理 → Top-3 + 置信度
  ├─ 兜底判定（三选一触发 Pl@ntNet）：
  │    ① top1 置信度 < 0.50
  │    ② top1 命中"模型未覆盖物种"标记
  │    ③ 用户主动点"识别不准"
  ├─ 结果融合：按学名去重 → 置信度排序 → 取 Top-3
  └─ 返回：物种图 / 名称 / 置信度 / 养护要点摘要
       ↓
     用户「采纳」或「纠正」
       ↓
     生成 user_plant + 初始 care_plan
```

**★ 关键设计：把用户的纠正落库。**

`recognition_record.confirmed` + 纠正后的 `species_id` 是宝贵的种子数据：
- 短期：统计模型在真实场景的准确率（比测试集更有说服力）
- 长期：作为主动学习（active learning）的标注来源
- 答辩：可以讲"我们设计了数据闭环"

#### 流程 B — 养护计划生成（F5）

见 3.4 节完整公式与系数表。核心是**每个数字都可追溯**。

#### 流程 C — 症状诊断（F11）★ 本次修正的核心

```
用户输入："叶子黄了" +（可选）照片
   │
   ├─ 先跑病害模型（若用户上传了照片）
   │    └─ 高置信度（≥0.7）命中病理性类别 → 病害路径，结束
   │
   └─ 否则进入症状路径：
        ├─ 输入：症状标签（UI 提供多选）+ 物种 + 养护历史（近30天浇水/施肥）+ 环境
        ├─ 规则引擎判因：symptom_rule 表，症状 × 条件 → 候选病因加权
        ├─ 取候选病因 Top-3（附带"命中了哪几条规则"）
        ├─ RAG 检索：该物种 × 该病因的知识片段
        └─ LLM 生成：最可能原因 + 判断依据 + 该怎么做
        ↓
      落库 disease_record(diagnosis_type = 'SYMPTOM')
```

**★ 架构原则：规则引擎缩小范围 → RAG 补充依据 → LLM 负责表达。**

三者各司其职。如果让 LLM 直接看图判断"为什么黄叶"，必然幻觉——因为同一张黄叶照片可能对应 5 种病因，信息量根本不够。

**可解释性示例输出**：

> **最可能：浇水过多（置信度 78%）**
> **判断依据**：① 黄叶从下部老叶开始 —— 符合积水烂根的特征；② 你近 14 天浇了 5 次，绿萝建议 7 天一次；③ 花盆是釉面陶瓷盆，透气性差。
> **建议**：先停止浇水，把盆移到通风处…

用户问「为什么」，系统**答得出来**。这就是价值主张"说得清"的落地。

## 3. AI 方案（重构）

### 3.1 模块一：物种识别

#### 数据

| 来源 | 用途 | 说明 |
|---|---|---|
| **House Plant Species**（Kaggle） | **主训练源** | 47 类 / 14,790 张。**唯一覆盖室内植物的中等规模公开集** |
| **Pl@ntNet API** | **兜底推理** | 免费 500 次/天 |
| iNaturalist | ❌ 不采用 | 野外观察 ≠ 室内盆栽，分布不一致；各观察许可混杂（CC BY / CC BY-NC） |

**主训练源的已知问题与处置**：

| 问题 | 处置 |
|---|---|
| 类间不平衡：66 张（Yucca）～ 547 张（Monstera）**差 8 倍** | 加权损失 + 对 <150 张的类做额外增强 + 分层划分 |
| Bing 爬取，**非专业人员人工清理** → 标签噪声 | 人工抽检每类 20 张，剔除明显错标/非植物/严重模糊图 |
| 室内室外混杂、整株照与特写混杂 | 不强行统一（真实场景也混杂），但**测试集必须人工过一遍** |
| 授权**仅限个人使用** | 定位校内项目，论文/对外发布需说明 |

#### 模型选型

**选 MobileNetV3-Large（4.2M 参数）或 EfficientNet-B0。**

| 选项 | 判断 |
|---|---|
| MobileNetV3-Large | ✅ **推荐**。参数少、CPU 可推理、ONNX 部署友好、小数据下不易过拟合 |
| EfficientNet-B0 | ✅ 可替代，精度略高、速度略慢 |
| ResNet50 | ❌ **不用**。25M 参数，尾类只有 66 张，必然过拟合 |

> 直觉：14,790 张 / 47 类，平均每类 315 张，最少的只有 66 张。**这个数据量撑不起大模型**，选小模型 + 强增强 + 迁移学习才是对的。

#### 训练策略

```
Stage 1  替换分类头(47类)，冻结主干，只训 head
         lr=1e-3, 10 epoch

Stage 2  解冻最后 2 个 stage，小学习率微调
         lr=1e-4, 20 epoch, 余弦退火 + 早停

损失      加权 CrossEntropy，weight ∝ 1/类频次（设上限防极端）
增强      RandomResizedCrop(224, scale=0.6~1.0) / HorizontalFlip
          ColorJitter(0.3) / RandomErasing(p=0.25) / RandAugment
划分      Stratified 70/15/15，按类分层，保证尾类在 val/test 也有样本
```

#### 部署

- 导出 `torch.onnx.export`，opset 13，输入 `1×3×224×224`
- **ONNX Runtime CPU 推理**（无需 GPU 也能演示，答辩现场更稳）
- FastAPI `POST /v1/recognize/species` → Top-3

#### 指标

| 指标 | 目标 | 说明 |
|---|---|---|
| Top-1 | ≥ 75% | 如实测显著低于此，优先查**标签噪声**而不是调模型 |
| **Top-3** | **≥ 92%** | ★ 这才是产品的核心指标 |
| 尾类 per-class recall | ≥ 60% | 关注 66 张那几类 |
| 混淆矩阵 | 必须产出 | 重点分析易混组（各种蕨类 / 各种多肉） |

> **预期管理**：不要承诺 99%。如实报告 Top-1 78% / Top-3 94% 比吹一个假数字强得多，而且产品设计本来就是"给 Top-3 让用户确认"。

#### ★ 关键工程决策：识别服务双通道

```
通道 A：自研模型    → 覆盖 47/50 种，主路径
通道 B：Pl@ntNet    → 未覆盖物种 + 低置信度兜底
```

**这条决策的真正价值是解除进度依赖**：Phase 3 可以**先用 Pl@ntNet 把整条链路跑通**（半天工作量），模型训练并行进行，训好后切换 `provider` 字段即可，前端零改动。**避免"等模型训好才能写后端"的进度风险。**

### 3.2 模块二：病害识别 + 症状诊断 ★ 修正核心

#### 为什么要拆成两个模块

初版把「白粉病、黑斑病、**黄叶**」并列成 5–10 个分类类别。这混淆了两类本质不同的问题：

| 类型 | 例子 | 图像上可分吗 | 处理方式 |
|---|---|---|---|
| **病理性病害** | 白粉病、黑斑病、炭疽病、锈病 | ✅ 可分（有特征性病斑/霉层/虫体） | 图像分类模型 |
| **生理性症状** | 黄叶、焦边、落叶、徒长 | ❌ **不可分** | 规则 + RAG 诊断 |

**为什么"黄叶"不可分**：黄叶是**结果**，不是**原因**。同一张黄叶照片，可能是浇水过多、缺水、光照不足、肥害、低温、空气干燥、正常代谢……**单凭一张照片信息量根本不够**。强行做分类 = 制造幻觉，用户会更不信任系统。

**拆开后反而更好讲**：「我们把病理性病害和生理性症状分开处理」是一个能讲清楚的设计决策，比笼统说"图片分类"高一个层次。

#### 模块 2A — 病害识别（图像分类）

| 项 | 内容 |
|---|---|
| **数据** | **Indoor Plant Disease Dataset**，21,097 张 / 15+ 类 |
| 覆盖物种 | 芦荟、仙人掌(Opuntia)、**绿萝**、**虎皮兰**、吊兰 |
| 类别示例 | Healthy、Aloe Rust、炭疽病、叶斑病、晒伤、胭脂虫感染、细菌性萎蔫、锰中毒、叶片枯萎、真菌性叶斑、叶尖坏死 |
| 来源 | Mendeley Data（CC BY 4.0）× 2 + Roboflow Universe（PD Equivalent，需署名） |
| 模型 | 同 MobileNetV3，独立训练一个头 / 一个模型 |
| **指标** | **macro-F1 ≥ 70%**（类不平衡，不用 accuracy）+ 混淆矩阵 |

**★ 两条实现路线**：

| | 方案 A（Demo 用） | 方案 B（论文用） |
|---|---|---|
| 做法 | 扁平化为 N 类多分类 | **物种条件化双头模型** |
| 输出 | 「绿萝-细菌性萎蔫」 | 先识别物种 → 只在该物种的病害子集里分类 |
| 优点 | 实现简单 | 逻辑正确："芦荟锈病"不会出现在绿萝的诊断里 |
| 缺点 | 可能输出跨物种的荒谬组合 | 复杂度上升 |

> 建议：**Demo 用 A，论文把 B 作为改进方向**。这样既有可交付的 Demo，又有可写的创新点。

**★ 铁律：处理建议不来自模型。** 模型只输出类别，处理建议来自 `disease_info` 表（人工整理）。模型会错，但建议不能错。

#### 模块 2B — 症状诊断（规则 + RAG，不做分类）

| 项 | 内容 |
|---|---|
| 输入 | **症状标签**（UI 多选，用户点选）+ 照片（仅展示，**不参与判因**）+ 物种 + 养护历史 + 环境 |
| 判因 | `symptom_rule` 表：症状 × 条件 → 候选病因加权求和 |
| 输出 | 候选病因 Top-3 + 置信度 + **命中了哪几条规则** |
| 增强 | RAG 检索该物种 × 该病因的知识片段，LLM 组织成自然语言 |

完整规则库见 **`03-症状诊断规则库.md`**（含 8 类症状 / 约 35 条规则 / 判因算法）。

**判因算法（简述）**：

```
对每个候选病因 C：
    score(C) = Σ weight(rule)  对所有命中且指向 C 的规则
归一化：confidence(C) = score(C) / Σ score(所有候选)
取 Top-3，confidence < 0.15 的丢弃
若最高 confidence < 0.4 → 不武断下结论，转而引导用户补充信息或转人工知识问答
```

**为什么用规则而不是直接用 LLM**：
- 规则**可解释**——能列出"命中哪几条"，这正是价值主张要的
- 规则**可测试**——每条规则可以写单元测试，LLM 不行
- 规则**零成本、零延迟**
- LLM 只负责把结构化结论写成自然语言，**不参与决策**。即使 LLM 抽风，结论也是对的

### 3.3 模块三：知识库问答（RAG）

#### 语料策略（★ 修正）

| 来源 | 许可 | 用法 |
|---|---|---|
| **自撰养护知识** | 自有 | ★ **主源，质量最高** |
| Wikipedia | CC BY-SA 4.0 | 主源，可抓取，**必须署名** |
| 公开论文 / 园艺机构公开资料 | 视情况 | 摘要改写 |
| RHS、Gardening Know How | ⚠️ **版权** | **不整段入库**，仅人工阅读后改写要点 |

**关于 RHS / GKH**：初版写「整理成 JSON」。整站抓取 + 存入知识库 + 经 LLM 生成回答对外提供，这是**衍生作品分发**，不属于合理使用。校内项目风险低，但只要项目可能对外（开源、写进简历、参赛），就要按合规做。

**★ 但更重要的一点（不只是合规）**：

> **自撰内容的质量直接决定 RAG 的效果。**

与其爬 1000 篇杂乱网页，不如**认真写 50 种植物的"养护卡片"**——每种 300–500 字，涵盖：浇水频率与判断方法、光照需求、施肥、常见问题与排查。50 × 400 字 = 2 万字，两个人两周能写完，**而且这 2 万字的结构化程度和针对性远超任何爬来的语料**。

这是本方案对 RAG 模块最重要的建议。

#### 流程

```
用户提问："绿萝叶子发黄怎么办"
  → ① 查询改写（结合上下文补全）
        "绿萝叶子发黄怎么办"（若来自某盆植物会话，注入物种与昵称）
  → ② Embedding
  → ③ Redis 向量检索 Top-K = 5
        ★ 元数据加权：命中当前 user_plant 的物种 → 提权
  → ④ 拼 Prompt
        [系统指令] + [检索片段 + 来源标注] + [用户的植物上下文] + [问题]
  → ⑤ LLM 生成，硬约束：
        · 基于检索片段回答，片段没提到就说不知道
        · 标注来源
        · 不编造农药用量与浓度
  → ⑥ 返回回答 + 引用列表
  → ⑦ 落库 qa_message（含 retrieved_chunks / citations，便于评测与追溯）
```

#### 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 嵌入模型 | **BGE-M3 或 bge-large-zh** | 中文场景效果好、**可本地部署**、免费、离线可演示 |
| 向量库 | **Redis Stack** | 已在技术栈内；Spring AI 有官方 `RedisVectorStore` |
| 分块 | 语义段落切，**300–500 token，overlap 50** | 太短丢上下文，太长稀释语义 |
| 元数据 | 每 chunk 带 `article_id / species_id / category / source / source_url / license` | 支持加权检索 + 来源标注 |
| 编排 | Spring AI | 统一 LLM 与向量库抽象 |

#### 评测

- 建 **50–100 条 QA 评测集**（人工写，含标准答案要点）
- 指标：检索命中率@5、引用正确率、人工评分 1–5
- **对比实验：无 RAG vs 有 RAG** ← 这是论文/答辩的标准动作，务必做

### 3.4 模块四：个性化养护建议

#### 规则引擎公式（把初版的定性描述落地）

```
effective_interval = clamp(
      base_interval
    × season_coef      // 季节
    × light_coef       // 光照
    × temp_coef        // 温度
    × humidity_coef    // 湿度
    × pot_coef         // 花盆材质
    × ac_coef,         // 空调房
  min_interval, max_interval)
```

#### 系数表

| 维度 | 取值 | 系数 |
|---|---|---|
| **季节** | 春 / 夏（生长季） | 0.8 |
| | 秋 | 1.0 |
| | 冬（休眠） | 1.5 |
| **光照** | DIRECT（直射） | 0.85 |
| | BRIGHT_INDIRECT（明亮散射） | 1.0 |
| | MEDIUM（中等） | 1.15 |
| | LOW（弱光） | 1.4 |
| **温度** | > 30°C | 0.85 |
| | 10 – 30°C | 1.0 |
| | < 10°C | 1.3 |
| **湿度** | < 30% | 0.9 |
| | 30 – 60% | 1.0 |
| | > 60% | 1.15 |
| **花盆** | 陶盆（透气） | 0.9 |
| | 塑料盆 | 1.0 |
| | 陶瓷盆（釉面） | 1.1 |
| **空调房** | 是 | 0.9 |

**边界**：`clamp` 到 **[2, 30] 天**。

**施肥间隔**（单独规则）：只看季节。

```
生长期（春/夏）：fertilizer_interval × 0.7
休眠期（冬）   ：× 2.0，或直接建议停肥
clamp 到 [14, 90] 天
```

#### ★ 可解释性输出（价值主张的落地）

每次生成计划，把系数明细存进 `care_plan.coefficient_detail`，前端可直接渲染：

```
绿萝 · 客厅 · 陶盆 · 空调房
  基准间隔            7.0 天
  × 夏季系数    0.8   5.6 天
  × 空调房      0.9   5.0 天
  × 陶盆透气    0.9   4.5 天
  ────────────────────────────
  建议间隔            5 天   （已限制在 2–30 天区间）
```

**用户能看懂每一个数字怎么来的。这就是"说得清"。**

#### LLM 润色

**★ 铁律：LLM 只做表达，不做决策。** 数字全部来自规则引擎。

```
输入（结构化）：{ species: 绿萝, interval: 5, factors: [夏季, 空调房, 陶盆] }

输出（自然语言）：
「本周建议浇水 1–2 次。绿萝在夏季生长旺盛，需水偏多；但你把它放在空调房、
 用的是透气的陶盆，水分蒸发比一般情况快，所以间隔从基准的 7 天缩短到 5 天左右。
 判断方法：手指插入土中 2–3 cm，感觉干了再浇，不要按固定日子浇。」
```

这样即使 LLM 服务不可用，降级返回结构化文本即可，**建议的数字永远是对的**。

### 5.2 技术栈（修正）

| 层 | 初版 | **修正后** |
|---|---|---|
| 后端 | Spring Boot 3 + Security + JPA/MyBatis-Plus | ✅ 不变 |

#### ★ 移除 PgVector 的理由

1. **少一个数据库**：部署、备份、监控、连接池全部减半
2. **消除跨库一致性问题**：初版的数据被 MySQL(PG) 割裂，`plant_species` 在 MySQL、`knowledge_article` 在 PG，join 不了、事务跨不了
3. **Redis 本来就在技术栈里且没有用途**——正好用它承担
4. **Redis Stack 是正经的向量数据库**：RediSearch 提供 KNN 向量检索，Spring AI 有官方 `RedisVectorStore` 实现，不影响答辩表述
