# 症状诊断规则库（F11）

> 本文件是 `02-项目重设计方案.md` 中 **3.2 模块 2B** 的配套数据资产。
> 作用：把「叶子黄了怎么办」这类**生理性症状**问题，从"靠 LLM 瞎猜"变成"**可解释、可测试的规则判因**"。

---

## 1. 为什么需要这个库

用户说「叶子黄了」，这句话的信息量**不足以确定病因**：

| 同一张黄叶照片，可能的病因 |
|---|
| 浇水过多（烂根） |
| 浇水不足 |
| 光照不足 |
| 光照过强（晒伤） |
| 施肥过多（肥害） |
| 缺肥（缺氮/缺铁） |
| 空气干燥 |
| 低温冻伤 |
| 正常代谢（老叶更新） |
| 水质问题（硬水/含氯） |

**一张照片无法区分这 10 种情况。** 但如果加上「黄叶从下部老叶还是新叶开始」「最近浇了几次水」「放在哪里」——范围立刻能收缩到 2–3 种。

**本规则库就是把园艺专家的这套判断逻辑显式化、可计算化。**

## 2. 数据模型

### 2.1 表结构

```sql
CREATE TABLE `symptom_rule` (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  symptom_code  VARCHAR(32)     NOT NULL COMMENT '症状编码 YELLOW_LEAF',
  cause_code    VARCHAR(32)     NOT NULL COMMENT '病因编码 OVERWATER',
  condition_json JSON           NOT NULL COMMENT '触发条件（谓词）',
  weight        DECIMAL(3,2)    NOT NULL COMMENT '命中权重 0.00-1.00',
  explain_tpl   VARCHAR(255)    DEFAULT NULL COMMENT '可解释模板',
  priority      INT             NOT NULL DEFAULT 0 COMMENT '同分时的排序',
  enabled       TINYINT         NOT NULL DEFAULT 1,
  created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_symptom (symptom_code, enabled),
  KEY idx_cause (cause_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='症状判因规则';
```

### 2.2 条件谓词（condition_json）支持的字段

| 字段 | 取值 | 来源 |
|---|---|---|
| `leaf_position` | `OLD` 老叶先 / `NEW` 新叶先 / `ANY` 不限 / `UNIFORM` 全株均匀 | **用户选择**（UI 必选项） |
| `watering_ratio` | `{op, value}` 近期实际浇水次数 ÷ 应浇水次数 | 由 care_log + care_plan 计算 |
| `light_level` | `DIRECT` / `BRIGHT_INDIRECT` / `MEDIUM` / `LOW` | user_plant.light_level |
| `humidity` | `{op, value}` 百分比 | user_environment + 天气 |
| `temp` | `{op, value}` 摄氏度 | 天气 API |
| `season` | `SPRING` / `SUMMER` / `AUTUMN` / `WINTER` | 当前日期 |
| `fertilizing` | `NONE` 从未施肥 / `RECENT` 近7天施过 / `HEAVY` 浓度过高 | care_log |
| `pot_material` | `TERRACOTTA` / `PLASTIC` / `CERAMIC` | user_plant.pot_material |
| `vein_pattern` | `GREEN_VEIN` 叶脉绿而叶肉黄 / `NONE` | **用户选择**（可选） |
| `photo_disease_hit` | `true` 病害模型高置信度命中 | 病害模型输出 |

**多字段 = AND 关系**（全部满足才命中）。

### 2.3 病因字典（cause_info）

```sql
CREATE TABLE `cause_info` (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  cause_code   VARCHAR(32)     NOT NULL,
  name_cn      VARCHAR(64)     NOT NULL,
  category     VARCHAR(16)     NOT NULL COMMENT 'WATER/LIGHT/NUTRIENT/ENV/PEST/NORMAL',
  description  TEXT,
  action_plan  TEXT            COMMENT '该怎么做（分步骤）',
  urgency      VARCHAR(16)     DEFAULT 'MEDIUM' COMMENT 'LOW/MEDIUM/HIGH',
  created_at   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_cause_code (cause_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='症状病因字典';
```

## 6. 判因算法

```python
def diagnose(symptom_codes, context) -> List[Candidate]:
    """
    symptom_codes : 用户勾选的症状列表
    context       : {leaf_position, watering_ratio, light_level, humidity,
                     temp, season, fertilizing, pot_material,
                     vein_pattern, cause_hint}
    """
    scores = defaultdict(float)
    hits   = defaultdict(list)      # 病因 -> 命中的规则（可解释性）

    for sym in symptom_codes:
        for rule in load_rules(sym):                 # 已 enabled
            if match(rule.condition_json, context):  # 多字段 AND
                scores[rule.cause_code] += rule.weight
                hits[rule.cause_code].append(rule)

    if not scores:
        return []                                    # 信息不足，引导补充

    total = sum(scores.values())
    candidates = [
        Candidate(
            cause_code = c,
            confidence = s / total,
            evidence   = [r.explain_tpl for r in hits[c]],
            hit_rules  = [r.id for r in hits[c]],
        )
        for c, s in scores.items()
    ]
    candidates.sort(key=lambda x: -x.confidence)
    return [c for c in candidates[:3] if c.confidence >= 0.15]
```

### 输出降级策略（★ 重要）

| 情况 | 处理 |
|---|---|
| 最高 confidence ≥ 0.6 | 明确给出结论 + 建议 |
| 0.4 ≤ 最高 < 0.6 | "较可能是 X"，同时列出第二可能，给出**鉴别方法** |
| 最高 < 0.4 | **不下结论**，引导用户补充信息（如"黄叶是从下面还是上面开始？"）或转入 RAG 问答 |
| 无任何规则命中 | 转 RAG 问答，并提示"建议补充照片" |

**★ 决不允许**：在信息不足时武断给一个结论。这是"会解释为什么"这个定位的底线——**承认不确定，比假装确定更值得信任**。

## 7. 可解释性输出示例

### 示例：绿萝，客厅，近14天浇了5次（建议2次），黄叶从下部老叶开始

```
输入症状：YELLOW_LEAF
上下文： leaf_position=OLD, watering_ratio=2.5,
        pot_material=CERAMIC, season=SUMMER, light_level=MEDIUM

命中规则：
  #1  OVERWATER  w=0.95   (OLD + ratio>=1.5)
  #3  OVERWATER  w=0.40   (ANY + ratio>=2.0)
  #2  OVERWATER  w=0.30   (OLD + CERAMIC)

scores: OVERWATER = 1.65   → 归一化 confidence = 1.00
```

**返回给用户**：

> **最可能：浇水过多（置信度 100%）**
>
> **判断依据**：
> 1. 黄叶从**下部老叶**开始 —— 这是积水烂根的典型特征（缺水通常从新叶或全株开始）
> 2. 你近 14 天浇水 **5 次**，而绿萝建议约 **7 天一次**（约 2 次），**超出 2.5 倍**
> 3. 花盆是**釉面陶瓷盆**，透气性差，水分不易蒸发
>
> **建议**：
> 1. 立即停止浇水，把花盆移到通风处
> 2. 检查盆底排水孔是否堵塞
> 3. 如果土壤仍然潮湿且有异味，建议脱盆检查根系，剪除发黑腐烂的根
> 4. 恢复浇水后，改为"手指插入土中 2–3cm，干了再浇"
>
> **依据来源**：养护知识库《绿萝·浇水》

每一条依据都能对应到具体的规则和用户数据。**这就是"说得清"。**

## 8. 与病害模块的分流逻辑

```
用户提交症状 +（可选）照片
   │
   ├─ 照片存在？
   │    └─ 是 → 跑病害模型
   │         └─ top1 置信度 ≥ 0.7 且类别 ≠ Healthy
   │              └─ 是 → 【病害路径】返回病害结果 + disease_info.treatment
   │              └─ 否 → 继续
   │
   └─ 【症状路径】
        ├─ 调 diagnose(symptom_codes, context)
        ├─ 有候选 → 取 Top-3
        │     ├─ RAG 检索：该物种 × 该病因的知识片段
        │     └─ LLM 组织成自然语言（含依据 + 建议 + 来源）
        └─ 无候选 / 置信度 < 0.4
              └─ 转 RAG 问答，并引导用户补充信息
```

**注意**：`SPOT`（斑点）症状要**优先**走病害模型，因为病理性叶斑和生理性斑点虽然肉眼相似，但病斑形态（边缘、霉层、同心轮纹）是图像可分的；而黄叶是图像不可分的。

| 规则扩展 | 若某病因长期判不准，优先**加规则**而不是换模型 |

## 10. 答辩要点（这个模块能讲什么）

1. **问题定义**：为什么"黄叶"不能做图像分类 —— 一张照片对应 10 种病因，信息量不足
2. **方法选择**：规则引擎 + RAG，而非端到端模型 —— 因为要**可解释**
3. **可解释性**：每个结论都能列出命中规则和用户数据
4. **不确定性处理**：置信度 < 0.4 时不武断下结论，转而引导补充信息
5. **与病害模块的协同**：症状优先跑病害模型，高置信度则走病理路径（分流逻辑）
6. **对比实验**：纯 LLM 直接回答 vs 规则+RAG —— 前者的幻觉率与不可解释性
