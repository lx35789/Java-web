# 21 · 模型与工具选型（对应两个核心问题）

> 回答：**问题一（确认同一株）和问题二（连续节点个性化养护），分别用什么模型和工具实现。**
>
> ## 一句话结论
> **整个系统只需要 2 个真正的"模型"：物种识别（第三方 API）和文本向量（BGE-small）。**
> 其余全部是**确定性算法 + 规则引擎 + 统计**。
> 这是本项目的核心架构判断，也是答辩时的加分点——**不是模型堆得越多越好，而是每个环节用够用的东西**。

# 第一部分 · 问题一：确认是同一株植物

## 总览

| 层 | 做什么 | 用什么模型 | 用什么工具/库 | 运行位置 | 延迟目标 |
|---|---|---|---|---|---|
| **L1** 身份锚定 | 建立 `plant_id`、绑定盆标签 | **无** | MySQL + MyBatis-Plus；**ZXing**（二维码）或前端 `qrcode` | 后端 + 前端 | <10 ms |
| **L2** 观测叶锚定 | 首次点选并分割出观察叶 | **无**（默认）<br>可选 MobileSAM | **OpenCV**：ExG 阈值 + `cv2.grabCut` | AI 服务 (Python) | 200–500 ms |
| **L3a** 叶形指纹 | 判断是否同一片叶 | **无** | **`cv2.matchShapes`（Hu 七阶矩）** | AI 服务 | <5 ms |
| **L3b** 叶脉/疤痕匹配 | 精细确认（叶面疤痕是天然唯一标识） | **无** | **ORB / AKAZE + BFMatcher + RANSAC**（OpenCV 自带） | AI 服务 | 50–100 ms |
| **L3c** 背景指纹 | 同一位置长期拍摄的辅助校验 | **无** | LAB 直方图卡方距离 / **pHash**（`imagehash`） | AI 服务 | <10 ms |
| **L3d** 综合判定 | 输出 `identity_score` 与告警 | 可选：**逻辑回归**（3 个特征） | numpy / scikit-learn | AI 服务 | <1 ms |

## 为什么这些环节**不需要深度学习**

| 需求 | 直觉方案 | 实际方案 | 理由 |
|---|---|---|---|
| 分割出叶片 | SAM / U-Net / YOLOv8-Seg | **ExG 阈值 + GrabCut** | 已实测：ExG>10 能稳定分出叶片（`leaf_frac` 0.59–0.64，4102 张零失败）。SEG 模型是过度设计 |
| 判断同一片叶 | 孪生网络 / ReID 模型 | **Hu 矩 + ORB 匹配** | 叶片**固有疤痕**本身就是唯一标识，传统特征足够；且无训练数据 |
| 校验拍摄位置 | 场景识别 CNN | **背景直方图 / pHash** | 只需"像不像"，不需"是什么" |

## ⚠️ 明确不要用的（答辩防守清单）

| 技术 | 否决理由 |
|---|---|
| **ArUco / AprilTag** | 需要专用标记 + 姿态估计；我们不需要位姿，只需身份。已有文档 01 否决 |
| **SuperPoint + SuperGlue** | 重量级、依赖 GPU、训练/部署成本高；收益与"贴个标签"不匹配 |
| **植株 ReID（重识别）模型** | 开放集问题、无训练数据、误判代价高（用户会失去信任）；且**同一性本就不是图像能推断的** |
| **每株训练一个模型** | 毫无必要 |

## ✅ 值得做的一个低成本增强：**二维码盆标签**

之前否决的是 ArUco（视觉标记 + 位姿），**二维码是完全不同的东西**：

```
打印一版二维码贴纸（编号写在旁边）→ 贴在花盆上 → App 拍照识别
工具：Java 端 ZXing（Apache-2.0，成熟、毫秒级、识别率 >99%）
```

- **成本**：几毛钱打印费 + 一个成熟库
- **收益**：把"同一株"从"用户可能点错"变成"**扫码即确定**"
- **答辩说法**：*"身份识别用标准二维码，而不是视觉重识别——因为同一性是物理事实，应该用物理手段锚定"*

# 第二部分 · 问题二：连续时间节点的个性化养护

## 总览

| 环节 | 做什么 | 用什么模型 | 用什么工具/库 | 运行位置 | 延迟目标 |
|---|---|---|---|---|---|
| **① 物种识别** | 认出是什么植物 | **百度植物识别 API**（主）<br>**Pl@ntNet API**（备） | Java `RestClient` + Provider 抽象 + 降级链 | 后端→AI 服务 | P95 ≤ 3 s |
| **② 色彩分析** | 叶色指标 | **无**（确定性算法） | **OpenCV + numpy**：ExG 分割 + CIELAB `a*`/`b*` | AI 服务 | **实测 9 ms/图** |
| **③ 光源质检** | 判断本次拍摄是否可比 | **无** | OpenCV：镜面高光色度 + 滚动 MAD | AI 服务 | <10 ms |
| **④ 几何分析** | 叶片下垂/萎蔫角度 | **无**（轮廓 PCA）<br>可选自训关键点模型 | OpenCV：轮廓提取 → PCA 主轴夹角 / 叶尖曲率极值 | AI 服务 | 20–50 ms |
| **⑤ 偏差检测** | 相对本株自己的滚动基线 | **无**（统计） | **EWMA 基线 + MAD 阈值**；进阶用 **CUSUM 变点检测** | 后端 (Java) | <10 ms |
| **⑥ 归因** | 判断缺水/涝害/病害 | **规则引擎，不是模型** | 自研规则解释器 + `symptom_rule` 表（~35 条 IF-THEN + 证据打分） | 后端 | <20 ms |
| **⑦ 知识检索 (RAG)** | 给出带出处的解释 | **BGE-small-zh-v1.5**（512 维，~95 MB） | `sentence-transformers` 或 ONNX Runtime + numpy 暴力余弦 | AI 服务 | 检索 <5 ms |
| **⑧ 措辞生成** | 把结论说得像人话 | **LLM（可选）** | **DeepSeek API**；或先纯模板 | 后端 | 若用 ≤2 s |
| **⑨ 闭环参数调整** | 改浇水间隔/施肥量 | **无**（控制律） | 比例调整 `α=0.2~0.3` + 观察期锁定 | 后端 | <5 ms |
| **⑩ 排程提醒** | 到期任务 | **无** | **Spring Scheduler**（或 Quartz） | 后端 | — |

## 关键说明

### ② 色彩分析为什么不叫"模型"
它是**确定性算法**：`ExG = 2G−R−B` 分割 → CIELAB 取 `a*` → `chlorophyll = −a*`。
已实测 4102 张、9 ms/图、零失败。**没有训练、没有权重、完全可复现**——这在答辩时是优势，不是劣势。

### ④ 几何通道是**必须补的**
文档 19 的结论：颜色受光源影响极大（光源解释 **79.2%** 的表观变化）。
而**叶片下垂角度几乎不受光照影响**，对水分胁迫同样敏感。
用 OpenCV 提轮廓 → PCA 主轴 → 与水平线夹角即可，**不需要模型**。

### ⑤ 为什么用 EWMA + MAD，不用 Kalman
单变量基线的平滑，**EWMA（指数加权移动平均）足够**，且参数只有"平滑系数"一个、可解释。
Kalman 滤波是给多传感器融合用的，在这里是过度设计（文档 01 已否决）。
**MAD（中位数绝对偏差）** 代替标准差，抗异常值。

### ⑥ 归因为什么**必须**是规则引擎，不能上 ML
1. **没有标注数据**：要训一个有监督诊断模型，需要几千条"症状 → 确诊"标注，我们只有 4102 张**类别**标签（健康/涝害/病毒），没有"症状"标注。
2. **可解释性是产品卖点**：答辩必问"为什么得出涝害 62.5%"。规则引擎能逐条列出证据；ML 只能给一个数。
3. **可维护**：规则存在 `symptom_rule` 表里，加一条规则改一行数据，不用重训。
4. **不要用 Drools**：35 条规则用重型规则引擎是杀鸡用牛刀，且规则是数据驱动的。**自己写一个 200 行的解释器更灵活**。

### ⑦ RAG 是唯一必需的"小模型"
- **BGE-small-zh-v1.5**：512 维、24M 参数、~95 MB、**MIT 许可**、CPU 上 ~10–30 ms/条
- 检索：知识库 200–500 条 → **numpy 暴力余弦 <5 ms**，**不需要向量数据库**（文档 17 §1.1 已决策：不上 Redis Stack）
- 备选：`text2vec-base-chinese`（效果接近，许可需确认）

### ⑧ LLM 只做措辞，且建议**先不上**
- 架构红线：**LLM 不参与判断**，只把规则引擎的结构化结论改写成自然语言
- 建议顺序：**先纯模板跑通 → 再挂 LLM 做增强**。模板可控、可复现、零成本、零延迟
- 若要上：**DeepSeek API** 最便宜；本地可选 Qwen2.5-1.5B-Instruct（Apache-2.0，但 CPU 推理慢）

# 第四部分 · 技术栈与模块边界

## 边界划分原则
**图像处理放 Python（生态在那里），业务/规则/事务放 Java（可靠性与事务在那里）。**

```
前端 Vue 3 + Vite + Element Plus + ECharts + Pinia   （已完成，23 页面）
        │  HTTP + JWT
        ▼
后端 Spring Boot 3 + MyBatis-Plus + MySQL 8 + Caffeine + Spring Scheduler + Spring Security
        │  负责：业务、规则引擎、闭环控制、排程、持久化
        │  HTTP（内网）

AI 服务 FastAPI + OpenCV + numpy + scipy + ONNX Runtime
        │  负责：所有图像处理、embedding、第三方识别代理

外部：百度识图 / Pl@ntNet /（可选）DeepSeek
```

# 第五部分 · 答辩话术

**问：你们用了什么模型？**

> 整个系统只有两个真正的模型：**物种识别**走第三方 API（百度主 + Pl@ntNet 备），
> **知识检索**用 BGE-small 做文本向量。其余环节——叶片分割、叶色分析、
> 光源质检、叶片下垂姿态、偏差检测、症状归因、参数调整——**全部是确定性算法、
> 统计方法和规则引擎，没有一个深度学习模型**。
>
> 这是我们刻意的选择：**这个问题的瓶颈不在模型能力，而在测量可靠性**。
> 我们用 4102 张真实图像量化出来，光源差异能解释 79.2% 的表观颜色变化——
> 这种情况下堆更多模型不会让结果更准，只会让错误更难解释。
> 所以我们把力气花在**拍摄标准化、光源质检、显著性阈值**上，
> 把判断交给可逐条列证据的规则引擎，而不是一个给不出理由的黑箱。
