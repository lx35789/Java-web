# 32 · AI 养护顾问：从「继续追问」到千问个性化对话

> 2026-11-25。诊断结果页的「继续追问」以前 `router.push('/qa')`，而 `/qa` 只是重定向回诊断页，
> 后端也没有任何 `/qa` 接口 —— 点了等于没点。这次把这条链路真正打通：
> 点击 → 带上这次诊断结论 → 进入独立对话页 → 每次提问都自动读这盆植物的档案和养护记录 → 千问流式回答。

---

## 一、为什么不是「接一个聊天框」

通用大模型给的是「绿萝黄叶的 10 种原因」，用户要的是
「我这盆上礼拜浇过水、放在北阳台、健康指数刚掉了 61 分，现在到底浇不浇」。

所以每次提问前，后端都会重新拼一次**事实清单**注入系统提示词：

| 注入内容 | 来源 | 例子 |
|---|---|---|
| 昵称 / 物种 / 位置 / 光照 / 盆器 / 土 | `user_plant` + `plant_species` | 虎皮兰，阳台，明亮散射光，釉面陶瓷盆，泥炭土 |
| 当前健康状态 | `user_plant.health_status` | 健康 / 需关注 / 有病害 |
| 最近一次浇水、下次浇水日 | `care_log` / `care_task` | 11-22 17:38，下次 11-27 |
| 养护节律与上次校准说明 | `care_plan` | 浇水每 7 天；「比上次晚了 3 天，间隔调长 8%」 |
| 最近 5 条养护记录 | `care_log` | 11-20 浇水 300ml |
| 最近状态快评 + 趋势 | `plant_observation` | 健康指数 62，较上次下降 12 分 |
| 本次诊断结论 | `qa_session.diagnosis_context` | 虫害（红蜘蛛/蚧壳虫）40%，处理步骤…… |

实测（虎皮兰，档案里有一条 3 天前的浇水记录）：

> 现在不用浇，再等 5 天左右更稳妥。上次浇水是 11 月 22 日 17:38，才过去 3 天；虎皮兰在秋冬季用泥炭土 + 陶瓷盆，干得慢……

模型主动把「昵称、上次浇水时间、盆器材质、土的保水性」都引用了，而不是复述通用知识。

## 二、链路

```
诊断页「继续追问」
   │  sessionStorage['gt:ai-context'] = {plantId,title,text}   ← 结论几百字，塞 URL 会被截断
   ▼
/qa?from=diagnosis&plantId=135
   │  首次提问 → POST /qa/sessions（title + userPlantId + diagnosisContext）
   ▼
POST /qa/sessions/{id}/messages   (SSE)
   │  ① 用户消息落库  ② 拼系统提示词（上面那张表）
   │  ③ 取最近 12 条历史  ④ 调千问 stream=true
   ▼
event: meta → delta × N → done
   │  done 里带 assistantMessage（含 model / latencyMs），落库并回填列表
   ▼
前端逐字渲染 + 光标；「有用/没用」写 qa_message.feedback
```

**为什么 SSE 不用 EventSource**：EventSource 只能 GET，既带不了请求体也带不了 `Authorization`，
而提问需要 JWT。改用 `fetch` + `ReadableStream` 自己解帧（`frontend/src/api/qa.js`）。

**为什么流式**：qwen-plus 一次回答 4~8 秒，非流式体验是「转圈 6 秒突然出一大段」。

| 文件 | 作用 |

接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/qa/sessions` | 历史会话（按更新时间倒序，30 条） |
| POST | `/api/v1/qa/sessions` | 新建（`content` / `userPlantId` / `diagnosisContext`） |
| GET | `/api/v1/qa/sessions/{id}` | 会话 + 全部消息 |
| PUT | `/api/v1/qa/sessions/{id}` | 改标题 / 换植株 / 更新诊断上下文 |

| POST | `/api/v1/qa/sessions/{id}/messages` | 提问，`text/event-stream` |
| POST | `/api/v1/qa/messages/{id}/feedback` | 有用 / 没用 |

数据库改动一处（已同步 `db/schema.sql`）：

```sql
ALTER TABLE qa_session
  ADD COLUMN diagnosis_context TEXT NULL COMMENT '对话起点诊断摘要' AFTER message_count;
```

## 四、提示词约束

- 必须结合这盆植物的真实情况，禁止通用模板；能引用昵称/间隔/上次浇水
- 先一句结论，再 2~4 条可执行动作
- 中文口语、短句、不用 Markdown 标题与表格，总长 ≤ 300 字
- 信息不足先问 1~2 个关键问题，不编造；不确定要说不确定
- 药剂只给成分名（阿维菌素、吡虫啉）与安全提示，不给处方剂量
- 只聊园艺养护，超范围礼貌拒绝

历史只带最近 12 条（`HISTORY_LIMIT`），既控 token，也避免早期无关话题带偏。
系统提示词里的日期/季节按服务器当天计算，所以「秋末蒸发慢」这类判断会随季节变化。

## 五、踩坑

1. **`Map.of` 泛型推断**：`Map.of("sessionId", Long, "title", String)` 会把 V 推断成交集类型，
   编译报「String 无法转换为 capture#1」。改成 `Map.<String,Object>of(...)`。
2. **枚举值泄漏进回答**：直接把 `lightLevel` 原样塞提示词，模型会照抄 `BRIGHT_INDIRECT`。
   复用 `CarePlanService.lightLabel/potLabel`（本次改为 public），盆径、土型另加映射。
3. **MySQL 默认时间不回填实体**：`DEFAULT CURRENT_TIMESTAMP` 只在库里生效，
   insert 后实体的 `createdAt` 仍是 null，新建会话返回给前端就是空时间。显式 set。
4. **流式读超时**：`HttpRequest.timeout` 只管到响应头，正文靠逐行读，不会因为长文本被截断；
   但前端断连要能停 —— `onDelta` 抛 `UncheckedIOException` 时中断读取，避免空转烧 token。
5. **带图/带检索的旧设想**：`qa_message` 里有 `retrieved_chunks`、`citations` 字段，
   这次没做 RAG（知识库 `knowledge_chunk` 还是空的），先留字段不填。

## 六、验证记录

| 用例 | 结果 |
|---|---|
| 直接提问（有 3 天前浇水记录） | 引用「11 月 22 日 17:38」与盆器/土型，给出「再等 5 天」 |

| 消息落库 | USER/ASSISTANT 各一条，`model`/`latency_ms` 正确 |
| 枚举泄漏 | 回答中不再出现 `BRIGHT_INDIRECT` / `CERAMIC` / `PEAT` |

## 七、还没做

- **RAG 引用**：知识库分块表是空的，回答不带来源；要做得先把 `knowledge_article/chunk` 灌满
- **图片追问**：`LlmClient.chatVision` 已能用，但对话里还不能传照片（比如「你看这张新叶是不是也中招了」）
- **会话删除入口**：后端支持软删，前端只做了「新对话」
- **成本保护**：没有按用户限流，`/qa` 目前任何人都能无限问
