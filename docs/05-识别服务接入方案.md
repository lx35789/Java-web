## 1. 先纠正选型：用「植物识别」，不要用「识万物」

百度图像识别下面有两个容易混淆的产品，选错了会踩坑：

| | **植物识别**（推荐） | **看图识万物** |
|---|---|---|
| 定位 | 垂直分类模型 | 视觉专家模型 + 多模态大模型 |
| 覆盖 | 2 万+ 种植物、近 8 千种花卉 | 动植物、名人、影视、汽车、商品、文物… |
| 返回 | **植物名称 + 置信度 + 百科信息** | 一段自然语言回答 |
| 入参 | `image` / `url` / `baike_num` | `image` / `url` / **`question`（必填）** |
| 适合 | ✅ 识别的**主链路** | 辅助问答 |

**为什么不用「识万物」做主链路**：

1. **它要求传 `question`**，本质是"看图问答"，不是"分类打分"。你要的 Top-3 + 置信度，它给不了结构化结果
2. 多模态大模型推理**延迟高、成本高**，而识别是高频操作
3. 输出是自由文本，**不稳定**——今天返回"绿萝"，明天可能返回"这是绿萝，属于天南星科…"，你的前端没法稳定解析
4. 覆盖面虽广，但对"室内观叶植物精细分类"不一定比垂直模型强

> 「识万物」不是没用，它的正确位置见第 6 节。

## 2. 候选方案对比

### 2.1 横向对比

| 方案 | 覆盖 | 中文名 | Top-N | 病害 | 免费额度 | 单价 | 境内速度 |
|---|---|---|---|---|---|---|---|
| **百度植物识别** | 2 万+ 种 / 8 千花卉 | ✅ 原生 | ✅ `result` 数组 | ❌ | 新用户测试资源 | **3 元/千次** | ✅ 快 |
| **Pl@ntNet** | 5 万+ 种 | ❌ 学名为主 | ✅ 返回带 score 列表 | ⚠️ 有病害接口但覆盖窄 | **500 次/天** | 免费档够用 | ⚠️ 境外 |
| **Kindwise (plant.id)** | 多物种 | ❌ | ✅ | ✅ **自带病害识别** | **注册送 100 credits**，dev key 免费 | €0.05/次起 | ⚠️ 境外 |
| 百度看图识万物 | 极广 | ✅ | ❌ 自由文本 | ❌ | — | 按大模型计费 | ✅ 快 |
| 自研 MobileNetV3 | 47 类 | 需自己映射 | ✅ | ❌ | — | 训练成本 | ✅ 本地 |

### 2.2 逐项点评

**百度植物识别 —— 最省事的选择**

- 2 万+ 种植物、近 8 千种花卉，**返回植物名称和置信度信息**，还支持获取识别结果的百科信息（词条 URL、图片、描述）[cite:d0952163-2]
- 定价 **3 元/千次**（月调用 ≤5 万次档），量大递减 [cite:d0952163-1]
- **返回中文名**——这对你太重要了。Pl@ntNet 返回的是学名，你还得自己建映射表转成"绿萝"
- 境内访问快，不用考虑跨境网络

**Pl@ntNet —— 免费额度最友好**

- **500 次/天免费**，对 Demo 和同学试用绰绰有余 [cite:a23e8b37-3]
- 5 万+ 可识别物种，国际化程度高
- 缺点：返回学名为主，且服务器在境外，延迟不稳定；免费版要求展示 "powered by Pl@ntNet"

**Kindwise (plant.id) —— ★ 功能最全**

- 注册送 **100 free credits**，dev key 免费使用，正式价 €0.05/次起 [cite:c0d61adf-3]
- **★ 它同时提供物种识别和病害识别/虫害识别**

### 2.3 ★ 一个可能改变你排期的发现

回顾第一轮评审的结论：**你项目最大的技术风险是病害识别没有数据**——PlantVillage 里一种室内观叶植物都没有，我们最后换成了室内病害数据集，但那个数据集只覆盖绿萝、虎皮兰、芦荟、吊兰、多肉。

**如果接 Kindwise，病害模块立刻可用**，不用等数据集下载、清洗、训练。

| | 自研病害模型 | Kindwise 病害 API |
|---|---|---|
| 启动成本 | 下载 21,097 张图 + 训练 + 调参 | 注册 + 20 行代码 |
| 工期 | 约 1.5 周（Phase 4） | 半天 |
| 覆盖物种 | 5 种 | 更广 |
| 效果 | macro-F1 目标 ≥70% | 商业级 |
| 代价 | 无 | 100 credits 用完后 €0.05/次 |

**建议**：Demo 和中期检查用 Kindwise 顶上，自研模型按原计划并行推进。这样 Phase 4 不再是关键路径。

> 注意：这不改变"症状诊断"模块的价值。生理性症状（黄叶/焦边/落叶）**任何一家 API 都做不了**，仍然必须靠你的规则引擎——那才是真正的自研部分。

## 3. 推荐架构：Provider 抽象 + 降级链

**核心原则：不要让业务代码知道用的是哪家 API。**

第一轮设计里 `recognition_record.provider` 字段已经预留了，现在把它用起来。

### 3.1 后端接口设计（Java）

```java
/**
 * 物种识别供应商统一接口
 * 所有实现返回归一化后的 RecognitionResult，业务层不感知具体厂商
 */
public interface PlantRecognitionProvider {

    /** 供应商标识，写入 recognition_record.provider */
    String name();

    /** 优先级，数字越小越先尝试 */
    int order();

    /** 当前是否可用（配额耗尽 / 熔断中 返回 false） */
    boolean available();

    /**
     * @param imageBytes 已做 EXIF 矫正与压缩的 JPEG 字节
     * @return Top-N 结果，已按置信度降序
     */
    List<RecognitionCandidate> recognize(byte[] imageBytes, int topN);
}

public record RecognitionCandidate(
    String rawName,        // 供应商原始名称，如 "绿萝" 或 "Epipremnum aureum"
    String scientificName, // 学名，可能为 null
    double confidence,
    String imageUrl,       // 百科缩略图，可能为 null
    String description     // 百科描述，可能为 null
) {}
```

### 3.2 适配器实现

```
PlantRecognitionProvider
├── BaiduPlantProvider      百度植物识别（主）
├── PlantNetProvider        Pl@ntNet（备）
├── SelfModelProvider       自研 ONNX 模型（兜底 / 对比实验用）
└── KindwiseProvider        plant.id（可选）
```

### 3.3 降级链（编排器）

```java
@Service
public class RecognitionOrchestrator {

    private final List<PlantRecognitionProvider> providers; // 按 order 排序

    public RecognitionResponse recognize(byte[] image, int topN) {
        for (PlantRecognitionProvider p : providers) {
            if (!p.available()) continue;
            try {
                List<RecognitionCandidate> list = p.recognize(image, topN);
                if (list.isEmpty()) continue;

                // 置信度太低 → 继续尝试下一家，并合并结果
                if (list.get(0).confidence() < MERGE_THRESHOLD) {
                    List<RecognitionCandidate> merged = mergeWithNext(image, topN, list, p);
                    if (!merged.isEmpty()) return build(merged, p.name() + "+fallback");
                }
                return build(list, p.name());

            } catch (Exception e) {
                log.warn("识别供应商 {} 失败，降级", p.name(), e);
                // 失败不计费，继续下一家
            }
        }
        throw new BizException(3002, "识别服务暂时不可用");
    }
}
```

**降级链建议顺序**：`百度(1) → Pl@ntNet(2) → 自研模型(3)`

理由：
- 百度最快、中文名直接可用、有百科
- Pl@ntNet 免费额度兜底，不花钱
- 自研模型放最后：它的作用是**保底可用**（比如断网、配额全耗尽时仍能演示），以及作为论文的对比 baseline

### 3.4 结果归一化（关键一步）

各家返回的物种名不一样，必须映射到你的 `plant_species` 表：

```
百度      → "绿萝"            → 直接匹配 plant_species.common_name
Pl@ntNet → "Epipremnum aureum" → 匹配 scientific_name，或别名表
自研模型  → classIndex 33      → 匹配 model_class_index
```

**匹配不上怎么办**：不要丢弃。`recognition_result.raw_name` 字段就是为此预留的 —— 照常展示"识别到：XX（不在你的植物库中）"，并提示用户手动选择。硬塞进 50 种里才是错的。

## 4. 接百度的具体工程问题

这些是文档里不显眼但一定会踩的点：

| # | 问题 | 处理 |
|---|---|---|
| 1 | **access_token 有效期 30 天**，且获取接口有频次限制 | 用 Redis 缓存 token，过期前 1 小时自动刷新；**不要每次识别都去换 token** |
| 2 | 图片需 **base64 编码 + urlencode**，编码后 ≤ **4M** | 前端上传时就压到长边 1024 / JPEG q80，既省流量又稳过限制 [cite:c81ce372-2] |
| 3 | 边长要求 **最短 15px，最长 4096px** | 用户可能传超大头像图，服务端要校验并拒绝/压缩 |
| 4 | **QPS 限制 10** | 加 Redis 令牌桶；批量场景（比如导入历史照片）要排队 |
| 5 | `Content-Type` 必须是 `application/x-www-form-urlencoded` | 不是 JSON，别搞错 |
| 6 | 要拿百科信息必须显式传 **`baike_num`** | 不传就不返回，默认 0 |
| 7 | **中文名做映射** | 百度也可能返回"绿萝（黄金葛）"这类带括号的，映射前要清洗 |
| 8 | **调用失败不计费** | 但这意味着失败要重试/降级，否则用户拿到空结果 |

### 请求示例（可直接对照实现）

```
POST https://aip.baidubce.com/rest/2.0/image-classify/v1/plant?access_token={token}
Content-Type: application/x-www-form-urlencoded

image={base64后urlencode的图片}&baike_num=1
```

## 5. 成本估算

按百度 **3 元/千次** 计算：

| 场景 | 调用量 | 成本 |
|---|---|---|
| 开发调试一周 | ~500 次 | **1.5 元** |
| 答辩演示 | ~100 次 | **0.3 元** |
| 50 名同学试用一个月（人均 20 次） | ~1000 次 | **3 元** |

**结论：整个项目周期内，识别费用不会超过一杯奶茶钱。**

> 百度新用户通常还有免费测试资源（需实名认证），先去控制台领，可能连这 3 元都不用花。

**必做**：Redis 缓存识别结果（相同图片 hash → 相同结果），既省钱又快，还能防重复点击。

## 6. 一个容易被忽略的机会：百科信息

百度植物识别可以返回 `baike_info`，包含：

- `baike_url` 百科词条链接
- `image_url` 百科配图
- `description` 百科内容描述

**这有三个用途**：

1. **识别结果卡片直接展示** —— 用户看到"绿萝"+ 配图 + 一段介绍，体验立刻完整，而且这是 API 的**预期用途**，合规无风险
2. **给 RAG 提供兜底语料** —— 当你的自撰养护卡片没覆盖某个物种时，可以用百科描述做补充
3. **配合「识万物」的 `question` 参数**做轻量问答

> ⚠️ **但第 2 条要谨慎**：通过 API 返回的内容，其使用受百度 API 服务条款约束。作为**识别结果的展示**是正常用途；**批量抓取入库当作 RAG 语料库**可能超出授权范围。
>
> 建议：展示直接用；若要入库，先读服务条款，或只存 `baike_url` 做跳转而不复制内容。**第一轮评审里 RHS / Gardening Know How 的版权问题，在这里同样适用。**

## 7. ★ 重新分配 AI 工作量（本方案最重要的一节）

这是你必须先想清楚的问题：**既然识别可以用 API，那这个项目的"AI"还剩下什么？**

### 7.1 先回到第一轮评审的结论

> 核心价值主张是「**会解释为什么的养护助手**」，不是「识别得准」。

原因很直接：识别准确率的天花板由数据和模型规模决定，**自研模型必然打不过商业 API**。把项目价值押在识别准确率上，等于选了一个必输的赛道。

**所以用 API 不是偷懒，而是把精力从"重复造轮子"转移到"真正有差异的地方"。**

### 7.2 三种定位，对应三种做法

| 项目性质 | 识别怎么做 | 理由 |
|---|---|---|
| **A. 就是要快速出 Demo / 中期检查** | 全用百度 API | 半天接入，效果最好，把时间留给别的模块 |
| **B. 毕业设计，必须有自研模型** | 自研模型做**主体**，API 做**兜底 + 对比 baseline** | 工作量体现在训练、调参、评估、对比分析上，API 保证演示不翻车 |
| **C. 想做出真正的产品** | API 做识别，自研精力投在症状诊断 + RAG | 识别是红海，诊断和知识才是差异化 |

> 如果你属于 B（大多数毕设都是），**正确姿势不是二选一**：
> 自研模型证明"我能做"，API 保证"它好用"，并做一组对比实验。

### 7.3 ★ 一个真正有价值的创新点

无论你用哪家 API，**用户的纠正数据都是你的独家资产**。

`recognition_record.confirmed` + 纠正后的 `species_id` 已经在表里了。基于它可以写：

> **《主流植物识别 API 在室内观叶植物细分场景下的真实表现评估》**
>
> 用 300–500 条真实用户上传的室内绿植照片（含用户纠正作为 ground truth），
> 横向对比百度 / Pl@ntNet / 自研模型的 Top-1、Top-3 准确率，并分析各自的失效模式。

**为什么这个有分量**：
- 公开数据集（Kaggle House Plant Species 是 Bing 爬取、非专业标注）测不出真实场景表现
- 各家的官方 benchmark 都是通用场景，**没有人做过"室内盆栽 + 手机随手拍"这个细分场景的评测**
- 这是你独有的数据，别人复制不了
- 而且它天然回答了答辩最可能被问的问题："你为什么用 API？你自己做了什么？"

这比单纯"我训了一个 MobileNetV3，准确率 82%"有价值得多。

### 7.4 工作量重新分配后的样子

| 模块 | 用 API 后 | 自研投入 |
|---|---|---|
| 物种识别 | 百度为主 | 保留自研模型做对比实验，**不追求 SOTA** |
| 病害识别 | Kindwise 顶上 | 自研模型降级为可选 |
| **症状诊断** | ❌ API 做不了 | ★ **全部自研**（规则引擎 + 35 条规则） |
| **RAG 问答** | ❌ API 做不了 | ★ **全部自研**（语料 + 检索 + 评测集） |
| **个性化养护计划** | ❌ API 做不了 | ★ **全部自研**（规则引擎 + 系数体系） |
| **API 横向评测** | — | ★ **新的创新点** |

**五个模块里三个 API 完全做不了，这才是你的项目主体。**

## 9. 落地步骤（建议顺序）

```
第 1 天   注册百度智能云 → 实名 → 创建图像识别应用 → 拿 API Key / Secret Key
          领免费测试资源，先用在线调试工具试几张自己的照片

第 2 天   后端实现 PlantRecognitionProvider 接口 + BaiduPlantProvider
          access_token 用 Redis 缓存 + 自动刷新
          跑通"上传 → 百度识别 → 归一化 → Top-3 返回"

第 3 天   接入 Pl@ntNet 作为降级；实现 RecognitionOrchestrator 降级链
          Redis 结果缓存（按图片 hash）

第 4 天   物种名 → plant_species 映射（含别名、学名、清洗括号）
          映射不上的走 raw_name 展示，不硬塞

第 5 天   注册 Kindwise，试用病害识别，评估是否用它替代 Phase 4
```

**整个过程前端零改动**——因为 `api/recognition.js` 和 `provider` 字段早就隔离好了。
