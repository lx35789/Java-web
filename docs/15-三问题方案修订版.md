# 问题 1：怎么确认是同一株植物

## 问题本质（保持）

用户手持拍照，角度、光照、叶片位置均无法保证一致，无法做单叶级像素追踪。
但系统需要知道"这是同一盆植物"，才能对比两次观测。

## ★ 修订说明

原方案提了**三层递进对齐**。逐层复核后：**第一、二层必须砍掉，第三层换个更轻的实现。**

### ❌ 砍掉第一层：花盆贴 ArUco / 二维码

**理由：用户不会为了养一盆绿萝去打印贴纸贴花盆。**

这与整个产品的核心设计冲突——我们花了大量精力论证"记录成本要趋近于零"，
而这个方案把成本直接拉满。**产品上不可行。**

### ❌ 砍掉第二层：SuperPoint + SuperGlue 整株配准

**三个问题，一个比一个致命：**

| # | 问题 | 说明 |
|---|---|---|
| 1 | **前提不成立** | SuperPoint/SuperGlue 是为**刚体场景**设计的（SLAM、三维重建），假设两个视角看到的是**同一个不变的物体**。但植物是**非刚体，而且正在变化**——**变化恰恰是我们要测量的东西**。用它对齐再测变化，逻辑上自相矛盾 |
| 2 | **场景不匹配** | 它依赖显著特征点。室内盆栽的背景是白墙、桌面、纯色窗帘——**特征点又少又重复**，匹配可靠性很低。文献里验证有效的场景是**田间植株**，有土壤、杂草、自然纹理 |
| 3 | **收益存疑** | 我们的指标是「**黄叶占植株的比例**」——**这是相对量，角度变化影响有限**。真正需要的是**拍摄一致性**，不是算法对齐 |

> 原方案引用"在农业机器人场景中已被验证有效"——**这是真实的，但场景不同**。
> 田间有丰富纹理，室内没有。**不能直接外推。**

### 🔻 第三层保留，但换实现

原方案用 **YOLOv8-Seg 分割**。问题：

- **家庭盆栽没有分割标注数据集**（原文引用的 0.9064/0.7233 是某个**特定叶片分割任务**的数字，不能外推）
- 从零标注 + 训练 = **2–3 周**

**改用 HSV 阈值 + 掩码并集**：

```
前景（植株区域）= 绿色掩码 ∪ 黄色掩码 ∪ 褐色掩码
```

白墙、桌面等背景因为**不落在任何颜色区间**而自动被排除，**根本不需要分割模型**。

| | YOLOv8-Seg | HSV 阈值 |
|---|---|---|
| 工期 | 2–3 周 | **1 天** |
| 需要标注数据 | ✅ 需要（且没有） | ❌ 不需要 |
| 效果 | 好 | **对趋势判断足够** |

### ★ 新增：用「标准化拍摄」替代「算法对齐」

```
固定角度  → 盆边贴标记，每次从同一方向拍
固定光照  → 统一在上午某时段（自然光稳定）
固定背景  → 白墙或纯色，避免杂物
加参照物  → 放一张固定大小的卡片
APP 辅助  → 拍照时叠加半透明轮廓线，提示对齐
```

**做不到标准化就退一步：只做纵向自比较（同一盆的照片互比），不做横向比较。**

## 修订后的解决方案

```
第一层（替代原第一、二层）
  「标准化拍摄引导」+ 植物 ID 由系统分配，不依赖图像识别身份

第二层（原第三层，换实现）
  HSV 阈值颜色统计，在"三色掩码并集"区域内算占比：
    · green_ratio  → 健康叶占比
    · yellow_ratio → 黄叶率
    · brown_ratio  → 褐斑/枯焦率
  合成 → health_index (0–100)

第三层（新增，原方案没有）
  多指标联合判别：
    · 黄叶占比变化趋势
    · 健康指数曲线斜率
    · 单指标饱和时的交叉验证
```

| 工具 | 用途 | 状态 |
|---|---|---|
| **OpenCV**（HSV 阈值、像素统计） | 颜色指标提取 | ✅ **已实现**：`experiments/common/color_metrics.py` |
| ~~ArUco / 二维码~~ | ~~花盆锚定~~ | ❌ **移除**：产品上不可行 |
| ~~SuperPoint + SuperGlue~~ | ~~图像配准~~ | ❌ **移除**：刚体假设不成立 |
| ~~YOLOv8-Segment~~ | ~~植株分割~~ | ❌ **移除**：无标注数据，工期不可承受 |
| ~~SAM / SAM2~~ | ~~零样本分割~~ | ❌ **移除**：性能与工期不匹配 |
| Node.js（自测） | 算法逻辑交叉验证 | ✅ **已跑通**：`_selftest.js` 22/22 通过 |

# 问题 2：怎么实现连续时间节点的个性化养护

## 问题本质（保持）

用户不会每天上传照片，但系统需要给出连续时间节点的养护建议，
且要能自动判别"从上次到这次实际发生了什么变化"。

## ★ 修订说明

**原方案最有价值的部分就是「三条铁律」，全部保留。**
需要改的只有一处工具选型。

### ✅ 保留：三条铁律（原文精华）

| # | 铁律 | 评价 |
|---|---|---|
| 1 | **判别靠观测对** | ✅ 正确。没有两次观测就没有"变化" |
| 2 | **预测限 2 天** | ✅ 合理。限制外推，避免越猜越离谱 |
| 3 | **超期不硬猜** | ✅✅ **非常好**，与产品的"承认不确定"完全一致 |

### ✅ 保留：判别逻辑（原文扎实）

- 变化量判别：Δ黄叶率 = 今天 − 上次
- 变化速率判别：速率 = Δ / 间隔天数
- 阶段转移判别：状态机（健康→亚健康→轻症→中症→重症，双向）
- 归因判别：结合两次观测间的环境数据与用户操作

### ❌ 砍掉：卡尔曼滤波

**前提不满足，三个都不满足：**

| 卡尔曼滤波要求 | 实际情况 |
|---|---|
| 线性高斯系统 | 植物状态变化是**非线性**的（黄化会加速、会突变） |
| **规则观测间隔** | 用户上传照片**间隔完全不规则**（今天明天后天，或隔两周） |
| 已知状态转移模型 | 写不出"昨天 82 → 今天多少"的转移矩阵 |

> **典型的"用了高级工具但前提不成立"。**
> 答辩时被问一句——「你的状态转移矩阵和观测矩阵怎么定的？」——就下不来台。

### ✅ 替代：规则外推 + 阈值触发

```
预测（限 2 天）不用卡尔曼滤波，用：
  · 土壤湿度衰减模型（基于上次浇水时间 + 环境温湿度）
  · 规则触发：湿度预估 < 阈值 → 提醒"明天检查是否需要浇水"
  · ★ 只输出提醒，不输出精确数字（原文这点是对的，保持）
```

### ⏸️ 移入「未来工作」：LSTM / TCN

原文说"数据积累后升级"——**这个判断是对的**，但 16 周内不会积累到那个量。
放进论文的"展望"章节正合适。

### ⚠️ 统一天气 API

原文用**和风天气**（需注册 key）。我们设计里已定 **Open-Meteo**（**免费、无需密钥**）。
**统一用 Open-Meteo**，避免两套代码。

### ★ 新增（原方案缺的重要一环）：自适应调整

原文只讲"判别"和"预测"，**没讲系统怎么根据判别结果调整养护计划**。

补上闭环：

```
生成计划 → 提醒 → 用户执行 → 观测状态 → 评估效果 → 调整计划
                                        ↑
                                  ★ 原方案缺这一段
```

调整逻辑（已写入 `13-状态追踪与个性化验证.md`）：

```java
// 状态持续下滑 且 浇水频率偏低 → 间隔太长
if (slope < -5 && waterRatio < 1.0)  next = current * 0.85;
// 状态持续下滑 但 浇水频率已偏高 → 间隔太短
if (slope < -5 && waterRatio > 1.8)  next = current * 1.15;
// 状态稳定向好 → 保持
```

**★ 并且调整也必须可解释**（与产品核心定位一致）：

```
你的养护计划已自动调整
  浇水间隔：5 天 → 4 天
  为什么调整？
   · 最近 3 次观测显示健康指数从 82 降到 64
   · 这 14 天你实际浇了 2 次，低于建议的 3 次
   · 综合判断：水分不足，间隔偏长
  [保持原计划]  [采纳新计划]
```

# 问题 3：识别病症和连续性跟踪养护的数据怎么来

## 问题本质（保持）

网络没有现成的"同一植株昨天今天成对"数据，用户上传不可控，自己养殖没时间。

## ★ 修订说明

**这是原方案问题最多的一节。** 逐个核实后：

| 原文数据来源 | 核实结果 | 处理 |
|---|---|---|
| **PlantVillage** | ⚠️ 真实，但 **54,306 张 / 14 种作物全都是农作物**（苹果、番茄、马铃薯…），**没有一种室内观叶植物** | ❌ **移除** |
| Wheat Leaf Disease | ✅ **真实存在**（Nature Scientific Data），但内容是**小麦田间**病害时序 | ⚠️ 降级为"概念参考" |
| **PowderyMildew（epifitter 内置）** | ❌ **描述错误**。epifitter 是**生成合成曲线**的工具，官方原文：*"creates synthetic disease progress curves… **They are not a substitute for biological validation**"* | ❌ **移除** |
| GrowliFlower | ✅ **真实存在**（波恩大学），但是**田间花椰菜 + 多光谱 + 机器人拍摄** | ⚠️ 降级为"概念参考" |
| 苹果火疫病纵向数据 | **高光谱**（可见光-近红外） | ❌ **移除**：手机相机拍不出高光谱 |
| 松材线虫病监测数据 | **高光谱** | ❌ **移除**：同上 |
| **智能灌溉环境传感器数据集** | ✅ 20 天 / 30 分钟 / 960 条环境时序 | ✅ **保留**（最接近家庭场景） |
| 园艺规则库 | 可行，但**不能照搬 RHS**（版权） | ✅ 保留，改为**自撰** |
| 合成数据 | ✅ 可行 | ✅ **保留且已实现** |

### ★ 关于 PlantVillage 必须说清楚

**原文写"在域内准确率可达 99% 以上"——这句话本身没错，但它是个著名的陷阱：**

> PlantVillage 是**实验室条件下、单片叶子、统一背景**拍摄的。
> 模型在这个集上能到 99%，但换成**手机拍整株、家里复杂光线**，性能会**断崖式下降**。
> 这是文献里被反复讨论的 generalization gap。
>
> **用它报 99%，答辩时被问「那你在真实照片上测过吗」就崩了。**
