# 08 · 诊断流程详解

> 回答一个问题：**用户说「叶子黄了」，系统到底是怎么一步步得出结论的？**
> 配套：`03-症状诊断规则库.md`（规则表）、`04-API接口设计.md` 第 7 节

---

## 0. 先用一句话说清楚（汇报直接可用）

### 15 秒版

> 用户说「叶子黄了」，系统**不会直接猜**。它先问一个关键问题——「黄叶是从下面的老叶开始，还是上面的新叶？」然后自动去查这盆植物最近的浇水记录、光照、花盆材质、空气湿度，**把能排除的原因一个个排除掉**，最后剩下的就是最可能的原因，**并且把排除的过程一条条列给用户看**。

### 30 秒版（带类比）

> 这个过程很像**医生问诊**。
>
> 只看到你咳嗽，医生不会直接开药——他会问「咳多久了」「有没有痰」「发烧吗」，再让你去验个血。**信息够了才下结论。**
>
> 我们做的是同一件事。**照片只能告诉我们"叶子黄了"，但"为什么黄"必须靠问诊。** 所以我们问「黄叶从哪开始」，再自动查「最近浇了几次水」「放哪儿」「什么盆」，把 10 种可能收缩到 2 种，最后给出结论和依据。

## 1. 全景数据流

先看整体，再拆细节：

```
【用户侧】
  上传照片（可选）  +  勾选症状  +  回答"黄叶从哪开始"
        │
        ▼
【后端：自动采集上下文】 ← ★ 关键：用户不用填这些
   ├── 从 care_log 算：近14天浇了几次水  → watering_ratio
   ├── 从 user_plant 读：光照、花盆材质、摆放位置
   ├── 从 user_environment 读：有没有空调
   ├── 从天气 API 读：当前温度、空气湿度
   └── 从日期算：当前季节
        │
        ▼
【规则引擎：判因】 ← ★ 核心，全部可解释
   ① 取出该症状下所有启用的规则
   ② 逐条检查条件是否满足（多条件为"且"）
   ③ 命中的规则，按病因累加权重
   ④ 归一化成置信度
   ⑤ 丢弃太弱的，取前 3
        │
        ▼
【置信度分档】← ★ 决定"给结论"还是"继续问"
   ≥ 0.6  → 明确给结论
   0.4–0.6 → 说"较可能"，并列出第二可能和鉴别方法
   < 0.4  → 不下结论，引导用户补充信息
        │
        ▼
【RAG 检索 + 大模型润色】
   知识库找依据 → 大模型把结论说成人话（★ 不参与判断）
        │
        ▼
【展示 + 落库】
   病因 + 置信度 + 判断依据 + 该怎么做 + 来源标注
```

## 2. 完整流程：13 个步骤

### 阶段 A：收集信息

| 步 | 做什么 | 数据从哪来 | 产出 |
|---|---|---|---|
| **1** | 用户上传照片（**可选**） | 手机 | 图片文件 |
| **2** | 识别植物种类 | 百度 / Pl@ntNet API | 绿萝（置信度 0.87） |
| **3** | 跑病害识别（**可选**） | 病害模型 / API | 有没有病理性病害 |
| **4** | 用户勾选症状 | 界面多选 | `["YELLOW_LEAF"]` |
| **5** | **系统追问关键问题** | 界面必选 | `leaf_position = "OLD"` ← ★ 最关键的一项 |

> **第 5 步是整个流程的灵魂。**
>
> 「黄叶从老叶还是新叶开始」这一项，就能把候选病因从 10 种收缩到 2–3 种。
> 所以我们在界面上把它做成**必选项**——不选不让提交。

### 阶段 B：自动补齐上下文（用户完全无感）

| 步 | 采集什么 | 从哪张表 / 哪里算 | 结果 |
|---|---|---|---|
| **6** | 近 14 天浇水次数 | 数 `care_log` 里 `log_type='WATER'` 的记录 | 5 次 |
| | 这 14 天"应该"浇几次 | `14 ÷ 养护计划的间隔天数` | 14 ÷ 5 = 2.8 次 |
| | **浇水频率比** | 实际 ÷ 应该 | **1.79**（浇多了） |
| **7** | 光照条件 | `user_plant.light_level` | MEDIUM |
| **8** | 花盆材质 | `user_plant.pot_material` | CERAMIC（釉面陶瓷） |
| **9** | 温度和湿度 | 天气 API（按用户城市） | 31.5°C / 28% |
| **10** | 当前季节 | 系统日期 | SUMMER |
| **11** | 最近施肥情况 | 数 `care_log` 里 `log_type='FERTILIZE'` | 30 天内无 → NONE |

> **★ 这一步是"个性化"的来源。**
>
> 两个用户拍同一张黄叶照片、选同一个症状，**如果一个是陶盆、一个是釉面陶瓷盆，浇水频率不同，结论可能完全不一样。**
>
> 通用识别 API 永远给不了这个——因为它不知道这些数据。

### 阶段 C：判因计算（核心）

| 步 | 做什么 | 说明 |
|---|---|---|
| **12** | 规则匹配 + 权重累加 + 归一化 | 见第 3 节完整算例 |
| **13** | 置信度分档 → 输出 | 决定给结论 / 引导补充 |

## 3. ★ 完整算例：跟着一个真实案例走一遍

### 案例背景

> **小绿**（绿萝），摆在客厅，**釉面陶瓷盆**，家里**开空调**
> 用户说：**「叶子黄了」**，并选择：**黄叶从下部老叶开始**

### 第 1 步：系统自动采集到的上下文

```
leaf_position  = OLD          用户回答
watering_ratio = 1.79         近14天浇5次，建议2.8次 → 5 ÷ 2.8
pot_material   = CERAMIC      植物档案
light_level    = MEDIUM       植物档案
humidity       = 28           天气API
temp           = 31.5         天气API
season         = SUMMER       系统日期
fertilizing    = NONE         养护日志
vein_pattern   = NONE         用户未提供
cause_hint     = null         用户未提供
```

### 第 2 步：取出「叶片发黄」的 13 条规则，逐条检查

规则表在 `symptom_rule` 表里，查 `symptom_code = 'YELLOW_LEAF' AND enabled = 1`：

| 规则 | 病因 | 触发条件 | 权重 | 是否命中 | 为什么 |
|---|---|---|---|---|---|
| #1 | 浇水过多 | 老叶 **且** 浇水≥1.5倍 | 0.95 | ✅ | OLD ✓，1.79 ≥ 1.5 ✓ |
| #2 | 浇水过多 | 老叶 **且** 釉面陶瓷盆 | 0.30 | ✅ | OLD ✓，CERAMIC ✓ |
| #3 | 浇水过多 | 浇水≥2.0倍 | 0.40 | ❌ | 1.79 < 2.0 |
| #4 | 光照不足 | **新叶** 且 弱光 | 0.85 | ❌ | 不是新叶 |
| #5 | 光照不足 | 全株均匀黄 且 弱光 | 0.60 | ❌ | 不是全株均匀 |
| #6 | 缺肥 | 叶脉绿**且**从未施肥 | 0.80 | ❌ | 用户没说叶脉情况 |
| #7 | 肥害 | 新叶 且 近期施过肥 | 0.75 | ❌ | 不是新叶 |
| #8 | 空气干燥 | 湿度 < 30% | 0.55 | ✅ | 28% < 30% ✓ |
| #9 | 正常代谢 | 老叶 且 **秋季** 且 浇水<1.2倍 | 0.55 | ❌ | 现在是夏天 |
| #10 | 正常代谢 | 老叶 且 浇水<1.0倍 | 0.35 | ❌ | 1.79 > 1.0 |
| #11 | 低温冻伤 | 温度 < 10°C | 0.70 | ❌ | 31.5°C |
| #12 | 虫害 | 任意 | 0.20 | ✅ | 无条件，总是命中 |
| #13 | 水质问题 | 用户提示用过自来水 | 0.25 | ❌ | 未提供 |

**13 条规则命中 4 条。**

### 第 3 步：按病因累加权重

```
浇水过多   = 0.95 + 0.30          = 1.25   ← 两条规则都指向它
空气干燥   = 0.55                 = 0.55
虫害       = 0.20                 = 0.20
                                     ─────
总计                                   2.00
```

### 第 4 步：归一化成置信度

```
浇水过多   = 1.25 ÷ 2.00 = 62.5%
空气干燥   = 0.55 ÷ 2.00 = 27.5%
虫害       = 0.20 ÷ 2.00 = 10.0%
```

### 第 5 步：丢弃太弱的，取前 3

> **规则：置信度低于 15% 的直接丢弃**，因为它多半是"无条件规则"带来的噪声。

```
虫害 10.0% < 15%  → 丢弃
```

**最终结果：**

| 排序 | 病因 | 置信度 | 依据 |
|---|---|---|---|
| 1 | **浇水过多 / 烂根** | **62.5%** | 命中了规则 #1、#2 |
| 2 | 空气过于干燥 | 27.5% | 命中了规则 #8 |

### 第 6 步：置信度分档

62.5% ≥ 60% → **属于"明确"档，直接给结论。**

> 如果算出来最高只有 35%，系统**不会下结论**，而是说：
> 「目前信息还不足以判断原因，麻烦补充这几点：黄叶是从老叶还是新叶开始？最近两周浇了几次水？」

## 4. ★ 用户最终看到什么（这才是重点）

前面算出来的东西，对用户来说是一堆数字。**我们怎么把它变成人话？**

### 系统实际返回的内容

```
┌─ 最可能：浇水过多 / 烂根        置信度 62.5%   [尽快处理] ─┐
│                                                            │
│  📋 判断依据                                                │
│   · 黄叶从下部老叶开始，且你近 14 天浇水 5 次，              │
│     是建议值（约 2.8 次）的 1.8 倍 —— 积水导致根系缺氧        │
│   · 釉面陶瓷盆透气性差，水分不易蒸发                        │
│                                                            │
│  🩹 建议这样做                                              │
│   1. 立即停止浇水，把花盆移到通风处                          │
│   2. 检查盆底排水孔是否堵塞                                 │
│   3. 如果土壤仍然潮湿且有异味，建议脱盆检查根系              │
│   4. 恢复浇水后改为「手指插入土中 2–3cm，干了再浇」          │
│                                                            │
│  命中规则 #1、#2                                            │
└────────────────────────────────────────────────────────────┘

┌─ 次可能：空气过于干燥          置信度 27.5%   [不急] ──────┐
│  📋 判断依据                                                │
│   · 空调房内湿度约 28%，低于 30%，蒸腾过强会加重叶色变差      │
│                                                            │
│  🩹 建议这样做                                              │
│   1. 在花盆附近放一盆水，或用加湿器                          │
│   2. 避免放在空调出风口正对的位置                            │
│                                                            │
│  命中规则 #8                                                │
└────────────────────────────────────────────────────────────┘

💡 综合建议：综合来看，最可能是浇水过多导致根系缺氧。空气干燥
   会加重这个问题。建议先停水观察 5–7 天，同时改善一下湿度。

📎 依据来源：《绿萝·浇水与积水判断》《花盆材质对水分蒸发的影响》
```

### ★ 可解释性是怎么产生的

关键在**每条规则都自带一句"解释模板"**：

| 规则 | 解释模板（存在数据库里） | 实际渲染出来 |
|---|---|---|
| #1 | 黄叶从下部老叶开始，且你近 14 天浇水次数是建议值的 **{ratio}** 倍——积水导致根系缺氧 | …浇水次数是建议值的 **1.8** 倍… |
| #2 | 釉面陶瓷盆透气性差，水分不易蒸发 | （原样） |
| #8 | 空气湿度低于 30%，蒸腾过强导致叶色变差 | （原样） |

**模板里的 `{ratio}` 会被真实数据替换掉。**

所以用户看到的不是"系统觉得你浇多了"，而是**"系统发现你浇了 5 次，而建议是 2.8 次"**——这是事实陈述，不是主观判断。

**这就是"说得清"的落地。**

|---|---|---|---|

| 叶脉特征 | 用户回答 | 可选 | 每次 |
| 植物种类 | 拍照识别 | 自动 | 一次 |
| 光照条件 | 植物档案 | 一次 | 很少变 |
| 花盆材质 | 植物档案 | 一次 | 很少变 |
| 摆放位置 | 植物档案 | 一次 | 很少变 |
| 浇水频率 | **养护日志统计** | 手填或点"已完成"自动生成 | 每次浇水 |

## 6. 为什么不用大模型直接判断？

这是最可能被问的问题，把答案记牢：

### 如果让大模型直接看图判断

```
用户：上传一张黄叶照片
大模型：叶子黄了，应该是浇水过多。
用户：为什么？
大模型：因为叶子发黄通常是因为浇水过多。
```

**问题在哪：**

| 问题 | 具体表现 |
|---|---|
| **信息量不够** | 同一张黄叶照片对应 10 种可能，照片本身**看不出**是浇多了还是浇少了 |
| **不可解释** | 问它"为什么"，它只能重复结论 |
| **不可调试** | 判断错了，你不知道该改哪里 |
| **不可测试** | 没法写单元测试验证它对不对 |
| **有幻觉风险** | 可能编出一个听起来合理但错误的解释 |

### 我们的做法

| 环节 | 谁负责 | 为什么 |
|---|---|---|
| **问什么** | 产品设计 | 只问最有区分度的问题（从老叶还是新叶） |
| **判断** | **规则引擎** | 可解释、可测试、可调优、零延迟、零成本 |
| **给依据** | **知识库检索** | 让答案有出处，不是凭空生成 |
| **说人话** | **大模型** | 把结构化的结论组织成自然语言 |

> **★ 大模型只做"翻译"，不做"判断"。**
> 所以**即使大模型完全不可用，系统降级返回结构化文本，结论依然是对的。**

## 7. 边界与降级

### 信息不足时怎么办（★ 重要的产品态度）

| 最高置信度 | 系统行为 | 界面表现 |
|---|---|---|
| **≥ 0.6** | 明确给结论 | "最可能：浇水过多（62.5%）" |
| **0.4 – 0.6** | 说"较可能"，同时列出第二可能和**鉴别方法** | "较可能是 X，也可能是 Y。可以这样区分：…" |
| **< 0.4** | **不下结论**，引导补充信息 | "信息还不够，麻烦补充这几点：…" |
| **一条规则都没命中** | 转知识库问答 | "建议直接描述一下情况，我帮你查资料" |

> **★ 我们宁可说"不知道"，也不武断给一个结论。**
>
> 因为给错结论的代价比不给结论大得多——用户会按错的建议去处理，可能把植物弄死。

### 换了语境会怎样

同一个症状，不同上下文，结论完全不同：

| 场景 | 关键差异 | 结论 |
|---|---|---|
| 老叶先黄 + 浇水频繁 | ratio 1.79 | **浇水过多** 62.5% |
| 老叶先黄 + 浇水正常 + 秋季 | ratio 0.8，AUTUMN | **正常代谢** 权重占优 |
| 新叶先黄 + 弱光 | NEW + LOW | **光照不足** |
| 叶脉绿、叶肉黄 + 从未施肥 | GREEN_VEIN + NONE | **缺肥** |
| 全株均匀发黄 + 弱光 | UNIFORM + LOW | **光照不足** |

**这就是为什么必须问"从老叶还是新叶开始"——它决定了后面完全不同的判断路径。**

## 8. 汇报时怎么讲这一段

### 如果老师问「你们的诊断具体怎么做的？」

**照这个顺序讲**：

> **第一步，我们不直接猜。** 用户说叶子黄了，照片只能告诉我们"黄了"，但看不出"为什么黄"。所以我们先问一个关键问题——**黄叶是从下面的老叶开始，还是上面的新叶？**
>
> **第二步，系统自动去查这盆植物的档案。** 最近的浇水记录、放在哪个房间、用的是陶盆还是陶瓷盆、家里湿度多少。这些用户不用填，系统自己算。
>
> **第三步，把能排除的排除掉。** 我们准备了 35 条规则，比如「老叶先黄 + 最近浇水太频繁 → 多半是浇多了」「新叶先黄 + 光照不足 → 是缺光」。系统逐条检查，命中的就累加权重。
>
> **第四步，得票最高的就是结论，而且我们要把票数亮出来。** 比如这个案例里，"浇水过多"拿到 62.5%，"空气干燥"27.5%。**用户能看到这个比例是怎么来的，也能看到命中了哪几条规则。**
>
> **最后一点很重要：如果票数都不高，系统不会硬给结论。** 它会说"信息不足，麻烦补充这几点"。**我们认为承认不确定，比假装确定更值得信任。**

### 三个数字，记住就能撑住追问

| 数字 | 含义 |
|---|---|
| **35 条** | 症状判因规则总数 |
| **10 类 / 14 类** | 覆盖的症状数 / 病因数 |
| **62.5%** | 上面算例的结论置信度 |

### 最可能被追问的两个点

**Q：这些规则是你们拍脑袋定的吗？**
> 不是。它们来自园艺里公认的判断经验——比如"黄叶从老叶开始 + 浇水过频 = 多半积水"。**我们做的是把它变成可计算、可解释、可测试的规则。** 每条规则能单独写单元测试，大模型做不到。

**Q：为什么是 62.5% 而不是 90%？**
