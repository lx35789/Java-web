# 13 · 植物状态追踪与个性化养护验证

> 回答两个问题：**怎么持续追踪一株植物的状态变化？怎么证明个性化养护真的有效？**
> 配套：`db/schema.sql`、`08-诊断流程详解.md`、`12-连续养护的数据来源.md`

---

## 0. 先说一个现有设计的缺口

翻了一下当前的数据库设计，**没有真正的"状态时间序列"**：

| 现有的 | 性质 | 缺什么 |
|---|---|---|
| `user_plant.health_status` | **静态枚举**（HEALTHY / WARNING / DISEASED / DEAD） | 只有一个"当前值"，**没有历史，看不出变化** |
| `plant_photo` | 照片 + `taken_at` 时间 | 有图有时间，但**没有从图里提取出状态** |
| `disease_record` | **事件**，一次诊断一条 | 是离散事件，不是连续观测 |
| `care_log` | **行为记录**（我做了什么） | 记录的是"人做了什么"，不是"植物怎么样了" |

**核心问题：我们在记录「用户做了什么」，但没有记录「植物变成了什么样」。**

而这恰恰是"个性化养护"能不能成立的关键——**没有状态反馈，怎么知道计划对不对？**

---

## 1. 状态怎么定义

### 1.1 三个维度，够用就行

不要设计一堆指标，用户答不上来。**三个维度、每个 3–5 秒能回答**：

| 维度 | 选项 | 谁来判断 |
|---|---|---|
| **叶片状态** | 精神饱满 / 一般 / 有点蔫或发黄 / 明显不好 | 用户看 + 照片分析 |
| **长势** | 有新叶 / 没变化 / 有落叶 | 用户看 |
| **黄叶数量** | 没有 / 1–2 片 / 3–5 片 / 很多 | 用户数 + 照片分析 |

### 1.2 合成一个「健康指数」（0–100）

**不要让用户算分**，系统自动合成：

```
健康指数 = 100
         − 叶片状态扣分     （蔫/黄 扣 10–30）
         − 黄叶数量扣分     （每片扣 3，上限 30）
         − 落叶扣分
         + 新叶加分         （+10，上限 +20）
```

**为什么要合成一个分**：因为**单个指标看不出趋势，合成一个数才能画曲线**。

```
健康指数
 100 ┤●
  90 ┤  ●──●
  80 ┤        ●
  70 ┤          ●
  60 ┤            ●──●
     └────────────────────→ 时间（周）
      第1周            第6周
              ↑ 这里开始下滑
```

**这条曲线就是"持续追踪"的产物。**

## 2. ★ 怎么采集（关键：寄生在已有动作上）

**和记录浇水一样——绝对不要让用户"专门去做状态记录"。**

### 2.1 三个天然的观测点

| 观测点 | 用户成本 | 说明 |
|---|---|---|
| ★ **拍照时** | **0**（本来就在拍） | 每次拍照自动形成一条观测记录 |
| ★ **做诊断时** | **0**（本来就在诊断） | 诊断结果自动成为一次状态快照 |
| **点"已完成"时** | **可选一次点击** | 弹出极简问题："浇完了，植物看起来？" |

> **★ 原则和上一轮一样：不要创造新动作，要附着在已有动作上。**
>
> 用户拍照是为了识别或记录，**顺手就完成了一次状态观测**。

### 2.2 主动询问的时机（不要天天问）

只在**这些时刻**才问，而且只问一次：

| 时机 | 问题 |
|---|---|
| 添加植物时 | 「它现在状态怎么样？」（建立基线） |
| 复诊时（上次诊断后 7 天） | 「比上次好点了吗？」 |
| 连续 3 次跳过提醒时 | 「是不是不太需要浇水了？它现在怎么样？」 |
| 每周一次（可选，可关闭） | 「本周状态打卡」 |

### 2.3 极简交互（3 秒完成）

```
┌─ 小绿今天怎么样？ ─────────────────┐
│                                    │
│  叶片   [饱满] [一般] [发蔫] [很差] │
│  新叶   [有]  [没有]               │
│  黄叶   [无] [1-2] [3-5] [很多]    │
│                                    │
│           [跳过]      [记录]        │
└────────────────────────────────────┘
```

**三个选择，点三下。** 比填表单快得多。

## 3. 数据模型（新增一张表）

```sql
-- 植物状态观测：每次观测一条，形成时间序列
CREATE TABLE `plant_observation` (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_plant_id   BIGINT UNSIGNED NOT NULL,
  observed_at     DATETIME        NOT NULL  COMMENT '观测时刻',

  -- 来源：区分主动记录 / 拍照自动 / 诊断自动
  source          VARCHAR(24)     NOT NULL  COMMENT 'PHOTO/MANUAL/DIAGNOSIS/REMINDER',

  photo_id        BIGINT UNSIGNED DEFAULT NULL COMMENT '若来自照片',
  diagnosis_id    BIGINT UNSIGNED DEFAULT NULL COMMENT '若来自诊断',

  -- 用户主观指标
  leaf_score      TINYINT         DEFAULT NULL COMMENT '1饱满 2一般 3发蔫 4很差',
  growth_score    TINYINT         DEFAULT NULL COMMENT '1有新叶 2无变化 3有落叶',
  yellow_leaf     TINYINT         DEFAULT NULL COMMENT '0无 1少 2中 3多',

  -- ★ 客观指标：从照片自动算出来（见第 5 节）
  green_ratio     DECIMAL(5,4)    DEFAULT NULL COMMENT '绿色像素占比',
  yellow_ratio    DECIMAL(5,4)    DEFAULT NULL COMMENT '黄色像素占比',

  -- 合成
  health_index    TINYINT         NOT NULL  COMMENT '0-100 综合健康指数',

  note            VARCHAR(255)    DEFAULT NULL,
  created_at      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,

  PRIMARY KEY (id),
  KEY idx_plant_time (user_plant_id, observed_at),
  CONSTRAINT fk_obs_plant FOREIGN KEY (user_plant_id)
      REFERENCES `user_plant`(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='植物状态观测（时间序列）';
```

> **同时建议**：`user_plant.health_status` 保留，但**改成由最新观测自动推导**，而不是让用户手改。
> 这样两者不会打架。

## 4. ★ 怎么用于个性化：把「开环」变成「闭环」

**这是本节最重要的部分。**

### 4.1 现在的规则引擎是"开环"的

```
环境数据（季节/光照/花盆/天气）→ 规则引擎 → 浇水间隔
```

**问题：算出来的间隔对不对，系统不知道。** 它只是按公式算，没有反馈。

### 4.2 加上状态追踪后变成"闭环"

```
        ┌──────────────────────────────┐
        │                              │
        ▼                              │
   规则引擎 → 生成计划 → 提醒 → 用户执行 │
        │                              │
        │                              │
        └── ← 观测状态 ← ← ← ← ← ← ← ← ┘
               （植物变好还是变差？）
```

**有了反馈，系统就能自己调整。**

### 4.3 自适应调整算法

```java
/**
 * 根据近期观测结果，微调浇水间隔
 * 注意：只在有足够观测数据时才调整，且必须可解释
 */
public AdjustResult adaptWateringInterval(Long userPlantId) {
    List<PlantObservation> recent = obsRepo.findRecent(userPlantId, 3); // 最近 3 次
    if (recent.size() < 2) return AdjustResult.noChange("观测数据不足");

    CarePlan plan = planRepo.findActive(userPlantId, "WATER");
    int current = plan.getEffectiveIntervalDays();
    int speciesMin = plan.getSpecies().getMinIntervalDays();

    double slope = healthSlope(recent);          // 健康指数斜率
    double waterRatio = recentWateringRatio(userPlantId);

    // 情况 A：状态在变差，且浇水频率偏低 → 间隔太长了，缩短
    if (slope < -5 && waterRatio < 1.0) {
        int next = Math.max(speciesMin, (int) Math.round(current * 0.85));
        return AdjustResult.change(next,
            "最近 " + recent.size() + " 次观测显示健康指数持续下滑，"
          + "且实际浇水频率低于建议值，判断间隔偏长");
    }

    // 情况 B：状态在变差，且浇水频率偏高 → 间隔太短了，延长
    if (slope < -5 && waterRatio > 1.8) {
        int next = (int) Math.round(current * 1.15);
        return AdjustResult.change(next,
            "最近 " + recent.size() + " 次观测显示健康指数下滑，"
          + "但实际浇水频率已达建议值的 " + String.format("%.1f", waterRatio) + " 倍，"
          + "判断存在浇水过频，延长间隔");
    }

    // 情况 C：状态稳定向好 → 保持
    return AdjustResult.noChange("状态稳定，维持当前计划");
}

/** 斜率：负数表示在变差 */
private double healthSlope(List<PlantObservation> list) {
    // 线性回归或简单首尾差
    int first = list.get(0).getHealthIndex();
    int last  = list.get(list.size() - 1).getHealthIndex();
    return (double) (last - first) / (list.size() - 1);
}
```

### 4.4 ★ 调整也必须可解释（和项目的核心定位一致）

调整发生时，**要像诊断一样给出理由**：

```
┌─ 你的养护计划已自动调整 ──────────────────┐
│                                           │
│   浇水间隔：5 天  →  4 天                  │
│                                           │
│   为什么调整？                             │
│   · 最近 3 次观测显示健康指数从 82 降到 64  │
│   · 这 14 天你实际浇了 2 次，低于建议的 3 次 │
│   · 综合判断：水分不足，间隔偏长            │
│                                           │
│   [ 保持原计划 ]  [ 采纳新计划 ]            │
└───────────────────────────────────────────┘
```

> **★ 这一点很重要**：如果系统悄悄改了计划，用户会觉得莫名其妙。
> **改了就要说清楚为什么**——这和"可解释"的核心定位是一致的。

## 5. ★ 客观量化：从照片自动算状态

**问题**：用户主观打分不可靠（有人觉得"还行"其实是快死了）。

**解法**：用**简单的图像分析**算客观指标——**不需要训练模型，几十行代码**。

### 5.1 原理

植物叶片健康时是**绿色**，出问题时向**黄色/褐色**转变。所以在 HSV 色彩空间里做阈值分割就能量化：

```python
import cv2
import numpy as np

def analyze_leaf_health(image_bytes: bytes) -> dict:
    """
    返回绿色占比 / 黄色占比 / 褐色占比
    这是最朴素的植物表型分析，无需训练模型
    """
    img = cv2.imdecode(np.frombuffer(image_bytes, np.uint8), cv2.IMREAD_COLOR)
    hsv = cv2.cvtColor(img, cv2.COLOR_BGR2HSV)

    # 绿色：H 35–85
    green = cv2.inRange(hsv, (35, 40, 40), (85, 255, 255))

    # 黄色：H 20–35
    yellow = cv2.inRange(hsv, (20, 60, 60), (35, 255, 255))

    # 褐色/枯焦：H 0–20 且饱和度较高、明度偏低
    brown = cv2.inRange(hsv, (0, 60, 20), (20, 255, 160))

    # 只统计"植物区域"（排除背景）—— 用绿色+黄色+褐色作为前景掩码
    plant_mask = cv2.bitwise_or(cv2.bitwise_or(green, yellow), brown)
    total = int(np.count_nonzero(plant_mask))
    if total < 500:                      # 前景太小，判定为无效
        return {"valid": False}

    return {
        "valid": True,
        "greenRatio":  np.count_nonzero(green)  / total,
        "yellowRatio": np.count_nonzero(yellow) / total,
        "brownRatio":  np.count_nonzero(brown)  / total,
    }
```

### 5.2 怎么变成指标

```python
health_index_from_photo = round(
      greenRatio  * 100
    - yellowRatio * 80
    - brownRatio  * 120
)   # 再 clamp 到 0–100
```

**绿色越多分越高，黄褐越多扣分越狠。**

### 5.3 ★ 必须配「标准化拍摄」，否则数据不可比

**这是最容易失败的地方**——换了个光线、换了个角度，算出来的值就没法比较。

| 措施 | 做法 |
|---|---|
| **固定角度** | 在花盆边贴个标记，手机每次都从标记方向拍 |
| **固定光照** | 统一在上午某个时段拍（自然光稳定） |
| **固定背景** | 白墙或纯色背景，避免杂物 |
| **加参照物** | 放一张固定大小的小卡片，便于对比尺度 |
| **APP 辅助** | 拍照时叠加半透明轮廓线，提示用户对齐 |

> **★ 如果做不到标准化，就退而求其次**：
> **只做纵向自比较**（同一盆植物的照片互相比），**不做横向比较**（不同植物之间不比）。
> 因为同一盆植物的拍摄习惯相对一致，光线影响被部分抵消。

### 5.4 诚实的局限

**要主动承认这些局限**（写在论文里、答辩时说）：

| 局限 | 影响 |
|---|---|
| 光照变化会显著影响颜色值 | 标准化拍摄能缓解，不能消除 |
| 背景杂物会干扰分割 | 需要用户配合 |
| 不同物种的正常颜色不同 | 需要按物种设基线 |
| 不能识别病斑类型 | 它只给"状态分"，诊断还是靠规则引擎 |

> **定位**：这是一个**低成本、够用的客观参考指标**，不是精确的植物表型测量。
> **它和用户主观打分互为校验**——两者偏差大时，提示用户重新观测。

## 6. ★ 怎么测试验证个性化养护

这是问题的核心：**怎么证明"个性化"比"通用建议"更好？**

### 6.1 实验设计

| 项 | 设计 |
|---|---|
| **假设** | 使用个性化养护计划的植物，状态改善程度显著优于使用固定建议的植物 |
| **分组** | **A 组（实验）**：用系统的个性化计划<br>**B 组（对照）**：用通用建议（如"一周浇一次"） |
| **对象** | 同一种植物（建议用绿萝，好养不易死）、相近起始状态 |
| **样本量** | 每组 **5–10 盆**（低于 5 盆结论不可信） |
| **周期** | **至少 6–8 周**（植物生长慢，短了看不出差异） |
| **控制变量** | 同一环境（同一房间）、同一时期（同一季节）、同规格花盆和土壤 |

### 6.2 因变量（怎么衡量"变好了"）

| 指标 | 采集方式 | 频率 |
|---|---|---|
| ★ **健康指数** | 用户打分 + 照片分析 | **每周 1 次** |
| 黄叶数量 | 人工数 | 每周 1 次 |
| 新叶数量 | 人工数 | 每周 1 次 |
| 株高 / 冠幅 | 卷尺 | 每 2 周 |
| **存活率** | 是否死亡 | 全程 |
| 浇水次数偏差 | 实际 vs 建议 | 持续 |

### 6.3 分析

```
对比两组：健康指数变化量（末次 − 首次）
        黄叶数量变化量
        新叶数量

用简单的 t 检验或 Mann-Whitney U 检验（样本小用后者）
报告：均值 ± 标准差、p 值、效应量
```

### 6.4 ★ 但现实约束很硬

**必须承认**：16 周里做严格对照实验**很难**：

| 约束 | 影响 |
|---|---|
| 植物生长慢 | 6–8 周可能只看出"没死"，看不出"长得更好" |
| 同学不一定配合 | 每周观测会掉队 |
| 需要同质样本 | 买 20 盆同规格绿萝要经费 |
| 期间会放假 | 寒假/暑假没人浇水 |

### 6.5 三个可行的替代方案

#### 方案 A：★ 团队自养小样本对照（最推荐）

**团队自己养 8–10 盆，亲自记录。** 这是最可控的：

```
	A组（个性化）        B组（固定一周一次）
	─────────────────────────────────────
	  1 号                 6 号
	  2 号                 7 号
	  3 号                 8 号
	  4 号                 9 号
	  5 号                10 号
	  同一房间、同一批次购入、同规格盆土
```

**优点**：可控、观测不掉队、数据质量高。
**缺点**：样本小，结论只能算"初步验证"。
**但对学生项目，这已经足够诚实且有说服力了。**

#### 方案 B：回顾性分析（用已有数据）

不去做新实验，而是分析系统里已有的数据：

> 对比"连续记录 ≥ 4 周的植物"与"记录稀疏的植物"，其健康指数的变化差异。

**优点**：零额外成本，用的是真实用户数据。
**缺点**：有选择偏差（愿意记录的人本来就更上心），**必须在论文里说明这一点**。

#### 方案 C：专家评审（补足"效果"之外的维度）

植物状态变化慢，但**建议的合理性**可以立刻评估：

> 请 3–5 位有园艺经验的人（园艺店老板、农学老师）对系统生成的建议打分：
> 「这个建议合不合理？」「比通用建议更贴合这盆植物的情况吗？」
> 1–5 分，报告平均值和一致性。

**优点**：快、成本低、能立刻做。
**缺点**：评的是"合理性"不是"效果"。

### 6.6 ★ 建议组合使用

```
主证据   → 方案 A（团队自养 8–10 盆，8 周）
辅助证据 → 方案 C（专家评审，1 周内可完成）
补充分析 → 方案 B（回顾性分析已有数据）
```

**三条证据互相印证，比单独做一条要可信得多**，而且**承认了各自的局限**——这在答辩时是加分项。

## 7. 展示设计（让用户看到变化）

有了时间序列，就能做出很有说服力的界面：

### 7.1 状态趋势图

```
健康指数
 100 ┤
  90 ┤    ●───●
  80 ┤  ●       ●
  70 ┤            ●───●
  60 ┤                  ●
     └──────────────────────→
      6/1  6/8  6/15 6/22 6/29
            ↑
         开始用个性化计划
```

### 7.2 时间线 + 照片对比

```
[6/1 照片]  →  [6/15 照片]  →  [6/29 照片]
  🌿 健康 82     🍂 健康 64      🌿 健康 79
                                   ↑ 调整间隔后恢复
```

**这个"V 型曲线 + 三张照片"是最有说服力的证据** —— 它同时证明了：
1. 系统发现了问题（健康指数下滑）
2. 系统做了调整（间隔 5→4 天）
3. 调整生效了（状态恢复）

> **★ 这一条如果做实了，就是整个项目最亮眼的演示素材。**

## 8. 汇报话术（1 分钟版）

> **要追踪一株植物的状态变化，光有"健康/不健康"这种标签是不够的——那是静态的。必须把它变成有时间戳的记录。**
>
> 所以我们加了一层「状态观测」：用户拍照、做诊断的时候，**顺手就完成了一次观测**。系统还会从照片里自动算出绿色和黄色的比例，给一个客观分数。**这些分数连起来就是一条曲线。**
>
> **这条曲线让我们的养护计划从"开环"变成了"闭环"。**
> 原来的规则引擎只按公式算间隔，算完就完事了——对不对它不知道。有了状态曲线，系统就能发现"健康指数在连续下滑"，**自动把间隔从 5 天调到 4 天，并且告诉你为什么调**。
>
> **验证方面**，我们设计了三重证据：
> 一是**团队自养 8 到 10 盆做对照**，一半用个性化计划、一半用"一周浇一次"的通用建议，跟踪 8 周；
> 二是**请园艺从业者评审建议的合理性**；
> 三是**回顾性分析系统里已有的数据**。
> 三条证据互相印证，而且我们会在论文里说明各自的局限。

## 9. 如果被追问

**Q：健康指数是用户打的分，主观性太强，能作为研究指标吗？**

> 所以我们做了双轨：**用户主观打分 + 照片客观分析**。
> 照片分析用 HSV 色彩空间算绿色和黄色的像素占比，不依赖模型，是客观值。
> **两者互为校验**——偏差大时提示用户重新观测。论文里会同时报告两个指标的一致性。

**Q：照片分析受光线影响很大吧？**

> 是，这是已知局限。
> 对策是**标准化拍摄**（固定角度、固定时段、固定背景、加参照物），以及**只做纵向自比较、不做横向比较**——同一盆植物的照片互相比，光线影响被部分抵消。
> 我们把它定位为**低成本、够用的参考指标**，不是精确的植物表型测量。

**Q：8 周能看出差异吗？**

> 说实话，**能看出"没死"和"状态趋势"，不一定能看出"长得更好"**。植物生长太慢。
> 所以我们不把结论下得太满——报告的是"初步验证"，并明确说明样本量和周期的限制。**承认局限比夸大结论更可信。**

**Q：如果实验结果不显著怎么办？**

> 那也是有价值的结论。**不显著说明"个性化"在这个尺度上的收益没有想象中大**，或者说明我们的系数体系需要调整。
> 我们会分析原因：是样本太小、周期太短，还是系数设置不合理。
> **实验的价值不只在于证明假设成立，也在于发现问题。**

## 10. 一页纸总结

│        没记录"植物变成了什么样"                  │
├────────────────────────────────────────────────┤
│  解法：新增 plant_observation 表                 │
│        · 三个维度：叶片 / 长势 / 黄叶数           │
│        · 合成一个 0–100 健康指数                 │
│        · 形成时间序列 → 能画曲线                 │
├────────────────────────────────────────────────┤
│  采集：寄生在已有动作上（拍照、诊断时自动记录）    │
│        + 每周一次三秒打卡（可关闭）               │
│        + ★ 照片自动分析（HSV 色彩分割，无需模型） │
├────────────────────────────────────────────────┤
│  价值：把规则引擎从「开环」变「闭环」             │
│        状态下滑 → 自动调间隔 → 并解释为什么调      │

│        ③ 回顾性分析已有数据（补充）              │
└────────────────────────────────────────────────┘
