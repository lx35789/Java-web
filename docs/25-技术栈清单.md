## 2. 移动端（Android）

| 技术 | 版本 | 用途 |
|---|---|---|
| **Capacitor** | 8.6 | 把 Vue 打包的 `dist/` 封装成原生 Android App |
| **Android SDK** | compileSdk 36 / targetSdk 36 / minSdk 24 | 覆盖 Android 7.0 以上 |
| **Gradle** | 8.14.3 | Android 构建 |
| **JDK** | 21 | Capacitor 8 要求 |

**关键点（PPT 可讲）**

- 移动端**不是**另一套代码：同一份 Vue 前端，`npm run build --mode android` → `cap sync` → `assembleDebug`
- 后端不打包进 APK（Android 跑不了 MySQL，Spring Boot 也不支持 ART）
- `androidScheme: http` → App 源为 `http://localhost`，访问 https 后端不触发混合内容
- 上传前压缩：3.2 MB → 121 KB，公网隧道上传从十几秒降到 **0.6 秒**

## 9. 答辩时可能被问到的三个点

**Q：为什么移动端用 Capacitor 而不是原生开发？**
A：前端已经是 Vue 3 的完整应用，Capacitor 直接复用同一套代码，改一处两端生效；原生开发要重写一遍 UI 与业务，成本高。代价是性能不如原生，但这个应用是表单+图片为主，没有性能瓶颈。

**Q：为什么后端是 Java + Python 两个服务？**
A：职责分离。Java 负责业务、权限、数据；Python 负责模型推理（生态在 Python 侧，ONNX Runtime + NumPy 更顺手）。两者通过 HTTP 通信，可独立部署、独立扩容、独立重启。

**Q：模型为什么用 MobileNetV3 而不是更大的网络？**
A：部署目标是 CPU 推理 + 手机端可用。MobileNetV3-Large 在 160×160 输入下单张推理约 50–100ms，模型仅 16 MB；更大的骨干（EfficientNet、ConvNeXt）训练慢一倍以上、收益有限（训练文档里做过对比，`mobilenetv3_large_100` 实测最优）。
