# 植语助手（GreenThumb AI）技术评审与修正方案

> 评审对象：项目定位 / 核心功能 / AI 方案 / 数据来源 / 技术架构 / 数据库表
> 结论先行：**产品设计是合格的，AI 落点也清晰，但病害识别模块的数据地基是空的，另有 3 个高风险项，需在写代码前修正。**

## 1. 【致命】病害识别：PlantVillage 里没有室内绿植

### 事实

PlantVillage 数据集：**54,306 张图像，14 种作物，26 种病害**。这 14 种作物是苹果、蓝莓、樱桃、玉米、葡萄、橙、桃、辣椒、马铃薯、树莓、大豆、南瓜、草莓、番茄——**全部是农作物，没有一种室内观叶植物**。

所以方案里这句：

> 「PlantVillage 数据集筛选室内植物相关病害」

**这个动作在物理上不存在**。没有可筛选的对象。

### 为什么不能"迁移"

即使你硬用番茄的早疫病、葡萄的黑腐病训练，模型学到的判别特征会被**物种外观差异**主导，而不是**病斑病理特征**。龟背竹的叶斑在纹理上跟葡萄叶斑毫无可比性。跨物种迁移在**物种识别**任务上成立（都是"叶子"），在**病害识别**任务上基本不成立。

### 解决方案：换成真实的室内植物病害数据集

存在一个直接命中的数据集 —— **Combined Indoor Plant Disease Dataset: Succulents & Houseplants**：

| 项 | 内容 |
|---|---|
| 规模 | **21,097 张**，15+ 类别 |
| 物种 | 芦荟、仙人掌（Opuntia）、**绿萝（Money Plant / Epipremnum aureum）**、**虎皮兰（Snake Plant / Dracaena trifasciata）**、吊兰 |
| 病害类 | Healthy、Aloe Rust、炭疽病、叶斑病、晒伤、胭脂虫感染、细菌性萎蔫、锰中毒、叶片枯萎、真菌性叶斑、叶尖坏死 |
| 来源 | Mendeley Data（**CC BY 4.0**）× 2 + Roboflow Universe（Public Domain Equivalent，需署名） |

**这个数据集的价值在于：它覆盖的正是你 50 种植物库里的绿萝和虎皮兰**，而 PlantVillage 一个都不覆盖。

### 但要注意一件事：类别结构不同

这个数据集是**「物种 × 病害」**结构（Aloe Rust 只对芦荟成立，细菌性萎蔫只对绿萝成立），**不是**你想要的「白粉病 / 黑斑病 / 黄叶」扁平分类。

两条路：

- **方案 A（推荐，简单）**：直接扁平化为 N 类多分类（含各物种的健康类），模型输出「绿萝-细菌性萎蔫」。缺点：类数少（约 11–15 类），且单类样本可能很少。
- **方案 B（更严谨，答辩加分）**：**物种条件化双头模型**——先跑物种识别，再把该物种对应的病害子集喂给病害头。这样"芦荟锈病"不会出现在绿萝的诊断结果里，逻辑正确。代价是实现复杂度上升。

> 建议：Demo 用 A，论文里把 B 作为改进方向写。

## 2. 【高风险】"黄叶"不是病害，是症状

你列的病害类别是「白粉病、黑斑病、**黄叶**等 5–10 类」。问题在于：

- **白粉病、黑斑病** = 病原体引起的**病理性病害**（真菌）
- **黄叶** = **症状**，病因可能是浇水过多、光照不足、肥害、空调房湿度低、正常代谢、缺氮……

**室内绿植的问题里，绝大多数是养护问题，不是病害。** 用户说"叶子黄了"，正确答案通常是"你浇多了"，而不是某个病原体。

### 修正建议：把「病害识别」和「症状诊断」拆成两条路径

```
用户上传图片
   │
   ├─ 有明确病斑/霉层/虫体  → 病害识别模型（真·病理类别，5–8 类）
   │                           输出：病害名 + 处理建议（来自 disease_info 表）
   │
   └─ 只是黄叶/焦边/落叶/徒长 → 症状诊断路径
                               输入：症状标签 + 该植物养护历史 + 环境
                               处理：规则引擎判因 → RAG 检索 → LLM 给方案
```

**这反而是设计亮点。** 答辩时「我们把病理性病害和生理性症状分开处理」是一个能讲清楚的设计决策，比笼统说"图片分类"高一个层次。

如果你确实想要「白粉病/黑斑病」这两个通用类别而又没有标注数据，兜底方案是用 **CLIP zero-shot 分类**（用文本 prompt 如 "a leaf with powdery mildew" 做图文匹配），不做训练也能出结果，承认它是弱分类器即可。

## 3. 【高风险】50 种植物库 vs 47 类模型，对不上

**House Plant Species（Kaggle）** 的真实情况：

| 项 | 内容 |
|---|---|
| 规模 | 14,790 张，**47 类** |
| 来源 | **Bing Images 爬取 + 非专业人员人工清理** |
| 不平衡 | 每类 **66 张（Yucca）～ 547 张（Monstera Deliciosa）**，差了 8 倍 |
| 内容 | 室内室外混杂，整株照 + 局部特写混杂 |
| **版权** | 数据集页明确写着 **"for personal use only due to copyright considerations"** |

三个问题：

1. **47 ≠ 50**：你的植物库有 3 种没有对应模型类。必须有一张映射表，未覆盖的走 Pl@ntNet API 兜底。
2. **版权**：校内毕设/课程设计用没问题；**如果要对外发布或商用，这个数据集不能用**（图片来自 Bing，原始版权不属于数据集作者）。
3. **长尾**：66 张的类，ResNet50 会直接过拟合。**用 MobileNetV3-Large 或 EfficientNet-B0**，ImageNet 预训练 + 冻结主干先训分类头 + 类权重（class weight）+ 强数据增强。

### 预期的真实指标（写给答辩预期管理）

别承诺 99%。14,790 张 / 47 类 / 非专业标注的真实预期：

- **Top-1：75% – 85%**
- **Top-3：92% – 96%**

**Top-3 才是你产品的核心指标**——方案里"识别结果给 Top-3，不追求 100% 准确"这个定位非常正确，坚持它。

## 4. 【高风险】RAG 语料版权

方案写「维基百科、RHS、Gardening Know How 等公开园艺内容，整理成 JSON」。

- **Wikipedia**：CC BY-SA，可用，**必须署名 + 相同方式共享**。
- **RHS（英国皇家园艺学会）、Gardening Know How**：**版权内容**。整站抓取、存入知识库、再通过 LLM 生成回答对外提供——这是**衍生作品分发**，不属于合理使用范畴。

**修正建议**：

1. 语料主体用 Wikipedia + **自己撰写的养护知识**（这本来就是"知识库整理"该干的活）+ 公开论文。
2. RHS/GKH 只做**人工阅读后改写**，不整段入库。
3. 尊重 robots.txt，控制抓取频率。
4. 每条知识记录都带 `source` / `source_url` / `license` 字段（已加进建表脚本），并在回答中标注来源——**这同时解决了 RAG 可溯源性的问题，一举两得**。

## 5. 【架构简化】可以省掉一个数据库

方案是 **MySQL + PgVector**。但注意：**你的技术栈里已经有 Redis 了，而 Redis Stack 自带向量检索（RediSearch），Spring AI 提供官方 `RedisVectorStore` 实现**（与 `PgVectorStore` 并列）。

而你原本列了 Redis 却**从未定义它用来干什么**。

### 建议

**砍掉 PgVector / PostgreSQL**，用 Redis Stack 同时承担：

| 用途 | 说明 |
|---|---|
| **向量检索** | RAG 知识库 embedding |
| **AI 接口限流** | ⚠️ 重要：Pl@ntNet 免费额度 **500 次/天**，不做限流会被烧穿 |
| 识别结果缓存 | 同一张图重复识别直接命中缓存 |
| 植物库缓存 | 50 条热数据 |
| Token / Session | 登录态 |

收益：少一个数据库的部署、备份、事务一致性、跨库 join 问题。对一个 1–3 人的项目，这是**实打实的工期节省**。

> 如果导师明确要求"必须体现向量数据库"——Redis Stack 也是向量数据库，RegisSearch 的 KNN 检索是正经的向量检索实现，不影响答辩表述。

## 6. 【遗漏】方案里没有但必须有的东西

| 缺失项 | 为什么必须有 |
|---|---|
| **`user_environment` 表** | 你的个性化规则引擎是「植物需水量×季节系数×光照系数×**天气系数**」——但用户的城市、空调、暖气状态**没有任何地方存**。规则引擎没有输入源 |
| **`disease_info` 表** | 病害识别输出「类别 + 处理建议」，处理建议存哪？ |
| **`knowledge_chunk` 表** | RAG 的检索单元是 chunk，不是整篇文章。方案里只有 `knowledge_article`，没有分块表和 embedding 映射 |
| **`qa_message` 表** | `qa_session` 存不下一轮轮对话。要拆成 session + message 两张表 |
| **`plant_species.model_class_index`** | 植物库 50 种与模型 47 类的映射关系 |
| **`care_plan` / `care_task` 关系** | 方案列了两张表但没定义关系。应为 1:N（一个计划生成多个到期任务） |

另外几个工程细节：

- **定时任务幂等**：`care_task` 需要 `UNIQUE(plan_id, due_date)`，否则定时任务重跑会生成重复提醒。
- **识别接口限流**：见上，Pl@ntNet 500/天。
- **`care_log` 与 `care_task` 的关系**：用户标记"完成"应生成一条 log 并回填 task。方案里两张表是孤立的。

## 7. 技术选型的具体建议

| 项 | 方案原文 | 建议 |
|---|---|---|
| 识别模型 | MobileNetV3 / ResNet50 | **MobileNetV3-Large 或 EfficientNet-B0**。ResNet50（25M 参数）在 66 张的尾类上必然过拟合 |
| 训练策略 | — | ImageNet 预训练 → 冻结主干训分类头 → 解冻最后 2 个 stage 微调（小学习率）+ 类权重 + 强增强（翻转/裁剪/色彩抖动/随机擦除） |
| 病害数据 | PlantVillage | **换 Indoor Plant Disease Dataset**（见第 1 节） |
| 向量库 | PgVector | **Redis Stack**（见第 5 节） |
| 天气 | Open-Meteo 免 Key | ✅ 正确，确认免 Key。但**要注意：Open-Meteo 需要经纬度，不需要城市名**——你需要先做一步城市名 → 经纬度（它有配套的 Geocoding API），否则用户填"杭州"你没法直接查 |
| Spring AI | — | 1.0.x (GA) 或 2.0.x 均可，`RedisVectorStore` / `PgVectorStore` 都是官方实现 |

## 8. 建议的落地顺序（按"最快跑出可演示闭环"排序）

**核心原则：不要让模型训练阻塞后端开发。**

```
Phase 0  工程骨架
         三模块（backend / ai-service / frontend）+ Docker Compose（MySQL + Redis Stack + MinIO）

Phase 1  无 AI 的完整业务闭环  ← 最先做，最先能演示
         注册登录 → 植物库（50 种，人工整理种子数据）→ 我的植物
         → 养护计划生成（纯规则引擎）→ 提醒日历 → 标记完成 → 养护日志
         此时产品已经"活着"了

Phase 2  RAG 问答  ← 性价比最高
         知识库整理 → 分块 → embedding → Redis 检索 → Prompt 注入 → 回答 + 标来源
         成本最低，演示效果最好，"AI 感"最强

Phase 3  拍照识别
         ⚠️ 先用 Pl@ntNet API 把「上传 → 识别 → Top-3 → 一键加入我的植物」
         整条链路串通（半天工作量），模型训练并行进行
         模型训好后切换 source 字段即可，前端零改动

Phase 4  病害识别
         用室内数据集训练；同时实现"症状 vs 病害"分流（第 2 节）

Phase 5  可选增强
         天气集成 / 成长时间线 / 统计看板 / 自然语言添加植物
```

> **Phase 3 的这个顺序安排很关键**：识别链路的后端代码不依赖模型，用 API 先跑通，模型训练（最耗时、最不可控）并行做。避免"等模型训好再写后端"导致的进度风险。

## 10. 需要你确认的决策点

1. **病害模块**：接受换成室内数据集 + "症状/病害分流"设计吗？
2. **数据集版权**：这是校内毕设，还是准备对外发布？（决定能不能用 Bing 爬取的数据集）
3. **向量库**：同意砍掉 PgVector 改用 Redis Stack 吗？导师有没有硬性要求？
4. **要不要保留"白粉病/黑斑病"**：没有标注数据，只能 CLIP zero-shot 弱分类或纯 RAG 文字诊断。要还是砍？
