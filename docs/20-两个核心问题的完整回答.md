# 20 · 两个核心问题的完整回答

> Q1：**怎么确认是同一株植物？**
> Q2：**怎么实现绿植在连续时间节点上的个性化养护？**
>
> 本文把所有实验结论收敛到这两个工程问题上。所有数字都来自 `experiments/` 的真实数据实验。

---

# 问题一：怎么确认是同一株植物

## 核心判断：**"同一性"不能靠图像推断，只能靠用户声明 + 系统维持 + 图像校验**

这是必须先说清楚的前提。图像能回答的是"**这两张看起来像不像同一株**"，
但"是不是同一株"在物理上是一个既成事实，不是一个可推断量。所以设计要分四层。

## 层 1 · 显式身份锚定（唯一确定性的手段，必做）

| 手段 | 实现 | 成本 |
|---|---|---|
| **`plant_id`（主键）** | 用户在 App 里"添加一株植物"时创建，之后所有观测、计划、诊断全部挂在这个 id 下 | 0 |
| **物理标签** | 建议用户在花盆上贴一张手写标签（编号/名字） | ≈0 |
| **身份证照** | 添加时拍一张整株照 + 一张盆/标签照，存 `plant.identity_photos` | 0 |

**关键**：一旦 `plant_id` 建立，**同株判定就完成了**，之后系统的工作不是"识别"，
而是"**维持关联 + 发现异常**"。这一点决定了后面所有设计的性质。

## 层 2 · 观测叶锚定（不是"同一株"，而是"同一片叶"）← 最关键

这一条是本次实验最重要的产品产出。

**实验依据**：叶片选择（同一株上拍哪片叶）贡献了总方差的 **34.6%–42.2%**，
是**最大的单项可控噪声源**，比场次差异和株间差异都大。

**实现**：

```
首次：拍一张参考图 → 用户在图上点击选定一片叶 → 系统裁出该叶区域
      生成 leaf_anchor_id，并记录：叶序位置、相对株型的方位、叶形轮廓指纹
后续：取景框内半透明叠加参考图 → 引导用户对准同一片叶
      拍完自动比对叶形轮廓，偏差过大则提示"似乎不是同一片叶"
```

**为什么盯"同一片叶"而不是"同一株"**：同一株上的不同叶片，生理状态本来就不同
（老叶/新叶/向阳叶/背阴叶），把它们混在一起算，等于每次都在换测量对象。

## 层 3 · 图像软校验（只告警，不阻断）

用户会点错、拍错。需要软校验，但**准确率做不到 100%，所以只能提示不能拦截**。

| 校验维度 | 特征 | 可靠性 |
|---|---|---|
| **背景指纹** | 同一株长期在同一位置拍 → 背景（窗台纹理、桌面、墙面）应相似；用背景块的 LAB 直方图做相似度 | 中（换位置就失效） |
| **叶形指纹** | 观察叶的轮廓矩、叶脉走向、**固有缺损/斑点/虫咬痕** | **高**（叶子的疤痕是天然唯一标识） |
| **株型结构** | 枝干分叉角度、叶片排布 | 中（生长会改变） |
| **拍摄元数据** | 时间、设备、GPS/WiFi（若可用） | 低（仅辅助） |

**判定规则**：
- 相似度高 → 正常
- 相似度中 → 记录但正常入库
- 相似度低 → 提示"这看起来不像是小绿的 L1 叶，确认要继续吗？"，用户可强制通过

> ⚠️ **明确不做**：不承诺"AI 自动认得出这是同一株"。之前在技术评审里已经否决过
> ArUco 码、SuperPoint+SuperGlue 对齐等重方案，理由是**投入产出比不成立**——
> 一个手写标签 + 一次点击锚定就能解决的问题，不值得上视觉重识别。

## 层 4 · 数据库落地

现有 19 张表已覆盖主体，需要补 3 张：

```sql
-- 观测叶锚点
CREATE TABLE leaf_anchor (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  plant_id      BIGINT NOT NULL,
  anchor_name   VARCHAR(32),        -- "L1 第3片成熟叶"
  ref_image_id  BIGINT,             -- 参考图
  ref_bbox      VARCHAR(64),        -- 参考图上的叶片框 x,y,w,h
  contour_sig   BLOB,               -- 叶形轮廓指纹

  active        TINYINT DEFAULT 1

  id         BIGINT PRIMARY KEY AUTO_INCREMENT,

  ADD COLUMN anchor_id        BIGINT NULL,
  ADD COLUMN identity_score   DECIMAL(4,3) NULL,  -- 叶形/背景相似度
  ADD COLUMN identity_flag    VARCHAR(16) NULL;   -- OK / SUSPECT / FORCED
```

# 问题二：怎么实现连续时间节点的个性化养护

## 核心判断：**个性化的来源不是"看懂照片"，而是"记录 + 闭环"**

先给一个可能反直觉但很重要的结论：

> 养护计划的**个性化**，主要来自**结构化数据**（浇水/施肥/环境/用户反馈），
> 照片只负责两件事：**① 异常告警 ② 趋势方向**。

依据：颜色指标受光源影响极大（光源解释 79.2% 的表观变化，跨场次 corr = 0.968），
而结构化记录**零测量噪声**。把个性化押在照片上是不稳的。

## 一、数据分三层

| 层 | 内容 | 噪声 | 在闭环中的角色 |
|---|---|---|---|
| **事实层** | 浇水、施肥、换盆、环境温湿度、光照时长、用户打卡 | **0** | 计划的主要输入 |
| **观测层** | 照片 → 色彩指标（CLAB `a*`）+ **几何指标（叶片下垂角度）** + 光源质检 | 高（颜色）/ 低（几何） | 偏差检测 |
| **知识层** | 物种参数（光/水/温湿度）、症状规则库、知识库 | — | 先验与解释 |

**新增建议**：观测层里加 **几何通道（叶片下垂姿态/萎蔫角度）**。
理由是颜色对光照太敏感，而几何量**几乎不受光照影响**，对水分胁迫同样敏感。
这不是备选，是应该尽早并入的主线。

## 二、"个性化"的三个来源（只有第三个是真个性化）

```
┌── 来源1：物种先验 ──────── 绿萝 = 夏季7天/200ml   ← 这不是个性化，是"按品种"
│
├── 来源2：环境修正 ──────── 东向窗×室内24℃×无加湿 → ×0.9  ← 这是"按环境"
│
└── 来源3：个体反馈闭环 ──── 这株植物自己的观测序列 → 参数微调  ← 只有这个是真个性化
                            ★ 核心
```

**大多数人做"个性化养护"只做到来源 1+2 就停了，那只是"按品种按环境"。
真正的个性化必须来自来源 3。**

## 三、闭环算法（可直接实现）

```
初始：  P0 = species_base(物种) × env_modifier(环境)
        记录 P0 到 care_plan，并把推导依据写入 CarePlanExplain（"为什么这么排"）

循环：  每个观测节点 t：
    1. 质检  ── 高光 a* 与本株滚动基线比较，|z| > 2 → 标记 QUALITY_SUSPECT
    │            该次观测仍然入库，但**不参与趋势判定**
    │
    2. 取指标 M_t = (chlorophyll_t, droop_angle_t)
    │
    3. 算偏差 D_t = M_t − baseline(self, 滚动窗口)
    │
    4. 显著性判定 ← ★ 这一步决定"要不要动作"，不是所有波动都算变化
    │     若 |D_t| < k·σ  → 判为"无明显变化"，**不动作**（关键：防震荡）
    │     若 |D_t| ≥ k·σ  → 判为显著变化，方向 dir = sign(D_t)
    │     k 由目标假阳性率定：k=1.96 → 5% 假阳性；k=2.8 → 80% power
    │
    5. 归因（症状规则引擎）
    │     显著变差 + 盆土记录干燥 + 间隔超期     → 缺水
    │     显著变差 + 盆土记录持续潮湿            → 涝害 → **减少**浇水频率
    │     显著变差 + 叶面出现斑驳/花叶           → 病毒/病害（走病害通道）
    │     显著变好                               → 保持参数，延长观察间隔
    │
    6. 参数更新（小步 + 观察期）
    │     water_interval ← water_interval × (1 + α·dir),  α = 0.2~0.3
    │     ★ 单次调整幅度 ≤ 30%，避免过冲
    │     ★ 调整后进入 观察期（3~7天），期内不再调整
    │
    7. 写日志 plan_adjust_log
    │     "第18天观测到显著失水（Δchlorophyll=-4.6，超阈值3.4），
    │      浇水间隔 7天 → 5天"
    │     ← 这条日志就是产品"会解释为什么"的数据来源
    └─→ 回到 1
```

## 四、观测节点怎么排（**用噪声反推频率**，这是最容易被忽略的一环）

不能每天都拍——信息量低，还会让噪声淹没趋势。节点密度应当由 σ 决定：

| 参数 | 含义 | 怎么定 |
|---|---|---|
| `σ` | 单次拍摄的测量噪声 | **由 15 分钟重复性实验实测**（见下） |
| `Δmin = k·σ` | 最小可检测变化 | k = 2.8（80% power, 5% 假阳性） |
| 稳定期间隔 | 无变化时的观测周期 | 7 天 |
| 加密期 | 检出显著变化后 | 连续 3 天 |
| 观察期 | 参数调整后 | 不早于 3 天 |

**举例**：若实测 σ = 1.2，则 Δmin = 3.4。
→ 只有叶绿素代理指标变化超过 3.4 才报"变好/变坏"，否则一律报"无明显变化"。
**这条硬阈值规则直接决定了产品不会乱报。**

## 五、质检与降级（吸收文档 19 的结论）

| 情况 | 处理 |
|---|---|
| 光源质检不通过（高光 a\* 偏离 > 2σ） | 提示"本次光线与以往差异较大，建议换回常拍位置重拍"；用户坚持则入库但标 `QUALITY_SUSPECT`，**不参与趋势** |
| 连续 2 次无有效观测 | 退回物种默认计划，并提示用户 |
| 用户手动纠正 | 记入 `plan_adjust_log`，作为规则库的反馈样本 |
| 第三方识别 API 全挂 | 降级为手动选物种，**绝不报 500** |

```sql

  plant_id     BIGINT NOT NULL,
  plan_id      BIGINT NOT NULL,
  adjust_time  DATETIME NOT NULL,
  trigger_obs  BIGINT,                    -- 由哪次观测触发
  delta_metric VARCHAR(128),              -- Δchlorophyll=-4.6 (threshold 3.4)
  param_key    VARCHAR(32),               -- water_interval
  old_value    VARCHAR(32),
  new_value    VARCHAR(32),
  reason       VARCHAR(255)               -- 缺水性失水，证据：叶色下降+叶片下垂+盆土干
);
```

## 七、一个完整走查示例（答辩可直接演示）

**主体**：一盆绿萝「小绿」，东向窗台，室内 24℃。

| 时点 | 事件 | 系统动作 | 依据 |
|---|---|---|---|
| **D0** | 用户添加植物，选物种「绿萝」，填环境（东向窗/24℃/无加湿），拍身份证照，**点击选定观察叶 L1** | 生成初始计划：**7 天浇水一次，200ml**；推导依据写入 `CarePlanExplain` | 物种先验 × 环境修正 |
| D7 | 观测①：质检通过；`chlorophyll=24.1`，Δ=−0.2，**< 阈值 3.4** | 判"无明显变化"，**不动作** | 显著性阈值 |
| D14 | 观测②：`chlorophyll=23.8`，Δ=−0.3，**< 阈值** | 判"无明显变化"，**不动作** | 防震荡 |
| D15–17 | 用户出差，未浇水 | — | — |
| **D18** | 观测③：**质检不过**（高光 a\* \|z\|=2.6） | 提示重拍 | 光源探针 |
| D18 | 重拍通过：`chlorophyll=19.2`，Δ=**−4.6 > 3.4**；**几何：叶片下垂角度 +12°**；记录"盆土干，距上次浇水 11 天" | ① 交叉确认（颜色+几何）② 规则引擎归因 **缺水（置信度 0.82）** ③ 立即补水 250ml ④ **间隔 7 天 → 5 天**（α=0.3 小步）⑤ 写 `plan_adjust_log` | 闭环第 4–7 步 |
| D19 | 加密观测：`chlorophyll=22.6`（Δ=+3.4），下垂角度 −9° | 判"恢复中"，进入**观察期**，暂不调整 | 加密期规则 |
| D24 | 观测④：`chlorophyll=24.0`，回到基线 | 观察期结束，**参数锁定 5 天**；提示用户 | 观察期规则 |

**最终用户看到的一句话**：

> 「已根据小绿的实际反应，把浇水间隔稳定在 **5 天**。
> 调整发生在 6 月 18 日——那次它叶片下垂、叶色变浅，盆土已经干了 11 天。」

**这一句话就是这个产品的全部价值**：**连续观测 → 归因 → 调整 → 解释**。

# 总结：两个问题的答案收敛到同一件事

| | 问题一（同一株） | 问题二（连续个性化） |
|---|---|---|
| **本质** | 身份关联的**维持**，不是识别 | 结构性记录 + **闭环反馈** |
| **最关键的一步** | **锚定同一片叶**（消除 34.6–42.2% 的最大噪声源） | **显著性阈值**（\|Δ\| ≥ 2.8σ 才动作，防震荡） |
| **最大的风险** | 用户拍错/换叶 → 用叶形指纹软校验 | **光源漂移**（解释 79.2% 的表观变化）→ 用高光探针质检 |
| **该新增的能力** | `leaf_anchor` + `identity_score` | **几何通道（叶片下垂）** + `plan_adjust_log` |
| **不该做的事** | 视觉重识别（ArUco / 特征点对齐） | 每天拍 / 单张照片下健康结论 |

**一句话**：用一个用户点击的锚点解决"同一株"，用一个显著性阈值解决"不乱报"，
用一条调整日志解决"为什么"。这三件事都不依赖算法有多强，但缺一个产品就不成立。
