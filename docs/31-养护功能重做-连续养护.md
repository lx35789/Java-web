# 31 · 养护功能重做：从「三张表」到一株植物的连续养护

> 2026-11-20。改动范围：`backend`（观测/时间轴/自适应）、`ai-service`（色彩分析）、`frontend`（植物详情页）。

---

## 一、原来的问题不是界面丑，是没有"连续"

翻代码发现，养护这套东西**表建得很全，核心逻辑基本没写**：

| 设计里有 | 改动前 | 后果 |
|---|---|---|
| `plant_observation`（健康指数时间序列） | **零后端代码**，只有建表语句 | 画不出趋势，不知道植物在变好还是变坏 |
| 计划按「季节×光照×温湿度×盆材质」算间隔 | 只在生成时算一次，往后排 4 个任务 | 越用越空，一段时间后日历上什么都没有 |
| 观测反馈调整计划 | 无 | 叶子蔫了系统不知道，计划照旧 —— 开环 |
| 单株的连续记录 | 日历/日志是**全局横切**的表格 | 看不到「这株植物这半年经历了什么」 |

根因一句话：**只记录了"人做了什么"（`care_log`），没记录"植物变成什么样"（`plant_observation` 空转）**。
没有反馈就没有个性化，剩下的只能是三张表。

`docs/13` 其实早就设计好了三问快评 + 健康指数公式，只是一直没落地。这次把它补完。

## 二、现在做成了什么

### 1. 一株植物的一条时间轴

`GET /api/v1/my-plants/{id}/timeline` 现在合并四类事件，按时间倒序：

| 类型 | 来源 | 展示 |
|---|---|---|
| `OBSERVATION` | `plant_observation` | 🩺 状态观测 · 健康指数 39 |
| `CARE` | `care_log` | 💧 浇水 200ml |
| `PHOTO` | `plant_photo` | 📷 照片缩略图 |
| `DIAGNOSIS` | `disease_record` | 🔍 诊断 · Orchid_Anthracnose |

这样才看得出「浇了水 → 三天后叶子蔫了 → 诊断出根腐」的因果，而不是三块互不相干的卡片。
旧的 `photos` 字段保留，不影响成长时间线。

### 2. 30 秒状态快评 → 0-100 健康指数

`POST /api/v1/my-plants/{id}/observations`

三个选择题（`docs/13` 定的三维度）：

| 维度 | 选项 | 扣分 |
|---|---|---|
| 叶片 | 精神饱满 / 一般 / 有点蔫 / 明显不好 | 0 / −8 / −20 / −36 |
| 长势 | 有新叶 / 没变化 / 有落叶 | +10 / 0 / −10 |
| 黄叶 | 没有 / 1-2 片 / 3-5 片 / 很多 | 0 / −6 / −15 / −28 |

带照片时会额外走 AI 色彩分析（见下），两个分数加权：

```
只有主观：health = 主观分
主观 + 客观：health = 0.65 × 主观 + 0.35 × 客观
```

同时把 `user_plant.health_status` 同步掉（≥80 健康 / ≥55 需关注 / 其余有病状），列表页不用现算。

> 权重为什么是 0.65/0.35：主观三项是用户对自己这盆植物的判断，比颜色占比更贴近真实状态；但用户偶尔会"懒得看仔细"，照片指标起校准作用。反过来（客观占主导）会让同一盆植物换个光线拍就跳分。

### 3. 照片色彩分析（不看品种，只看状态）

`POST /v1/plant/metrics`（ai-service，新增 `app/plant_metrics.py`）

用 HSV 阈值分绿/黄/褐三类，前景 = 三类的并集，所以白墙木桌天然被排除，不需要分割模型。
返回占比而不是像素数，因此对拍摄距离不敏感。实测：

| 样本 | 绿 | 黄 | 褐 | 提示分 |
|---|---|---|---|---|
| 健康兰花叶特写 | 0.97~1.00 | 0.00~0.03 | 0 | 97+ |
| 炭疽病叶 | 0.43~0.80 | 0.20~0.55 | 0.00~0.02 | 52~62 |
| 日灼叶 | 0.00~0.79 | 0.02~0.88 | 0.04~0.83 | 0~45 |

拍糊了 / 没拍到植株（前景像素 < 500）返回 `available=false`，后端自动降级为纯主观分，不阻断记录。

### 4. 计划自适应（闭环）

`CarePlanService.adapt()`，两个触发点：**记录观测后**、**完成浇水任务后**。

两类证据：

- **健康趋势**：最近一次 ≤55 → ×0.9；单次下滑 ≥12 → ×0.92；连续三次 ≥85 → ×1.08
- **实际节奏**：最近 3 个浇水间隔的均值比计划短 25% 以上 → ×0.9；长 35% 以上 → ×1.1

改动幅度限制在乘积 0.85~1.15，且不足 1 天不动（否则曲线抖一下整个日历就重排）。
改完把原因写进 `care_plan.llm_explain`，前端 `CarePlanExplain` 原样展示：

> 因为最近一次健康指数只有 39，把浇水间隔从 8 天缩短到 7 天。

重排任务用「先删今天及以后的 PENDING，再从最后一次实际浇水往后铺 4 条」，
因为表上有 `uk_plan_due(plan_id, due_date)` 唯一索引，原地改日期会撞。

### 5. 详情页重排

```
[头部]  已陪伴 128 天 · 近期记录 12 条 · 最近观测 2026-11-20 17:17
```

## 三、接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/my-plants/{id}/observations?days=90` | 曲线：points + turns + summary |
| POST | `/api/v1/my-plants/{id}/observations` | 记录快评，可带 photoId |
| GET | `/api/v1/my-plants/{id}/observations/latest` | 最近一次 |
| GET | `/api/v1/my-plants/{id}/timeline` | 四类事件合并流（新增 events，保留 photos） |
| POST | `/v1/plant/metrics`（ai-service） | 照片色彩占比 |

请求示例：

```json
POST /api/v1/my-plants/136/observations
{ "leafScore": 4, "growthScore": 3, "yellowLeaf": 3,
  "photoId": 236, "note": "叶面出现褐斑，边缘发黄" }
→ { "healthIndex": 39, "greenRatio": 0.7988, "yellowRatio": 0.198, ... }
```

## 四、实测记录（2026-11-20）

用测试账号建了一盆蝴蝶兰（id=136，9 月 1 日入手）：

| 步骤 | 结果 |
|---|---|
| 生成计划 | 浇水 8 天（11-28）、施肥 25 天（12-15） |
| 记录「叶片挺括、有新叶」 | 健康指数 **100** |
| 记录「明显不好 + 3 片以上黄叶 + 炭疽病叶照片」 | 主观 26、客观 62 → **39**，曲线出现 −61 拐点 |
| 自动校准 | 浇水间隔 8 → **7 天**，原因写入 `llm_explain` |
| 时间轴 | 2 条观测 + 1 条照片按时间混排 |

## 五、还没做的

1. **里程碑 / 每周小结**：入手 100 天、第一次开花、换盆等节点，以及自动生成周报。这次没做。
2. **主动提醒**：表里有 `care_task.remind_at`，但没有定时任务扫描，目前只能进页面看。
3. **观测断档提醒**：如果 14 天没记录状态，应该推一次「拍张照看看」。需要定时任务配合。
4. **客观指标只用颜色**：没做叶面积/株高，因为家庭拍摄没有参照物，强行做误差比收益大。
