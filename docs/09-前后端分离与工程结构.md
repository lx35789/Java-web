# 09 · 前后端分离与工程结构

> 回答两个问题：**要不要分开写？分开写具体怎么做？**
> 配套：`04-API接口设计.md`（接口契约）、`02-项目重设计方案.md` 第 5 章（架构）

---

## 0. 结论

### 要不要分开？

| 你的项目 | 结论 |
|---|---|
| 技术栈 | ✅ **必须分开** |

**不是因为"分离更高级"，而是三个具体理由：**

1. **你的前端已经独立跑起来了。** 这是分离最大的好处——**前端和后端可以并行开发**，不用等对方。你们现在浏览器里能点的界面，就是分离带来的。
2. **你有 AI 服务（Python）。** 就算前端不分离，Java 和 Python 也必然是两个进程。**既然已经多了一个，再多一个不算负担。**
3. **将来要加小程序/App，后端不用改。** 接口是通用的，多一个客户端只是多一个调用方。

### 但要清楚代价

分离不是免费的，代价有三个，你们必须知道：

| 代价 | 表现 |
|---|---|
| 要跑多个进程 | 开发时要同时开前端、后端（可能还有 AI 服务） |
| 有跨域问题 | 浏览器会因为端口不同拦截请求 |
| 接口对不上 | 前端要的字段后端没给 → 最常见的返工来源 |

**对 16 周的学生项目，这个代价可以接受。而且这三个代价都有成熟的解法，下面逐个说。**

> **什么时候不该分离**：如果这是一个只有 3–5 个页面、纯展示、后端就是查数据库的项目，那用 Thymeleaf 模板渲染一个 jar 更省事。**但你的项目不是**——有 24 个页面、有 AI、有大量交互。

**推荐 monorepo（一个 Git 仓库装所有东西）**，学生团队不要搞多仓库——同步代码、对齐版本太麻烦。

```
greenthumb/
├── docs/                    # 设计文档（已有 8 份）
├── db/
│   └── schema.sql           # 建表脚本（已有）
│
├── frontend/                # ★ 前端 Vue 3（已有）
│   ├── src/
│   ├── package.json
│   └── vite.config.js
│
├── backend/                 # ★ 后端 Spring Boot（待建）
│   ├── src/main/java/com/greenthumb/
│   │   ├── GreenThumbApplication.java
│   │   ├── config/          # 配置类：CORS、Redis、拦截器
│   │   ├── controller/      # 接 HTTP 请求
│   │   ├── service/         # 业务逻辑
│   │   ├── mapper/ 或 repository/   # 数据库访问
│   │   ├── entity/          # 数据库表对应的类
│   │   ├── dto/             # 接口的请求/响应对象
│   │   ├── engine/          # ★ 规则引擎：养护计划计算、症状判因

│   ├── src/main/resources/
│   │   ├── application.yml
│   │   └── static/          # 前端打包产物放这儿（可选，见第 6 节）
│   └── pom.xml
│
├── ai-service/              # ★ Python AI 服务（待建）
│   ├── app/
│   │   ├── main.py          # FastAPI 入口
│   │   ├── routers/         # 接口
│   │   └── models/          # ONNX 模型文件
│   ├── requirements.txt
│   └── Dockerfile
│
├── deploy/
```

> **为什么 `engine/` 单独一个包**：规则引擎是这个项目的核心资产（养护计划计算 + 症状判因），单独放便于测试和维护。它应该是**纯计算逻辑，不依赖数据库和网络**——这样才好写单元测试。

## 2. 三个服务怎么跑起来

### 开发时的端口约定（★ 定死了别改）

| 服务 | 端口 | 谁访问 |
|---|---|---|
| 前端 Vite | **5173** | 浏览器 |
| 后端 Spring Boot | **8080** | 前端（通过代理）、AI 服务回调 |
| AI 服务 FastAPI | **8000** | 只有后端访问 |
| MySQL | 3306 | 后端 |
| Redis | 6379 | 后端 |

### 开发时开三个终端

```bash
# 终端 1 —— 数据库（跑一次就行）
docker compose -f deploy/docker-compose.yml up -d mysql redis

# 终端 2 —— 后端
cd backend && mvn spring-boot:run

# 终端 3 —— 前端
cd frontend && npm run dev
```

**AI 服务在 Phase 3 之前不需要启动**——它的活儿可以用百度 API 顶替。

## 3. ★ 接口契约先行（最重要的一条）

**学生项目最常见的翻车方式**：前端写完了，后端说"这个字段我没做"，然后返工一周。

**解法：先把接口文档定死，两边照着写。**

你们**已经有这份文档了** —— `docs/04-API接口设计.md`，约 55 个接口，每个都有请求和响应示例。这就是你们的"合同"。

### 统一响应体（三边必须一致）

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "traceId": "a1b2c3d4"
}
```

- `code = 0` 成功，非 0 是业务错误
- **前端已经按这个格式写了拦截器**（`src/api/request.js`），后端必须照做

### 后端怎么写才对得上

```java
// 1. 统一响应体
@Data
public class ApiResponse<T> {
    private int code;
    private String message;
    private T data;
    private String traceId;

    public static <T> ApiResponse<T> ok(T data) {
        ApiResponse<T> r = new ApiResponse<>();
        r.code = 0; r.message = "ok"; r.data = data;
        r.traceId = UUID.randomUUID().toString().substring(0, 8);
        return r;
    }
}

// 2. Controller 照契约写
@RestController
@RequestMapping("/api/v1/species")   // ★ 注意前缀 /api/v1
public class SpeciesController {

    @GetMapping
    public ApiResponse<PageResult<SpeciesVO>> list(SpeciesQuery query) { ... }

    @GetMapping("/{id}")
    public ApiResponse<SpeciesVO> detail(@PathVariable Long id) { ... }
}
```

### 约定好的三件事

| 约定 | 值 |
|---|---|
| URL 前缀 | `/api/v1` |
| 分页参数 | `?page=1&size=20`（page 从 1 开始） |
| 分页响应 | `{ list: [], total, page, size }` |

## 4. 联调怎么做（跨域问题怎么解决）

浏览器有「同源策略」：`localhost:5173` 的页面去请求 `localhost:8080`，**浏览器会拦截**，报 CORS 错误。

### 开发环境：用 Vite 代理（★ 已经配好了）

`frontend/vite.config.js` 里已经有：

```js
server: {
  port: 5173,
  proxy: {
    '/api':   { target: 'http://localhost:8080', changeOrigin: true },
    '/files': { target: 'http://localhost:8080', changeOrigin: true }
  }
}
```

**它的作用**：前端请求 `/api/v1/species`（看起来是同源的），Vite 开发服务器**在背后转发**到 `localhost:8080`。浏览器完全不知道有跨域这回事。

```
浏览器 → localhost:5173/api/v1/species
              ↓ Vite 代理转发（浏览器看不见）
         localhost:8080/api/v1/species
```

> **★ 所以开发阶段完全不用配 CORS。** 前端代码里写 `/api/v1/xxx` 就对了，`request.js` 的 `baseURL` 已经设成 `/api/v1`。

### 生产/演示环境：两种做法

| 做法 | 是否需要 CORS | 说明 |
|---|---|---|
| **Nginx 反代**（推荐） | ❌ 不需要 | Nginx 同时托管前端静态文件和转发 `/api`，还是同源 |
| 前后端分开域名部署 | ✅ 需要 | 后端加 CORS 配置 |

**如果确实需要 CORS**，后端这样配：

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOriginPatterns("*")     // 生产环境要写具体域名
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

## 5. 环境变量管理

**同一条代码，在开发和上线时连的地址不一样。** 用配置文件区分，不要硬编码。

### 前端（已有）

`.env.development`（开发）：
```
VITE_API_BASE=/api/v1
VITE_USE_MOCK=true
```

`.env.production`（上线）：
```
VITE_API_BASE=/api/v1
VITE_USE_MOCK=false
```

代码里通过 `import.meta.env.VITE_API_BASE` 读取。

### 后端

`application-dev.yml`（开发）和 `application-prod.yml`（生产），用 `spring.profiles.active` 切换。

**★ 不要把密码、API Key 提交到 Git**。用环境变量或本地配置文件，并在 `.gitignore` 里排除。

```yaml
# application-dev.yml
server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/greenthumb
    username: root
    password: ${DB_PASSWORD:123456}    # 优先读环境变量
  data:
    redis:
      host: localhost
      port: 6379
baidu:
  api-key: ${BAIDU_API_KEY:}           # 空值也能启动，只是识别不可用
  secret-key: ${BAIDU_SECRET_KEY:}
```

## 6. 部署的三种方式（按场景选）

### 方式一：开发时三个进程（第 2 节讲的）

### 方式二：★ 答辩演示用这个 —— 打成一个 jar

**前端打包后塞进 Spring Boot 的 static 目录**，最终只有一个 jar：

```bash
# 1. 打包前端
cd frontend && npm run build          # 产物在 frontend/dist/

# 2. 复制到后端的静态资源目录
cp -r frontend/dist/* backend/src/main/resources/static/

# 3. 打包后端
cd backend && mvn clean package

# 4. 跑起来（只需要这一个命令）
java -jar target/greenthumb.jar
```

然后访问 `http://localhost:8080` 就是完整应用。

**为什么答辩推荐这个**：
- **只有一个进程**，不用担心演示时前端服务挂了
- **同源，没有跨域问题**
- 老师看到的是一个完整的东西，不是"先开三个终端"

> **⚠️ 一个必须处理的坑**：Vue Router 用的是 history 模式，用户刷新 `/plants/12` 这种地址时，Spring Boot 会去找 `/plants/12` 这个接口 → 404。
>
> **解法**：加一个兜底，把所有找不到的路径转发到 `index.html`：
>
> ```java
> @Controller
> public class SpaFallbackController {
>     @RequestMapping(value = {"/{path:[^\\.]*}", "/**/{path:[^\\.]*}"})
>     public String forward() {
>         return "forward:/index.html";
>     }
> }
> ```

### 方式三：正式部署 —— Nginx

```nginx
server {
    listen 80;

    # 前端静态文件
    location / {
        root /var/www/greenthumb;
        try_files $uri $uri/ /index.html;   # Vue Router 兜底
    }

    # 后端接口转发
    location /api/ {
        proxy_pass http://backend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

## 7. Git 与分工

### 分支策略（简单版，够用）

```
main        ← 始终是可运行的版本，答辩前打 tag
  ↑
dev         ← 日常集成
  ↑
feature/xxx ← 每个人自己的功能分支
```

**规矩**：
- 不要直接往 `main` 推
- 每天早上先 `git pull`，避免最后合并冲突
- **提交前确保能跑起来**——推一个跑不起来的代码比不推还糟

### 分工建议（按 3–4 人算）

| 角色 | 负责 | 依据 |
|---|---|---|
| **前端** | 24 个页面、组件、联调 | 工作量最大，建议 1–2 人 |
| **后端业务** | 用户、植物、养护计划、提醒、日志 | 1 人 |
| **后端 AI 集成 + 规则引擎** | 识别接入、症状判因、RAG、定时任务 | 1 人 |
| **知识库 + 测试** | 50 篇养护卡片、QA 评测集、测试 | 可以兼职 |

> **★ 知识库整理不要留到最后。** 它是 RAG 效果的决定性因素，而且**只有人能写**，AI 写不出准确的养护经验。建议从第 2 周就开始，每周写 5 种植物。

## 8. ★ 出问题了怎么排查（前端还是后端？）

接口调不通时，**按这个顺序查**，不要瞎猜：

```
① 浏览器 F12 → Console 有红色报错吗？
   ├─ 有 CORS 报错 → 检查 vite.config.js 的 proxy 是否生效、后端是否启动
   └─ 没有 → 往下

② F12 → Network → 找到那个请求，看它的状态
   ├─ 请求根本没发出去 → 前端代码问题（api 路径写错了）
   ├─ 状态 404 → 后端没有这个接口，或路径前缀不对（是不是少了 /api/v1）
   ├─ 状态 401/403 → token 问题，检查请求头有没有 Authorization
   ├─ 状态 500 → ★ 后端报错了，去看后端控制台的堆栈
   └─ 状态 200 但数据不对 → 往下

③ 看 Response 的内容
   ├─ 是 HTML 而不是 JSON → 请求打到了前端自己的服务器（proxy 没生效）
   ├─ code 不是 0 → 业务错误，看 message
   └─ code 是 0 但 data 为空 → 后端查询逻辑问题

④ 前端拿到数据但页面没显示
   └─ 字段名对不上（后端返回 speciesName，前端读的是 species_name）
```

### 最快的一招：绕过前端直接测后端

用浏览器直接访问（GET 接口），或用 curl：

```bash
curl http://localhost:8080/api/v1/species?page=1&size=5
```

**如果这样能通，说明后端没问题，是前端或代理的问题。** 这一下就能把问题范围砍一半。

## 9. 常见坑清单（提前避）

| # | 坑 | 后果 | 预防 |
|---|---|---|---|
| 1 | 接口字段名不一致（驼峰/下划线） | 页面空白，数据不显示 | **契约先行**，定死命名风格（建议统一驼峰） |
| 2 | URL 前缀不一致（有的 `/api/`，有的 `/api/v1`） | 一半接口 404 | 全局统一，后端 `@RequestMapping("/api/v1/...")` |
| 3 | 忘了配 proxy | CORS 报错 | 已有配置，别删 |
| 4 | 前端 history 模式刷新 404 | 演示时刷新就白屏 | 加 SPA 兜底转发 |
| 5 | Token 过期没处理 | 用户莫名其妙被踢 | 前端拦截器已处理 1002 错误码 |
| 6 | 密码/API Key 提交到 Git | 泄露 | `.gitignore` + 环境变量 |
| 7 | 时间格式不统一 | 前端显示 `[object Object]` | 统一 `yyyy-MM-dd HH:mm:ss` |
| 8 | 分页参数对不上（0 开始还是 1 开始） | 第一页数据丢了 | 定死 **page 从 1 开始** |
| 9 | 前后端各自改了字段没同步 | 返工 | **改接口先改文档**，再通知对方 |
| 10 | 演示当天服务起不来 | 事故 | **提前打包成单 jar 演练一遍** |

```
  □ 前端把 VITE_USE_MOCK 改成 false，验证真实接口
  □ 先打通「植物库列表 + 详情」两个接口，跑通链路
```
