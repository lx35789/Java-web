## 2. 踩到的两个坑（都会让准确率虚高，且不报错）

### 坑 1：cross 里的芦荟与 main **完全重复**

抽样 800 张做 MD5 比对，**800/800 命中**。也就是说 cross 的 21,097 张里，
芦荟那 18,655 张是 main 的子集拷贝。

**处理**：cross 里的 Aloe 全部不取，只用新增物种 + 绿萝。
如果直接合并，等于把同一批图算了两次，而且会让测试集里出现训练集的原图。

### 坑 2：新物种每张原图被 Roboflow 增广成 3 份

`cross` 里 Snake_Plant / Spider_Plant / Money_Plant 的文件名形如：

```
Snake_Plant_Healthy_001_jpg.rf.dad37eb5ea33fb650617e55efea2e077.jpg
Snake_Plant_Healthy_001_jpg.rf.e27a5fd7e185fa45e969aa3f52fffd11.jpg   ← 同一张原图
Snake_Plant_Healthy_001_jpg.rf.f5d7aa5babe26bd43c8e70040650a900.jpg
```

实测每个"类别"的真实规模远小于文件数：

| 类别 | 文件数 | 独立原图 | 增广倍数 |
|---|---|---|---|
| Snake_Plant_Anthracnose | 199 | 81 | 2.5× |
| Snake_Plant_Healthy | 215 | 89 | 2.4× |
| Spider_Plant_Leaf_Tip_Necrosis | 219 | 91 | 2.4× |
| Cactus_Healthy | 285 | 285 | 1.0× |

**如果按文件随机切分**，同一张原图的 3 个副本会同时进训练集和测试集，
测试集准确率会虚高几个点——而且**不会抛异常、不会警告**，只会在答辩时被问倒。

**处理**：新增 `--group-split`（默认开）。
切分单位从"文件"改成"原图组"，同一原图的所有增广副本只落在同一个 split。
日志会打印每组数量：

```
切分：train=9407(400组)  val=1992(398组)  test=1998(395组)  按组切分=True
```

## 3. 数据准备流程

新增脚本 `ai-service/train/prep_combined.py`：

```bash
python train/prep_combined.py --cap-groups 400 --max-side 448
# 输出：D:\indoor-plant-data\combined_v2
```

它做四件事：

1. **递归扫描 main**（`<物种>/<类别>/`）与 cross（只取白名单类别）
2. **类名归一**：`Money_Plant_Bacterial_wilt_disease` → `Money_Plant_Bacterial_Wilt`
   （不归一的话同一种病会分裂成两个类，模型学不到东西，后端知识库也查不到）
3. **跨来源 MD5 去重**（只对 cross 候选，main 作为基准）
4. **按原图组限流**：`--cap-groups 400` 表示每类最多 400 个"原图"，
   增广副本整组保留；文件名前缀 `g0003__` 就是组号

### 坑 3（性能）：不缩放会把 GPU 利用率压到 10%

原始数据里有 **Rose 3000×3000、Aloe 3072×4080** 的图。
workers=0 时每步都在主线程解码大图，实测：

| 预处理 | 50 步耗时 | 单轮 |
|---|---|---|
| 不缩放（硬链接原图） | **262 s** | ~13 min |
| `--max-side 448` | **43 s** | ~2.2 min |

慢 6 倍，GPU 利用率只有 8%。上表 `general_prep`（v1 用的）本来就是 448px 的，
所以 v1 没暴露这个问题。

**结论**：训练前必须统一缩放。`--max-side 448` 对 160 输入留了 2.8 倍余量，
足够 RandomResizedCrop(scale 0.7–1.0) 和 15° 旋转。输出 393 MB。

## 4. 训练

```bash
python train/train_indoor.py \
  --data "D:\indoor-plant-data\combined_v2" \
  --out  "D:\indoor-plant-data\general_v2" \
  --arch mobilenetv3_large_100 \
  --img-size 160 --epochs 25 --batch 64 --cap 0 \
  --group-split 1
```

25 轮，55.2 分钟（RTX 4060 Laptop，8.6 GB）。

训练曲线（val_acc）：

| epoch | 1 | 4 | 8 | 11 | 15 | 18 | 23 | 25 |
|---|---|---|---|---|---|---|---|---|
| val_acc | 0.8283 | 0.9081 | 0.9222 | 0.9352 | 0.9378 | **0.9418** | 0.9413 | 0.9388 |

**没退步**：v1 是 29 类 0.9364，v2 是 37 类 0.9418。

## 5. 实测结果（测试集 1,998 张，全部为未参与训练的原图组）

整体：**top-1 94.2%、top-3 98.4%**（训练脚本自报 93.29% / 98.10%，
差异来自评估时的裁剪方式不是 center-crop，两者都如实记录）。

### 新物种（留出测试集）

| 类别 | 样本 | Top-1 |
|---|---|---|
| Cactus_Dactylopius_Opuntia | 51 | 96.1% |
| Cactus_Healthy | 42 | 100% |
| Snake_Plant_Anthracnose | 30 | 93.3% |
| Snake_Plant_Healthy | 37 | 100% |
| Snake_Plant_Leaf_Withering | 30 | 90.0% |
| Spider_Plant_Fungal_leaf_spot | 27 | 100% |
| Spider_Plant_Healthy | 27 | 100% |
| Spider_Plant_Leaf_Tip_Necrosis | 31 | 96.8% |

抽样 90 张经 HTTP 接口实测：**88/90 = 97.8%**。

### 老物种（回归检查）

菊花 / 扶桑 / 姜黄 / 绿萝 基本 100%，月季 91.7–100%。
**唯一明显偏弱的是芦荟**：

| 类别 | Top-1 |
|---|---|
| Aloe_Anthracnose | 50.0% |
| Aloe_Leaf_Spot | 58.3% |
| Aloe_Healthy | 76.7% |
| Aloe_Sunburn | 80.0% |
| Aloe_Rust | 83.3% |

原因不变：芦荟那 16,318 张是"叶片抠图 + 纯黑底"的合成数据（黑像素占 74–87%），
与真实拍摄分布差距大。**这也正是当初单独训专用模型的原因**，见下一节。

### 专用模型 vs 通用模型（芦荟 300 张测试图实测）

| 路由 | Top-1 |
|---|---|
| `species=Aloe` → 专用 5 类模型 | **70.3%** |
| 不传 species → 通用 37 类 | 67.7% |

只差 2.6 个百分点，但专用仍略优，**保持路由到专用模型不变**。
（单张图上会出现专用错、通用对的情况，所以必须用测试集量，不能凭单张下结论。）

## 8. 已知局限（如实写）

| 局限 | 证据 |
|---|---|
| 新物种样本很少 | 每类 81–92 个独立原图，且都来自 Roboflow 单一来源 |
| 新物种准确率偏乐观 | 训练/测试同源同分布；换真实手机照片会明显下降 |
| 芦荟仍弱 | 通用模型 50–83%，靠专用模型兜到 70.3% |
| 仙人掌只覆盖 2 类 | 只有"健康"和"胭脂虫"，没有软腐、日灼等常见问题 |
| 虎皮兰/吊兰各 3 类 | 没有叶斑病(虎皮兰)、根腐等 |

**要真正提升，只能补真实拍摄数据重训**，换模型结构解决不了分布差异。
