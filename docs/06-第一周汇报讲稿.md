## 一句话开场（15 秒）

> 各位老师好，我们的项目叫**植语助手**，是一个面向室内绿植的 AI 养护助手。
> 用一句话概括：**用户拍张照片，系统不只告诉他「这是绿萝」，还告诉他「接下来该怎么养、出了问题是什么原因」。**

---

## 第一部分：为什么要做这个项目（2.5 分钟）

### 1.1 先讲一个大家都有的经历

> 我想先问一个问题：**在座有谁养死过植物？**
> [停顿一下]
>
> 我养死过三盆绿萝。后来我去搜「绿萝多久浇一次水」，得到的答案是四个字：**「见干见湿」**。
>
> 这等于没说。

### 1.2 现有工具的「三个断层」

我们把市面上的方案梳理了一遍，发现它们各解决了一部分，中间有三个断层：

| 断层 | 现象 | 例子 |
|---|---|---|
| **认识了，但不会养** | 识花 App 告诉你「这是龟背竹」，然后就没有然后了 | 拍照识别很准，但不管后续 |
| **会养，但套不到自己家** | 网上养护文章千篇一律 | 都说「一周浇一次」，可我家有空调、用陶盆、放北向房间，凭什么和作者家一样？ |
| **出问题，不知道原因** | 叶子黄了，搜出来十种可能 | 浇水多了？少了？缺光？缺肥？你不知道是哪个 |

**说白了：现在缺的不是「认识植物」的工具，而是「养得活」的工具。**

### 1.3 我们的定位（★ 这是最重要的一句）

> 所以我们做的**不是又一个识花 App**，而是：

> ### 「会解释为什么的养护助手」

具体是三个能力：

1. **认得准** —— 拍照给出最可能的 3 种，**并且承认不确定**，让用户自己确认，而不是假装权威
2. **说得清** —— 每一个浇水建议都能拆解出依据，比如：基准 7 天 × 夏季 0.8 × 空调房 0.9 × 陶盆 0.9 = 5 天
3. **记得住** —— 养护计划、到期提醒、浇水日志形成闭环，慢慢积累成这盆植物自己的档案

### 1.4 为什么重点在「说得清」

> 这里要说一个我们的判断：
>
> **识别植物这件事，我们打不过大厂。** 他们有上百万张图片、有算力、有专业标注团队。我们在 16 周里训出来的模型，准确率一定不如百度、不如 Pl@ntNet。
>
> 但有一件事他们做不了：**「为什么这周要浇两次水？」**
>
> 通用识别 API 只能告诉你「这是什么植物」，它不知道你家有没有空调、用的是陶盆还是塑料盆、最近浇了几次水。**这个「结合你的情况给出可解释的建议」的能力，才是我们的价值所在。**

## 第二部分：怎么能做出来（2 分钟）

### 2.1 核心判断

> 我们做过可行性分析，结论是：**这个项目没有需要攻克的理论难题，全部是成熟技术的组合。**
>
> 换句话说，难点不在「能不能做」，而在「做得完做不完」。所以我们第一周花的最大精力，是**把技术风险提前找出来并解决掉**。

### 2.2 三个风险点，以及我们的对策

**风险一：植物识别的准确率**

> 实话实说，自己从零训练一个识别模型，16 周内很难做到好用。
>
> **对策：不自研也能用。** 百度有现成的「植物识别」接口，能识别 2 万多种植物，**3 块钱 1000 次**。我们整个项目算下来，识别费用不超过 5 块钱。
>
> **自研模型我们照样做，但定位改了**——不是产品的依赖，而是**论文里的对比实验**：用我们的真实照片，横向比较百度、Pl@ntNet 和自研模型的表现。这反而是更有价值的研究工作。

**风险二：病害识别没有数据**

> 我们一开始打算用学术界最常用的 PlantVillage 数据集，后来发现它有一个致命问题：**里面 14 种作物全是农作物——苹果、番茄、马铃薯，一种室内观叶植物都没有。**
>
> 番茄的病斑和绿萝的病斑，长得完全不一样，模型学不到东西。
>
> **对策：** 我们找到了一个真正覆盖室内植物的数据集，2 万多张图，里面有绿萝、虎皮兰、多肉。同时，商业 API 里也有病害识别服务，可以作为兜底。

**风险三：AI 问答会不会瞎编**

> **对策：** 用 RAG 方案——**先查资料，再回答**。系统先从我们整理好的养护知识库里检索相关内容，再把资料和问题一起交给大模型，并且要求它标注来源。
>
> 这样回答是有依据的，不是凭空生成。

### 2.3 一句话总结可行性

> **识别可以买，病害有数据，问答是标准工程。** 真正需要我们原创的，是「怎么把用户的描述变成判断依据」——也就是我们说的诊断逻辑。

## 第三部分：怎么搭建框架（3 分钟）

### 3.1 用一个类比讲清楚

> 我把整个系统比作一家**餐厅**：

| 系统部件 | 类比 | 干什么 |
|---|---|---|
| **前端** | 门店大堂 | 用户看到、点击、拍照的地方 |
| **后端** | 后厨 + 店长 | 所有业务规则：什么时候浇水、该提醒谁、怎么算 |
| **AI 服务** | 专用厨房设备 | 「识别植物」这一件事专门交给它 |
| **MySQL 数据库** | 仓库 | 存放所有数据：用户、植物、记录 |
| **Redis** | 手边的小抽屉 | 常用的东西放这儿，拿得快；也用来做知识库检索 |
| **外部 API** | 供应商 | 百度识别、天气数据 |

> 用户在大堂（前端）点单，店长（后端）按规则决定做什么，需要识别时交给专用设备（AI 服务），数据从仓库（数据库）取。

### 3.2 三层架构

```
        用户手机 / 浏览器
              │
    ┌─────────▼─────────┐
    │   前端  Vue 3      │   门店大堂：拍照、看计划、看诊断结果
    └─────────┬─────────┘
              │
    ┌─────────▼─────────────────────────┐
    │   后端  Spring Boot                │   ★ 大脑：所有业务规则在这里
    │   · 用户 / 植物 / 养护计划          │
    │   · 规则引擎：算浇水频率、判病因     │
    │   · 知识库问答编排                  │
    │   · 定时任务：每天生成提醒           │
    └──┬──────────┬──────────┬──────────┘
       │          │          │
  ┌────▼───┐ ┌───▼─────┐ ┌──▼──────────┐
  │ MySQL  │ │ Redis   │ │ Python AI   │  专用设备：识别
  │ 仓库   │ │ 抽屉    │ │ 识别服务     │
  └────────┘ └─────────┘ └──┬──────────┘
                            │
                    ┌───────▼────────┐
                    │ 百度 / Pl@ntNet │  供应商
                    └────────────────┘
```

### 3.3 整个系统最核心的一张表

> 如果只让我讲一个技术设计，我会讲**养护计划的生成规则**，因为它是我们「说得清」这个定位的落地。
>
> 逻辑很简单，就是**连乘**：

```
实际浇水间隔 = 植物基准间隔
             × 季节系数      （夏天 0.8，冬天 1.5）
             × 光照系数      （弱光 1.4，直射 0.85）
             × 温度系数      （高温 0.85，低温 1.3）
             × 湿度系数
             × 花盆材质系数  （陶盆 0.9，陶瓷盆 1.1）
             × 空调房系数    （0.9）
```

> 举例：绿萝基准是 7 天。夏天 ×0.8，空调房 ×0.9，陶盆透气 ×0.9，**算出来 5 天**。
>
> 重点在于：**这个 5 天不是一个黑盒数字，每一步都能给用户看。** 用户问「为什么是 5 天」，系统答得出来。

- **症状规则表** —— 把 35 条判因规则做成数据库记录，管理员可以在后台调权重，不用改代码

### 5.3 前端页面框架：24 个页面，可运行

> **这个可以现场演示。**
>
> 打开浏览器就能看到完整界面：植物库、我的植物、养护日历、AI 问答、智能诊断……
> 目前数据是模拟的，但**页面结构和交互流程已经全部打通**。
>
> 也就是说，后端只要把接口填上，界面立刻就能用。

### 5.4 一个可以现场演示的亮点：智能诊断

> 我们把「病害识别」和「症状诊断」合并成了一个三步向导：
>
> **拍照识别 → 病害识别 → 症状诊断**
>
> 比如用户说「叶子黄了」，系统会追问一句：**「黄叶是从下面的老叶开始，还是上面的新叶？」**
>
> 就这一句话，能把可能的原因从 10 种缩小到 2–3 种。
>
> 而且当信息不够时，系统**不会硬给一个结论**，而是说「目前信息不足，麻烦补充这几点」。
> **我们认为，承认不确定，比假装确定更值得信任。**

## 第六部分：16 周排期（1 分钟）

| 阶段 | 内容 | 周次 |
|---|---|---|
| Phase 1 | 基础业务闭环（不依赖 AI）：植物库、我的植物、养护计划、提醒、日志 | 2–5 周 |
| Phase 2 | 知识库问答（RAG） | 6–8 周 |
| Phase 3 | 植物识别（先接 API 跑通，模型训练并行） | 9–11 周 |
| Phase 4 | 病害识别 + 症状诊断 | 12–13 周 |
| Phase 5 | 天气集成、成长时间线、统计看板、论文与答辩材料 | 14–16 周 |

> **排期里最关键的一条**：Phase 1 完全不依赖 AI。
>
> 也就是说，**即使模型训练出问题，我们在第 5 周就已经有一个完整可用的产品了**。AI 是加分项，不是阻塞项。这是我们刻意做的风险控制。

## 第七部分：预判问答（★ 汇报前一定要看）

老师最可能问的问题，以及怎么答：

### Q1：AI 部分你们是不是就是调 API？自己做了什么？

> **这是最可能被问的问题，一定要答好。**
>
> 答：AI 用在四个地方，其中**三个是 API 做不了的**：
>
> 1. **物种识别** —— 这部分我们确实用 API 为主，因为大厂的数据和算力我们比不了。但自研模型我们仍然在做，作为**对比实验**。
> 2. **症状诊断** —— **API 完全做不了。** 黄叶是「结果」不是「原因」，同一张黄叶照片可能对应 10 种病因，任何识别 API 都只告诉你「这是什么植物」，判断不了「为什么黄」。这部分是我们自研的规则引擎，**35 条规则**。
> 3. **知识库问答** —— **API 做不了。** 需要自己整理语料、分块、向量化、检索、评测，是一整套工程。
> 4. **个性化养护计划** —— **API 做不了。** 结合用户家里的光照、花盆、空调情况算浇水频率，这是我们的规则体系。
>
> 而且我们有一个别人没有的东西：**用户的纠正数据**。
> 用户识别后如果纠正了结果，这条数据会存下来。积累几百条之后，我们就可以做一件没人做过的事：
> **评估主流识别 API 在「室内盆栽 + 手机随手拍」这个细分场景下的真实准确率。**
> 公开数据集测不出真实场景表现，各家官方的测试也都在通用场景。**这个评测是我们独有的。**

### Q2：识别准确率能做到多少？

> 答：我们的目标是 **Top-1 75% 以上，Top-3 92% 以上**。
>
> 但更重要的是：**我们的产品设计本来就不要求 100% 准确。** 系统给用户 Top-3，让用户确认或纠正。这既符合真实场景，也顺便帮我们收集了标注数据。

### Q3：数据从哪来？会不会有版权问题？

> 答：我们做过梳理：
> - **植物图片**：用公开数据集，但要注意它的授权是「仅限个人使用」，所以我们把它定位为**校内项目**，不对外发布
> - **病害图片**：用 CC BY 4.0 授权的公开数据集，合规
> - **养护知识**：**以我们自撰为主**，配合维基百科（CC BY-SA）。
>   我们特意**没有**整站抓取国外的园艺网站，因为那属于版权内容，批量入库有侵权风险。
>   而且自撰的 50 篇养护卡片，**质量比爬来的网页高得多**。

### Q4：16 周来得及吗？

> 答：来得及，因为我们做了两件事：
> 1. **Phase 1 不依赖 AI**，第 5 周就有可用产品
> 2. **识别先用现成 API 跑通链路，模型训练并行进行** —— 这是最容易出问题的环节，我们把它从关键路径上移走了
>
> 另外第一周我们已经把数据库和前端框架搭好了，进度是超前的。

### Q5：项目的创新点是什么？

> 答：三个层次：
> 1. **应用创新**：把「识别」和「养护」打通，并且强调**可解释性**——不只给结论，给依据
> 2. **方法创新**：把「生理性症状诊断」从图像分类问题**重新定义**为规则推理 + 知识检索问题。这是我们对问题的重新理解
> 3. **数据创新**：基于用户纠正数据，做主流识别 API 在室内绿植细分场景的横向评测

### Q6：如果模型效果不好怎么办？

> 答：这正是我们设计**降级链**的原因。
> 识别请求会依次尝试：百度 → Pl@ntNet → 自研模型。任何一家出问题都不影响产品可用。
> 而且**前端完全不用改**——因为我们早就把「用哪家」这件事隔离在后端了。

## 附录：术语 → 大白话对照表

汇报时如果担心用词太专业，可以随时换成大白话：

| 专业说法 | 大白话 |
|---|---|
| RAG 检索增强生成 | **先查资料再回答**，不是凭空编 |
| 规则引擎 | **一套计算公式**，把各种因素乘起来 |
| 向量检索 | 按**意思相近**找资料，不是按关键词 |
| Top-3 准确率 | 给的 3 个答案里**有正确的那一个**的比例 |
| 降级链 | **备胎机制**，一个不行就换下一个 |
| 系数拆解 | 把数字怎么算出来的**一步步列出来** |
| 可解释性 | **能说出为什么** |
| 数据闭环 | 用户用得越多，数据越多，系统越好 |
| 幂等 | 同一件事**做多次和做一次结果一样**（防止重复提醒） |
