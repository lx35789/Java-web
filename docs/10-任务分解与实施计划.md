## 第一部分 · 职责划分

## 1. 一句话原则

> ### 前端：把数据变成人能看懂的东西，并收集用户的输入
> ### 后端：所有「算」和「判」，以及保证数据不丢不乱

---

## 2. ★ 三条不可动摇的分工红线

这三条如果搞错，后面会大返工：

### 红线一：**所有判断和计算，一律放后端**

包括：浇水间隔怎么算、病因怎么判、识别结果怎么融合、提醒什么时候生成。

**为什么**：

| 如果放前端 | 后果 |
|---|---|
| 用户能改 | 打开开发者工具就能把"建议 5 天"改成 500 天，规则就不权威了 |
| 加小程序要重写 | 换个客户端就得把规则逻辑抄一遍，还容易抄错 |
| 没法统一 | 网页和小程序算出不同结果，用户会困惑 |
| 没法测试 | 前端代码很难写单元测试 |

**正确做法**：后端算好，把**结果和依据一起返回**。

```json
// 后端不只返回 5，还返回为什么是 5
{
  "effectiveIntervalDays": 5,
  "baseIntervalDays": 7,
  "coefficientDetail": { "season": 0.8, "pot": 1.1, "ac": 0.9 },
  "calculation": "基准 7 天 × 夏季 0.8 × 空调房 0.9 × 釉面陶瓷盆 1.1 ≈ 5.4 天 → 取 5 天"
}
```

前端只负责**把这个拆解渲染成表格**。

### 红线二：**数据库只有后端能碰**

前端**永远不直连数据库**，也不应该知道表结构和 SQL。

**为什么**：直连数据库等于把数据库密码发给每一个用户。这是安全底线，不是风格问题。

### 红线三：**接口文档是唯一的合同**

前端要什么字段、后端给什么字段，**以 `docs/04-API接口设计.md` 为准**。

改接口 → **先改文档 → 再通知对方 → 然后才动代码**。

> **★ 这条最容易违反，也最容易造成返工。** 后端悄悄把 `speciesName` 改成 `plantName`，前端页面就白了，然后两边互相甩锅。

## 3. 逐模块职责对照表

### 3.1 认证与用户

| 前端 | 后端 |
|---|---|
| 登录/注册表单、校验提示 | 密码加密（BCrypt，**绝不明文存**） |
| 存 token 到 localStorage | 签发 JWT、验证签名 |
| 请求拦截器自动带 `Authorization` | 校验 token，过期返回 1002 |
| 收到 1002 自动跳登录页 | 登出时把 token 加入 Redis 黑名单 |
| 个人中心表单 | 用户信息增删改查 |
| 环境设置表单（城市、空调） | **城市名 → 经纬度**（调 Geocoding）并缓存 |

> **注意**：token 存 localStorage 有 XSS 风险，但对学生项目可接受。想更安全就存 httpOnly Cookie，代价是跨域配置更麻烦。**建议先用 localStorage，够用。**

### 3.2 植物库

| 前端 | 后端 |
|---|---|
| 列表页、搜索框、筛选器 | 按条件查询，支持模糊搜索 |
| 分页组件 | 分页（**page 从 1 开始**） |
| 详情页排版 | 返回完整属性 + 季节系数 |
| **不缓存数据** | **Redis 缓存**（50 条热数据，基本不变） |
| 难度/光照/毒性的标签展示 | 返回枚举原始值（`MEDIUM`），前端查字典转中文 |

> **关键**：后端返回 `"MEDIUM"`，**不返回 `"中等光照"`**。翻译是前端的事（字典在 `src/utils/constants.js`）。这样以后要改文案不用动后端。

### 3.3 我的植物

| 前端 | 后端 |
|---|---|
| 卡片列表、筛选 | 按用户查询，注意**只能查自己的** |
| 新增/编辑表单 | 保存，**自动生成初始养护计划** |
| 位置/光照/花盆的选择器 | 校验参数合法性 |
| 时间线展示（照片按时间排） | 返回照片列表 |
| 自然语言输入的解析结果确认界面 | **调 LLM 解析**"我新买了一盆龟背竹，放在客厅" |

> **★ 权限**：所有"我的"接口，后端必须校验 `user_id`，**不能只靠前端传的 id**。
> 否则用户改一下 URL 里的 id 就能看别人的植物。这是最常见的越权漏洞。

### 3.4 照片与文件

| 前端 | 后端 |
|---|---|
| 拍照/选图、本地预览 | 接收 multipart 上传 |
| **上传前压缩**（长边 1024、JPEG q80） | 校验格式和大小（jpg/png，≤10MB） |
| 进度条 | **EXIF 旋转矫正**（手机竖拍不处理会横过来） |
| 删除确认 | 生成缩略图、存 MinIO 或本地 |

> **★ EXIF 矫正必须做。** 手机拍的照片带旋转信息，不处理的话用户看到的图是歪的。这是"前端明明显示正常、后端存下来却是歪的"的经典原因。

### 3.5 拍照识别

| 前端 | 后端 |
|---|---|
| 上传 + 触发识别 | 图片预处理（归一化到 224×224） |
| 展示 Top-3 卡片、置信度标签 | **调用识别供应商** |
| 低置信度警告 | **降级链**：百度 → Pl@ntNet → 自研模型 |
| "就是它" / "识别不准" 按钮 | **结果归一化**：把供应商返回的名称映射到 50 种植物库 |
| 采纳后跳转 | 记录纠正数据（`confirmed` 字段） |

> **★ 前端完全不需要知道用的是哪家 API。** 它只看 `provider` 字段然后显示个标签。
> 这就是第一轮设计里"双通道 + provider 字段"的价值。

### 3.6 智能诊断（病害 + 症状）

| 前端 | 后端 |
|---|---|
| 三步向导的步骤流转 | 各步骤的接口 |
| 症状勾选、叶片位置必选 | **病害模型调用** |
| 上传照片 | **★ 自动采集判因上下文**（见下） |
| 渲染判断依据、建议步骤 | **★ 规则引擎判因** |
| 置信度不足时展示追问 | RAG 检索 + LLM 润色 |
| 病历卡片 | 落库诊断记录 |

**★ 症状诊断里前端和后端的分工特别要注意**：

| 数据 | 谁提供 |
|---|---|
| 症状标签 | **前端**（用户勾选） |
| 叶片位置 | **前端**（用户回答，必选） |
| 植物种类 | 前端传 id |
| **近 14 天浇水次数** | **★ 后端自己从 `care_log` 算** |
| **浇水频率比** | **★ 后端算** |
| 光照 / 花盆材质 | **★ 后端从 `user_plant` 读** |
| 温度 / 湿度 | **★ 后端调天气 API** |
| 季节 | **★ 后端按日期判断** |

> **前端只传用户能看见、能回答的东西。**
> 其他的全部由后端自己采集——**用户不该为了诊断去填"我最近浇了几次水"，系统自己数得出来。**
> 这是"降低使用门槛"的关键设计。

### 3.7 养护计划

| 前端 | 后端 |
|---|---|
| 系数拆解表格（`CarePlanExplain` 组件） | **★ 规则引擎计算** |
| 计划卡片、下次到期日 | 系数体系（季节/光照/温度/湿度/花盆/空调） |
| "重新生成"按钮 | 边界限制（clamp 到 2–30 天） |
| 手动覆盖间隔 | 保存系数明细 `coefficientDetail` 供前端展示 |
| | **LLM 把结果润色成自然语言** |

> **★ LLM 只做表达，不做决策。** 数字全部来自规则引擎。
> 即使 LLM 挂了，降级返回结构化文本，**建议的数字依然是对的**。

### 3.8 提醒任务

| 前端 | 后端 |
|---|---|
| 日历组件（自定义格子渲染） | 按月份查任务 |
| 今日待办列表 | 查今天 + 逾期的 |
| "标记完成"按钮 | **★ 同时写 care_log + 回填关联 + 算下一个到期日** |
| 跳过 / 延后 | 更新状态 |
| | **★ Spring Scheduler 每天 02:00 生成任务** |

> **★★ 定时任务必须幂等**：`care_task` 表上有 `UNIQUE(plan_id, due_date)`。
> 没有这个约束，服务重启或重跑就会生成一堆重复提醒，用户会被烦死。

### 3.9 养护日志

| 前端 | 后端 |
|---|---|
| 日志列表、筛选（植物/类型/日期） | 条件查询分页 |
| 补录表单 | 新增记录 |
| 删除确认 | 软删除 |
| 类型标签着色 | 返回枚举值 |

### 3.10 AI 问答

| 前端 | 后端 |
|---|---|
| 会话列表、消息气泡 | 会话和消息的增删查 |
| **★ SSE 流式接收**（逐字显示） | **★ 检索知识库 → 拼 Prompt → 调 LLM → 流式返回** |
| 展示"检索到的资料"折叠区 | 返回 `retrievedChunks` 供前端展示 |
| 来源标注渲染 | 返回 `citations` |
| 有用/没用 反馈按钮 | 记录反馈 |

> **★ 前端要做的最重要一件事是"流式接收"。** 目前 mock 是一次性返回，接后端时要改成读 SSE：
> ```
> retrieval → delta → delta → ... → citations → done
> ```
> 先发 `retrieval` 事件，前端立刻显示"正在检索到的资料"——**用户能感知到回答是有依据的**。

### 3.11 统计看板

| 前端 | 后端 |
|---|---|
| 指标卡片 | 聚合查询 |
| ECharts 折线图、饼图 | 返回趋势数据 |
| 快捷入口 | — |

### 3.12 天气

| 前端 | 后端 |
|---|---|
| 展示当前温度湿度 | 调 Open-Meteo |
| 展示"对养护计划的影响" | **★ 返回系数和解释**（`impactOnCare`） |
| 手动同步按钮 | **★ 城市名先转经纬度**（Open-Meteo 只吃坐标） |

### 3.13 管理端

| 前端 | 后端 |
|---|---|
| 5 个管理页面、表格 | 管理端接口 |
| 症状规则权重可编辑 | 更新规则（**改完立刻生效**） |
| 知识库"重建索引"按钮 | **重新分块 + 向量化** |
| AI 用量图表 | 调用统计 + 配额 |

## 4. 三个容易扯皮的地方（提前定好）

| 事项 | 谁做 | 说明 |
|---|---|---|
| **表单校验** | **两边都做** | 前端为了体验（即时提示），后端为了安全（**前端校验可以被绕过**） |
| **分页排序筛选** | **后端做** | 前端只传参数，不做本地过滤（数据量大时前端扛不住） |
| **数据格式化** | **前端做** | 后端返回 `0.625`，前端显示 `62.5%`；后端返回 `"MEDIUM"`，前端显示"中等光照" |
| **权限校验** | **后端做** | 前端隐藏按钮只是体验，不是安全 |
| **错误文案** | **后端给码，前端给文案** | 后端返回 `code: 3003`，前端查字典显示"今日 AI 识别次数已用完" |

## 第二部分 · 怎么完成

## 6. ★ 三条线并行，不要串行

这是完成项目的关键组织方式：

| 线 | 谁负责 | 什么时候开始 | 为什么重要 |
|---|---|---|---|
| **业务线**（Java 后端） | 1–2 人 | **第 2 周** | 主线，别的都挂在这上面 |
| **知识线**（写养护卡片、定规则） | 1 人（可兼职） | **★ 第 2 周就开始** | 最容易被拖到最后，**但它是 RAG 效果的决定因素** |
| **AI 线**（识别接入、模型训练） | 1 人 | 第 4 周开始调研，第 9 周正式做 | 最不可控，所以要**移出关键路径** |

**★ 知识线为什么必须早开始**：

- 50 篇养护卡片，每篇 300–500 字，共约 2 万字 → **每周写 5 篇，10 周写完**
- **只有人能写**，AI 写不出准确的养护经验
- 它决定了 RAG 问答的质量——**这是你们项目的核心卖点之一**
- 如果拖到第 13 周才开始，一定写不完，而且质量差

> **建议：把"每周写 5 篇养护卡片"当成硬性任务，和写代码同等重要。**

## 9. 风险与应对

| 风险 | 概率 | 应对 |
|---|---|---|
| **接口对不上，反复返工** | 高 | 契约先行；**先打通一个接口**再铺开 |
| **知识库写不完** | **高** | 第 2 周就开始，每周 5 篇，当硬任务 |
| 模型训练效果差 | 中 | 已移出关键路径；API 兜底；改成对比实验 |
| 后端进度慢 | 中 | 优先做 P0；**Phase 1 不依赖 AI** 就是为了这个 |
| 越权漏洞 | 中 | 所有"我的"接口强制校验 user_id |

## 11. ★ 明确「不做什么」（防范围膨胀）

**这是学生项目失败的头号原因：什么都想做，结果什么都没做完。**

| 不做 | 为什么 |
|---|---|
| ❌ 社区 / 评论功能 | 初版写了"可选"，**直接砍掉**。和核心价值无关 |
| ❌ 智能花盆 / 自动浇水 | 硬件项目，完全不同赛道 |
| ❌ 全植物百科 | 50 种够用，做多了每种都是空壳 |
| ❌ 真实支付 | 无意义 |
| ❌ 复杂社交（关注/私信/动态） | 同上 |
| ❌ 自研大模型 | 不可能，也没必要 |
| ❌ 多端（小程序/App） | 后端接口化就行，**别在第 10 周才开始写第二个端** |
| ❌ 追求识别准确率超过商业 API | 打不过，别浪费生命 |

### 如果有人提新需求，用这三句话挡回去

1. **「它服务于 S1/S2/S3 哪个场景？」**（三个核心场景见 `docs/02` 第 1.5 节）
2. **「不做它，项目还完整吗？」** —— 如果还完整，就不做
3. **「这个能放到第 14 周之后吗？」** —— 能就往后放，多半最后就砍了

## 12. 每周固定动作（养成习惯）

| 时间 | 做什么 |
|---|---|
| **周一** | 15 分钟站会：上周完成什么、这周做什么、卡在哪 |
| **每天** | `git pull` 再开始写；**提交前确保能跑起来** |
| **周五** | 更新进度表；**演示一次当前能跑的东西**（不能跑就说明这周白干） |
| **每周** | 写 5 篇养护卡片（知识线，别停） |

> **★「周五演示一次」是最好用的项目管理手段。**
> 它逼着大家每周产出可运行的东西，而不是"写了一堆代码但跑不起来"。
