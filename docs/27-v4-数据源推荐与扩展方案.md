# 27 · v4 扩展方案：室内绿植的病害识别

> 承接 `docs/26`（v3：10 物种 / 44 类）。目标是**再扩一批室内绿植物种**。
> 本文只列我逐个核对过许可、规模、格式的来源，以及各自的真实代价。

## 0. 结论（先看这个）

**坏消息：室内绿植的公开病害数据极其稀缺。** 龟背竹、橡皮树、发财树、
白掌、常春藤、竹芋、君子兰这些中国家庭最常见的观叶植物，
**我没有检索到任何一个带病害标注的公开数据集**。

能落地的是三条路，按"马上能干"排序：

| 路线 | 内容 | 新增 | 代价 |
|---|---|---|---|
| **A** | 兰花（蝴蝶兰类） | +1 物种 / +5~6 类 | 下载 695 张 + 裁框转分类 + 补健康类 |
| **B** | Houseplant Diseases Collection | +11 病类 + 1 健康 | **需申请权限**（文件 Restricted），拿到后要解决编码架构问题 |
| **C** | 自采（龟背竹等头部物种） | 每物种 2~4 类 | 每个物种约 300 张实拍 + 标注，唯一出路 |

**明确排除**：PlantVillage / PlantDoc / Master Plant Disease（农作物，定位不符）；
辣椒、番茄等蔬果（不是室内绿植）。

---

## 1. 为什么这么少

不是检索不够。原因有两个：

1. **学术投入错配**。农作物的病害损失能算成钱，室内观赏植物的商业价值低，
   数据集基本来自少数课题组的顺手之作。现有 44 类的源数据，
   高度集中在几个孟加拉高校课题组（芦荟、仙人掌、绿萝、虎皮兰、吊兰、
   月季、扶桑、万寿菊），本质上是同一批人做的系列数据集。
2. **"室内植物"数据集大多指向同一批物种**。我核对了 6 个标称"indoor /
   houseplant"的数据集，其中 4 个最终都收敛到芦荟、仙人掌、绿萝、虎皮兰、
   吊兰这 5 个物种——**正是项目已经覆盖的**。

所以真正的增量只有下面三个来源。

## 3. 路线 B 的架构问题（这一步想清楚再申请）

现有 `labels.json` 的类码是 `物种_病害` 两段式，`app/disease.py` 靠
`_` 前缀做物种过滤和路由。如果 B 的 12 个类是**跨物种的病害级**
（例如"白粉病"一个类覆盖月季、菊花、扶桑），现有结构装不下：

- 只能塞进某个物种前缀下 → 该病害在其他物种上永远识别不出来
- 或者新建 `General_Powdery_Mildew` → 物种过滤会把它当第 11 个物种，
  `speciesMass` 算错，前端还会把它列进"支持物种"

真要接，需要做一次小幅改造，两条路选一条：

1. **加"通用病害层"**：标签新增 `scoped: "global"` 字段，物种过滤时
   把 global 类一起保留，`speciesClassCount` 分为"专属/通用"两栏
2. **只取能确定物种的子集**：B 里凡是能对上现有 10 物种的图，并进现有类；
   对不上的丢弃。改动量最小，但浪费大半数据

我的建议是 **1**，但它是这一轮唯一需要动推理逻辑的改动，
要先确认 B 的数据形态再决定，别提前动手。

## 4. 路线 A：兰花（唯一"今天能开工"的）

蝴蝶兰是国内销量最高的室内观花盆栽之一，值得进模型。

要做四件事：

1. **下载**：Roboflow 项目页 → Download Dataset → YOLO 格式（含框）
2. **裁框转分类**：用框裁出病斑区域，四周留 20% 余量，输出
   `<class_code>/<gid>__<原名>.jpg`。`gid` 用原图文件名（同一张图的多个框同组），
   保证 `--group-split 1` 不会把同一张原图切到训练和测试两边
3. **补健康类**：数据集没有 healthy。要么从 `Indoor Plants Classification`
   （Mendeley 10.17632/59rz3cj69v.1，1,920 张 10 类）里找兰科图，
   要么自拍 150 张。**没有健康类的新物种不能进模型**——患病图会被判成
   该物种最像的那个病害，置信度还很高
4. **核类名**：数据集里有个类叫 `Bacillus_Anthracis`（炭疽杆菌，动物病原），
   兰花炭疽病的病原其实是 *Colletotrichum*。这类教科书级错误说明标注者
   不是植保专业，**每类抽 10 张人工过一遍**再入库

产物约 6 类（5 病 + 1 健康），物种数 10 → 11。

## 5. 路线 C：自采（头部物种的唯一出路）

龟背竹、橡皮树、发财树、白掌、常春藤、竹芋、君子兰没有公开数据，
只能自己攒。这件事没有捷径，但可以把成本压下来。

### 5.1 优先序

| 优先级 | 物种 | 理由 |
|---|---|---|
| 1 | 龟背竹 | 观叶第一网红，几乎人手一盆 |
| 2 | 白掌 | 室内开花+观叶，销量高 |
| 3 | 橡皮树 | 大型盆栽常见，叶斑/落叶问题多 |
| 4 | 常春藤 | 垂吊类代表，红蜘蛛高发 |
| 5 | 竹芋 | 叶色敏感，焦边/日灼咨询量极大 |
| 6 | 君子兰 | 中老年用户多，烂根/叶斑典型 |

### 5.2 数量与拍摄规范

- **每个物种**：健康 150 张 + 每种病害 100 张。低于 100 张不进模型
  （现有 `Tagetes_Pest_Damage` 只有 10 张测试图，80% 的逐类指标毫无意义，
  `docs/26` 第 8 节已承认这点）
- **构图**：与训练分布一致最重要。每类都要有"整株+背景"和"叶片特写"两档，
  各占一半。项目在 `docs/25` 栽过"全是叶片特写 → 真实照片识别不了"的坑，
  `app/disease.py` 的多尺度重试（`MULTI_SCALE_*`）是补丁不是解法
- **光线**：自然散射光，避免闪光灯直射和强逆光
- **命名**：`gid__原名.jpg`，**同一株植物必须同组**，否则同一株会跨训练/测试集

### 5.3 采集渠道

1. 自己家 + 朋友家（最真实，就是目标场景）
2. 本地花市 / 花店：一天能拍十几个物种，跟店主打个招呼即可
3. 花友群 / 小红书 / 贴吧：招呼一声征集，比爬虫省事且能拿到授权
4. 电商详情页：量大但版权不清，只能内部验证用，**不要进发布模型**

### 5.4 半自动标注（省 70% 时间）

纯手工标 300 张一个物种太慢。可行的流水线：

1. 先用现 v3 模型 + 多模态大模型各自打一个初标
2. 只把两者**不一致**的样本挑出来人工判 —— 实测这类样本通常占 20~30%
3. 一致的直接过，人工只做抽检

`experiments/` 下的 `multidl.py` 和 `run_validation*.py` 已经有调用多模态
模型的代码，可以改造成这个用途。

## 6. 工程改动清单（无新增物种时不生效）

改 5 处，漏任何一处都会静默出错、不报异常。

### 6.1 `ai-service/train/train_indoor.py`（最容易漏）

```python
# 第 34 行 CN：中文展示名，不加则 App 里显示英文 code
"Orchid_Soft_Rot": "兰花·软腐病",

# 第 75 行 SPECIES_PREFIX：物种前缀，不加则 labels.json 的 species 字段写错
SPECIES_PREFIX = [..., "Tagetes", "Orchid"]
```

**为什么 `SPECIES_PREFIX` 是硬要求**：`split_code()` 靠它把
`Orchid_Soft_Rot` 拆成 `("Orchid", "Soft Rot")`。不在列表里会退化成
`species = 整个 code`，于是后端 `SpeciesKeys.keyOf("兰花")` 返回 null，
永远不带物种参数，AI 服务不做物种过滤——兰花照片可能被判成"月季·黑斑病"，
全程不报错。

### 6.2 训练

```powershell
python ai-service/train/train_indoor.py `
  --data D:\indoor-plant-data\combined_v2 `
  --extra-data experiments\data\mendeley_v3 experiments\data\orchid_v4 `
  --out experiments\data\general_v4 `
  --arch mobilenetv3_large_100 --img-size 160 --epochs 20 --batch 64 `
  --lr 2e-3 --cap 800 --workers 0 --group-split 1 --pretrained 0 `
  --init-checkpoint experiments\data\general_v3\best.pt `
  --bg-random 0.15 --bg-dir D:\indoor-plant-data\main --auto-crop 1
```

`--init-checkpoint` 指向 v3：新增 6 类不该让已有 44 类从零重学。
`--group-split 1` 不是可选项（`docs/25`）。

### 6.3 数据库

- `db/seed_disease_v4.sql`：`code` 必须与 `labels.json` 完全一致，
  否则识别出病名但查不到防治方法，前端只剩一个孤零零的类名
- `db/seed_species_v4.sql`：兰花要进 `species` 表，否则植物档案里选不到

### 6.4 后端 `SpeciesKeys.java`

```java
PREFIX.put("兰花", "Orchid");
PREFIX.put("蝴蝶兰", "Orchid");   // 同物异名
```

### 6.5 前端不用改

`DISEASE_COVERED_SPECIES` 已改成从 `/diagnoses/model-status` 读
`coveredSpecies`，换模型自动跟随。

### 6.6 部署后自检

```bash
python ai-service/train/verify_deploy.py --token <登录token>
```

核对模型文件 / AI 服务类数 / 后端 coveredSpecies / SpeciesKeys 四处一致。

## 8. 验收标准

以路线 A 为例，四条必须同时成立：

1. `labels.json` 里 `Orchid_*` 都在，且 `species` 字段是 `Orchid` 不是完整 code
2. `GET /health` 返回 `numClasses` = 44 + 新增类数
3. `/api/v1/diagnoses/model-status` 的 `coveredSpecies` 含"兰花"
4. 3 张实拍（健康/软腐/褐斑）实测：`speciesMass` > 0.20，Top-1 落在对应类
